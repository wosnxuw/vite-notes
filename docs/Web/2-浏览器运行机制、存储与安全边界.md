# 浏览器运行机制、存储与安全边界

这一篇建立对浏览器的底层心智模型，回答四个日常开发与排障中反复撞上的问题：**浏览器拿到 HTML/CSS/JS 后是如何把画面画出来的？为什么 JS 是单线程却不会轻易卡死？为什么同一个接口 `curl` 能通、放进浏览器却报 `CORS` 错误？前端数据该存在 Cookie、`localStorage` 还是 `IndexedDB`？**

理解浏览器的捷径，是不要把它当成“文档阅读器”，而要把它当成**一台专门运行不可信远程代码的微型沙箱操作系统（Sandbox OS）**。后面所有的渲染规则、事件循环和安全边界，都是从这个定位自然推导出来的。

---

## 一、多进程沙箱与页面渲染管线

### 1. 为什么开一个浏览器，任务管理器里冒出十几个进程？

现代浏览器（Chromium / WebKit / Gecko）普遍采用**多进程架构**：
- **浏览器主进程（Browser Process）**：管地址栏、书签、前进后退、磁盘文件与网络调度。
- **渲染进程（Renderer Process）**：默认按站点隔离，负责解析 HTML/CSS、执行页面 JS 和排版。它被操作系统放进严格的**沙箱**里——页面里的 JS 绝对不能直接读写你的本地硬盘、调系统命令或偷看另一个标签页的内存；即使某个网页写出了死循环崩掉，也只炸掉那一个标签页，不会带崩整个浏览器。
- **GPU 进程**：统一接管各标签页的图形合成与硬件加速（WebGL / WebGPU 也走这里）。
- **网络进程**：统一管理 HTTP 连接池、DNS 缓存、Cookie 与 TLS。

### 2. 从代码到像素：渲染管线（对标图形学管线）

浏览器拿到 HTML 和 CSS 文本后，需要经过一条固定的流水线才能变成屏幕上的像素：

1. **解析（Parse）**：把 HTML 解析成 **DOM 树**（节点结构），把 CSS 解析成 **CSSOM 树**（样式规则），两者结合生成只包含可见元素的 **Render Tree（渲染树）**。
2. **布局（Layout / 重排 Reflow）**：计算每个节点在屏幕上的精确几何位置和宽高（这一步计算量最大，改一个元素的尺寸往往会连锁影响整页排版）。
3. **绘制（Paint / 重绘 Repaint）**：把文字、颜色、边框、阴影光栅化成位图图层。
4. **合成（Composite）**：把多个独立图层交给 **GPU 进程**拼合成最终屏幕帧（概念上类似 OpenGL 的多图层帧缓冲合成）。

## 二、单线程模型与 Event Loop（事件循环）

### 1. 为什么 JS 主线程是单线程的？

渲染进程的主线程同时负责**跑 JS 代码**和**更新 DOM / 渲染页面**。之所以不做成 C++ 那种多线程并发，是因为 DOM 树是共享可变状态——如果线程 A 正在删除一个按钮，线程 B 同时修改这个按钮的文字，就必须给整棵 DOM 树加满锁，不仅复杂度爆炸，还极易死锁。

### 2. 单线程怎么做到 I/O 不阻塞？（类比 `tokio` / `asyncio`）

JS 的异步并发模型和 Rust 的 `tokio`、Python 的 `asyncio` 异曲同工：**主线程只跑一个事件循环（Event Loop），所有耗时操作不自己在主线程里死等，而是甩给浏览器底层（网络进程、定时器线程）异步执行，完事后把回调函数推进任务队列排队。**

事件循环里有两类优先级不同的队列：
- **宏任务（Macrotask）**：`<script>` 整体代码、`setTimeout` / `setInterval`、鼠标点击/键盘等 UI 事件、I/O 回调。
- **微任务（Microtask）**：`Promise.then / catch / finally`、`async / await` 暂停之后继续执行的那半段代码、`queueMicrotask`。

主线程的循环节拍固定为：
1. 从宏任务队列取 **1 个**任务，在调用栈里把同步代码一口气跑完；
2. 立刻把**微任务队列彻底清空**（如果在清空过程中又产生了新的微任务，也一并清完）；
3. 如果距离上一帧已到刷新时机（如 16.6ms 对应 60Hz），执行一次 **Layout → Paint → Composite 渲染**；
4. 回到第 1 步，取下一个宏任务。

> **两条直接影响架构设计的铁律**：
> 1. **主线程怕同步重计算，不怕异步等 I/O**：并发发 20 个 `fetch` 不会卡页面；但在主线程里写一个耗时 2 秒的纯 JS 大循环（或解析几十 MB 的大 JSON），浏览器根本抢不到机会进入第 3 步渲染，整个页面会彻底冻住。
> 2. **重计算怎么解？** 浏览器提供了 **Web Worker**——可以另起一个真正的独立后台线程跑密集计算（或跑编译成 WebAssembly 的 C++/Rust 代码）。Worker 不能直接操作 DOM，只能通过消息通道 `postMessage` 和主线程交换数据（类似并发编程里的 Actor / Channel 模型）。

## 三、彻底搞懂同源策略（SOP）与 CORS

前端联调中最经典的困惑莫过于：**“这个后端接口我用 `curl` 和 Postman 调得好好的，怎么一放进前端网页代码里就报红字 `blocked by CORS policy`？”**

根源很简单：**CORS 是浏览器单方面执行的安全守卫，后端服务器本身和 `curl` 根本没有这套限制。**

### 1. 什么是“同源（Same-Origin）”？

一个 URL 的**源（Origin）**由且仅由三部分决定：**`协议（Scheme）` + `域名（Host）` + `端口（Port）`**。三者必须**完全一致**才叫同源，差任何一个都叫**跨域（Cross-Origin）**。

注意不要把跨域误解成“IP 不同”——即便两个域名解析到同一台服务器的同一个 IP，只要子域名、协议或端口不同，浏览器依然判为跨域。以 `https://app.example.com`（默认 443 端口）为例：

| 请求目标 URL | 是否同源 | 原因 |
| :--- | :--- | :--- |
| `https://app.example.com/api/chat` | **同源** | 协议、域名、端口全一致（路径不同不算跨域） |
| `http://app.example.com/api/chat` | **跨域** | 协议不同（`http` vs `https`） |
| `https://api.example.com/chat` | **跨域** | 子域名不同（`api.` vs `app.`） |
| `https://app.example.com:8000/chat` | **跨域** | 端口不同（`8000` vs `443`） |

### 2. 浏览器为什么要设同源策略（SOP）？

假设你刚在标签页 A 登录了公司内网系统或网银（浏览器存着该站的登录 Cookie），紧接着在标签页 B 点开了一个陌生网站。

如果没有同源策略，陌生网站的 JS 就可以偷偷执行 `fetch("https://bank.com/api/balance")`。浏览器发出请求时可能会自动带上你在 `bank.com` 的 Cookie，如果陌生网站还能把返回结果读出来再发给黑客服务器，你的敏感数据就裸奔了。

因此浏览器立下**同源策略（Same-Origin Policy, SOP）**：**默认禁止不同源的页面脚本读取另一个源的接口响应，并限制带副作用的跨域复杂请求。**

### 3. CORS（跨域资源共享）如何安全放行？

前后端分离时，前端跑在 `http://localhost:5173`，后端跑在 `http://localhost:8000`（端口不同，必然跨域）。怎么让浏览器放行合法的前端？靠 **CORS（Cross-Origin Resource Sharing）** 协议：**浏览器问后端，后端在 HTTP 响应头里盖章放行。**

浏览器把跨域请求分成两类处理：

- **简单请求**（例如普通 `GET`，且没有 `Authorization` 这类自定义头、也没有 `Content-Type: application/json`）：
  浏览器直接发出请求，并在请求头自动附带 `Origin: http://localhost:5173`。响应回来后，浏览器检查响应头里有没有 `Access-Control-Allow-Origin: http://localhost:5173`（或 `*`）。如果没有，浏览器就**把响应数据扣留不给 JS**，并在控制台报 CORS 红错（注意：此时后端其实已经收到并执行过一次请求了）。
- **预检请求（Preflight `OPTIONS`）**：
  现代前后端开发 **99% 的业务接口都会触发预检**——只要请求头里出现 `Content-Type: application/json`、`Authorization: Bearer ...`，或者方法用了 `PUT` / `DELETE` / `PATCH`，浏览器在发真正业务请求前，会自动分成两步走：
  1. **先发 `OPTIONS` 探测请求（JS 代码里看不到，但在浏览器 Network 面板能看到）**：浏览器带着 `Origin: http://localhost:5173`、`Access-Control-Request-Method: POST`、`Access-Control-Request-Headers: authorization, content-type` 去问服务器“准不准发”；
  2. **服务器盖章后再发真请求**：只有当服务器对 `OPTIONS` 返回 `200`/`204` 且响应头包含匹配的 `Access-Control-Allow-Origin`、`Access-Control-Allow-Methods`、`Access-Control-Allow-Headers` 时，浏览器才会紧接着发出真正的 `POST /api/chat`；否则直接拦截报错，连真正的业务请求都不会发出去。

> **两个最常踩的 CORS 配置坑**：
> 1. **带 Cookie 跨域不能写 `*`**：如果前端需要携带 Cookie 发起跨域请求（`fetch(..., { credentials: 'include' })`），后端返回的 `Access-Control-Allow-Origin` **禁止使用通配符 `*`**，必须精确写明前端源（如 `https://app.example.com`），并额外加上 `Access-Control-Allow-Credentials: true`。
> 2. **不要在 Nginx 和后端同时配 CORS**：如果 Nginx 加了一次 `Access-Control-Allow-Origin`，FastAPI 里又加了一次，响应头会出现两个同名字段，浏览器会直接判定非法拦截。**只在一处配。**

### 4. 开发期与生产期解决 CORS 的三种标准姿势

| 阶段 / 场景 | 推荐方案 | 原理与优缺点 |
| :--- | :--- | :--- |
| **本地开发期** | **Vite 开发代理（`server.proxy`）** | 浏览器只请求 `localhost:5173/api/...`（完全同源），由 Vite 后台转发给 `localhost:8000`。前端代码和线上完全一致，无需改后端 CORS |
| **生产环境（最推荐）** | **Nginx / Caddy 同域反代** | `www.example.com` 托管前端，`www.example.com/api/` 反代后端。浏览器看来完全同源，**彻底消灭 CORS 和额外的 `OPTIONS` 预检往返** |
| **生产环境（必须分域名，如 `app.` 调 `api.`）** | **后端框架配 CORS 中间件** | 如 FastAPI 配 `CORSMiddleware`，显式白名单放行 `allow_origins=["https://app.example.com"]`、所需方法与自定义头（同时可加 `Access-Control-Max-Age` 缓存预检结果，减少重复 `OPTIONS`） |

## 四、浏览器客户端存储全景

浏览器为每个站点（按同源隔离）提供了四种主要的本地持久化/缓存机制，各自的设计目标完全不同：

| 存储方式 | 容量上限 | 生命周期 | 会随 HTTP 自动发给服务器吗？ | 数据类型与读写特性 | 典型用途 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Cookie** | 约 **4 KB** | 可设过期时间（不设则关浏览器失效） | **会！每次同源请求自动塞进 `Cookie` 请求头** | 纯字符串；支持 `HttpOnly` 禁止 JS 访问 | **登录态会话凭证**（Session ID / 安全 Token） |
| **`localStorage`** | 约 **5 MB** | 永久保留，除非代码或用户主动清理 | **不会**（纯前端读写） | 仅 **DOMString（UTF-16 字符串）**；同步阻塞 API | 主题色（暗色/亮色）、语言偏好、轻量草稿 |
| **`sessionStorage`** | 约 **5 MB** | **仅限当前标签页**，关闭标签页即销毁 | **不会** | 同 `localStorage`（UTF-16 字符串、同步 API） | 单次流程临时状态（如多步骤向导表单） |
| **`IndexedDB`** | 几十 MB ~ 数 GB（视磁盘空间） | 永久保留 | **不会** | 结构化对象、**二进制 Blob**、支持索引与事务；**异步非阻塞** | 离线文档、本地聊天历史、大文件 / 3D 模型缓存 |

关于 **`localStorage`** 的几条底层补充细节：
- 它遵循 W3C Web Storage 规范，键和值都必须是 DOMString（UTF-16 字符串），存 JSON 对象必须手动 `JSON.stringify` / `JSON.parse`；
- 严格遵循同源共享：**协议 + 域名 + 端口**完全相同的页面共享同一份 `localStorage`；
- 不同浏览器内核的落盘引擎并不统一，底层可能是 **SQLite**，也可能是 **LevelDB**（Chromium 家族）。

> **安全边界提醒（不要把什么都往 `localStorage` 里塞）**：
> `localStorage` 对当前页面里的**任何 JS 代码都是完全透明可读的**。一旦站点遭遇 XSS 攻击（或引入了被投毒的第三方脚本），攻击者一行 `localStorage.getItem('token')` 就能把凭证偷走；而带有 **`HttpOnly`** 标记的 Cookie 对 JS 完全不可见，只能由浏览器在发请求时自动携带。因此在安全性要求高的项目里，登录凭证优先考虑 `HttpOnly` Cookie 而非裸存 `localStorage`（具体权衡见第 5 篇）。
