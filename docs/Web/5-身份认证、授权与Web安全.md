# 身份认证、授权与 Web 安全

这一篇解决 Web 架构里最容不得糊弄的安全主线：**如何在无状态的 HTTP 之上可靠地建立用户会话？认证（AuthN）和授权（AuthZ / RBAC）到底怎么区分和落地？第三方登录（OAuth 2.0 / OIDC）与 Passkey 是怎么跑的？指挥 AI 写接口时必须盯死哪些安全漏洞？**

---

## 一、底层前提：HTTP 无状态与系统的状态哲学

HTTP 协议本身是**无状态（Stateless）**的：服务器默认无法区分两个连续的请求是不是来自同一个人，也记不住你上一秒干了什么——就像一个健忘的服务员，每次开口都得重新自我介绍。

需要注意，“无状态”并不是说每次请求都像纯函数那样无副作用（发 POST 依然会改数据库），而是指**应用服务器进程本身不依赖之前请求保存在内存里的上下文**。

### 为什么分布式架构推崇无状态？

从信息论与系统确定性的角度看，状态会急剧扩大系统的不确定性空间（复制、扩容、排障都需要更多隐性信息）：

- 有状态服务：$\text{输出} = f(\text{代码}, \text{配置}, \text{输入}, \text{内部状态})$
- 无状态服务：$\text{输出} = f(\text{代码}, \text{配置}, \text{输入})$

状态越多，系统熵越大。传统长寿命服务器常出现“A 机器能跑，B 机器不能跑”，本质就是依赖了进程里暗流涌动的隐性内部状态（就像类里写了一大堆隐式读成员变量的方法）：
- **有状态实例像一只养了三年的宠物猫**：有历史、有习惯、有病历、有独特状态，死了很难直接换一只；
- **无状态实例像一张刚打印出来的试卷**：坏了直接重打一张，流量大了直接加十台副本。

**无状态并不是“没有状态”，而是“把状态从计算节点里剥离出来，集中放到少数明确、可观测、可备份、可复制的状态系统（如数据库、Redis）里统一管理”。** 底层机器必然有状态，上层架构追求的是让状态被可控地隔离在边界之内。

## 二、在无状态 HTTP 上建立登录态：Session + Cookie vs JWT

因为 HTTP 健忘，要让服务器认出已登录用户，核心思路只有一个：**登录成功后给客户端发一张“凭证”，之后每次请求都把凭证带回来。** 工程上两大主流方案是 **Session + Cookie** 和 **JWT**。

### 1. Session + Cookie（服务端存状态）

1. 用户提交账号密码登录；
2. 服务端验证通过后，创建一个 Session 对象存进集中式缓存（通常是 **Redis**，避免多台后端机器之间不同步），把随机生成的 `SessionID`（类似短时效的 API Key）通过响应头 `Set-Cookie` 发给浏览器；
3. 浏览器把 `SessionID` 存进 Cookie；之后每次向同源服务器发请求时，**浏览器会自动把 Cookie 塞进请求头**，服务端拿着 `SessionID` 去 Redis 查出对应用户。

### 2. JWT（客户端自包含凭证）

**JWT（JSON Web Token）**把身份声明直接写进 Token 自身并盖上数字签名，服务端验签通过就能直接信任，**不需要每次请求都去查 Redis**，天然贴合无状态设计。

一条 JWT 长这样：`xxxxx.yyyyy.zzzzz`，由三段 Base64URL 编码的字符串用点拼接而成：

1. **Header（头部）**：声明签名算法（如 `HS256`、`RS256`）和类型 `JWT`：
   ```json
   { "alg": "HS256", "typ": "JWT" }
   ```
2. **Payload（负载）**：存放用户身份与有效期等公开声明：
   ```json
   {
     "sub": "1234567890",
     "name": "John Doe",
     "role": "admin",
     "iat": 1730000000,
     "exp": 1730003600
   }
   ```
3. **Signature（签名）**：服务端用密钥对 `Header + Payload` 算出的防伪签名。

> **两个必须死记的 JWT 陷阱**：
> 1. **Payload 是明文编码，不是加密！** 任何人拿到 JWT 都能直接 Base64 解码看到里面的内容，绝对不能往里塞密码、手机号等敏感信息；签名只防篡改，不保密。
> 2. **纯无状态 JWT 无法主动吊销**：一旦签发了一个 7 天有效的 JWT，如果用户第 2 分钟被封号、离职或修改密码，在 7 天到期前这张旧 Token 依然能通过验签（如果为了踢人再给它加一张 Redis 黑名单，就又退化成查库了）。

### 3. 破除旧二分法：现代工程到底怎么放凭证？

老教程常说：“Session 放 Cookie 会遭 CSRF，JWT 放 `localStorage` 用 `Authorization: Bearer` 头就能防 CSRF。”这个说法在现代浏览器里已经过时，甚至容易引入更危险的 XSS 泄露：

- **`localStorage` 存 JWT 的硬伤**：页面上任何 JS 都能读 `localStorage`。一旦网站某处存在 XSS 注入（或引入了被投毒的第三方依赖），恶意脚本一行代码就能把 Token 全部偷走。
- **现代 Cookie 的三个安全盾牌**：只要服务端下发 `Set-Cookie` 时配齐这三个属性，Cookie 几乎能同时防住 XSS 窃取和 CSRF 伪造：
  - **`HttpOnly`**：彻底禁止页面 JS（`document.cookie`）读取该 Cookie → **即使发生 XSS 也偷不走凭证**；
  - **`Secure`**：只允许在 HTTPS 加密连接下传输；
  - **`SameSite=Lax`（或 `Strict`）**：用户从外部恶意网站发起跨站 POST 请求时，浏览器**不会自动附带该 Cookie** → **从浏览器底层挡掉绝大多数 CSRF**。

### 4. 两种最稳的现代落地组合

- **组合 A（单体 / 中小 Web 应用最省心）**：**Redis Session + `HttpOnly / Secure / SameSite=Lax` Cookie**。随时可以一键踢人下线、逻辑简单、安全性最高。
- **组合 B（微服务 / 多端 App + Web 通用）**：**双 Token 机制（短命 Access Token + 长命 Refresh Token）**
  - **Access Token（JWT）**：有效期极短（如 15 分钟），用于日常调接口，后端纯验签不查库；
  - **Refresh Token**：有效期长（如 7~30 天），**存入数据库/Redis，Web 端放进 `HttpOnly` Cookie**。Access Token 过期后，前端静默拿 Refresh Token 换新；一旦要封号或登出，直接删掉数据库里的 Refresh Token 即可，最长容忍窗口只有 15 分钟。

## 三、认证（AuthN）vs 授权（AuthZ）与 RBAC 权限模型

很多系统把“登录”和“权限”混成一团，连状态码 `401` 和 `403` 都乱回。先把两个核心缩写切干净：

- **认证（Authentication，简称 `AuthN`）**：回答 **“你是谁？”**
  - 核实身份的过程（密码、Session、JWT、Passkey、OAuth 登录）。
  - 没通过时，接口返回 **`401 Unauthorized`**（未登录或凭证过期）。
- **授权（Authorization，简称 `AuthZ`）**：回答 **“你被允许做什么？”**
  - 在已经确认你是张三之后，判断张三能不能删除某篇文章、能不能进入管理后台。
  - 没通过时，接口返回 **`403 Forbidden`**（认出你是谁了，但权限不够）。

### 授权模型的三个演进层级

#### 1. 初级：角色硬编码（只适合极小项目）

直接在接口里写 `if user.role != "admin": raise 403`。项目一长大，到处散落 `if role in ("admin", "editor", "ops")`，每多一个新岗位就得全仓库翻代码重新发版。

#### 2. 标准：RBAC（基于角色的访问控制）

绝大多数后台、SaaS 和企业系统的标准答案是 **RBAC（Role-Based Access Control）**。核心思想是**把“人”和“具体权限点”解耦，中间插一层“角色”**：

- **用户（User）** ↔ **角色（Role）**：如 `管理员`、`内容编辑`、`只读访客`（多对多）；
- **角色（Role）** ↔ **权限点（Permission）**：用 `资源:动作` 命名，如 `doc:read`、`doc:write`、`doc:delete`、`user:ban`（多对多）。

落地后的最大好处是：**业务代码里不再出现任何角色名，只检查权限点**（如 `@require_permission("doc:delete")`）。以后业务需要新加一个“外部审核员”角色，只需要在数据库/后台把几个权限点勾到一起即可，后端一行代码不用改。

#### 3. 容易漏掉的致命补丁：对象级归属校验（防越权 / IDOR）

**RBAC 只管“功能权限”，管不了“数据归属”！**

假设所有普通用户都拥有 `order:read`（查看订单）和 `doc:delete`（删除文档）权限。如果 AI 写的删除接口 `DELETE /api/docs/{doc_id}` 只校验了“当前用户登录了且有 `doc:delete` 权限”，却忘了检查 **`doc.owner_id == current_user.id`**——那么张三只要把请求里的 `doc_id` 从 `100` 改成 `101`，就能直接删掉李四的文档！

这类漏洞叫 **IDOR（不安全的直接对象引用 / 水平越权）**。**凡是按 ID 操作个人/租户数据的 SQL 或接口，查询条件里必须强制拼上 `owner_id == current_user.id`（或 `tenant_id` 隔离）。**

#### 4. 进阶模型（按需了解）

- **ABAC（基于属性的访问控制）**：把环境、时间、数据密级等动态属性纳入规则（如“仅工作日 + 公司内网 IP + 文档密级 ≤ 员工职级”才放行）。
- **ReBAC（基于关系的访问控制）**：像 Google Docs / GitHub 那种层层共享协作模型（“因为你属于 A 团队，而 A 团队对仓库 X 有写入关系”），常借助 OpenFGA / SpiceDB 等专用引擎实现。

## 四、OAuth 2.0 与 OIDC：第三方登录到底怎么跑的？

几乎所有现代网站都有“使用 GitHub / Google / 微信登录”。这背后靠的是 **OAuth 2.0** 和 **OIDC** 两个紧密配合的协议：

- **OAuth 2.0（本质是授权委派）**：解决的是“在不把我的 GitHub 密码告诉第三方网站的前提下，允许第三方网站限时访问我的部分资源（如只读邮箱和公开仓库）”。
- **OIDC（OpenID Connect = OAuth 2.0 + 身份层）**：OAuth 2.0 原本只给访问资源的 `access_token`，并不规范怎么表示用户身份；OIDC 在它上面加了一张标准格式的用户身份证——**`ID Token`（一个 JWT）**，里面直接带用户的唯一 ID、邮箱和头像，专门用于规范化登录和企业单点登录（SSO）。

### 标准登录流程（Authorization Code + PKCE）四步走

假设用户在你的网站点击了“用 GitHub 登录”：

1. **跳去身份提供方授权**：你的网站把浏览器重定向到 GitHub 的授权页，URL 里带着你的应用标识 `client_id`、授权完跳回来的地址 `redirect_uri`、申请的权限范围 `scope`，以及一个防拦截的随机挑战哈希（PKCE `code_challenge`）。
2. **用户同意，带回一次性授权码**：用户在 GitHub 点“同意”后，GitHub 把浏览器重定向回你的回调地址：`https://yourapp.com/auth/callback?code=一次性短命码`。
3. **后端用 `code` 换取真正的 Token**：你的后端拿到 `code` 后，通过**服务端到服务端的 HTTPS 请求**（带上 `code` + 你保密的 `client_secret` / PKCE 原码）向 GitHub 换回 `access_token`（以及 OIDC 的 `id_token`）。
4. **签发你自己系统的登录态**：你的后端用拿到的数据查出用户的唯一 ID 和邮箱，在**你自己的数据库**里查找或新建本地用户，最后按第二节的方式签发**你自己系统的 Session 或 JWT**。到此第三方登录结束，后续业务请求全走你自己系统的鉴权。

> **为什么要绕一圈先拿 `code` 再换 Token？**
> 浏览器重定向 URL 会暴露在地址栏、浏览器历史、代理和 Nginx 访问日志里，如果把 `access_token` 直接塞在跳转 URL 里极易被截获。而 `code` 有效期极短、用一次就作废，且必须配合后端私藏的 `client_secret`（或 PKCE 验证码）才能换出 Token，把风险锁死在了后端通道里。

## 五、现代登录凭证演进：密码 → MFA（TOTP）→ Passkey

用户证明“我是我”的凭证本身也在经历三代演进：

| 时代 | 认证方式 | 安全短板与提升 |
| :--- | :--- | :--- |
| **第一代** | 纯账号 + 密码 | 容易撞库复用、数据库脱库泄露、被钓鱼网站骗走 |
| **第二代** | 密码 + **MFA**（短信 / 验证器 App 动态码） | 多因素认证，光偷走密码登不上去；但仍可能被“实时钓鱼代理”同时骗走密码和动态码 |
| **第三代** | **Passkey / 硬件安全密钥（WebAuthn）** | 基于非对称密钥且**强绑定域名**，天然抗钓鱼、彻底消灭密码 |

在 Apple 密码工具里，“验证码”对应第二代验证器 App，“通行密钥”对应第三代 Passkey。

### 1. 验证器 App 的核心机制：TOTP

验证器 App（Google Authenticator、Apple 密码、1Password）背后的算法叫 **TOTP（Time-based One-Time Password，基于时间的一次性密码）**，离线也能算出验证码，核心逻辑极其简洁：

1. 绑定时（例如 OpenAI 给你一个二维码），二维码里藏着一串**共享秘密种子（Secret Seed）**以及账号、服务名和步长（通常每 30 秒刷新一次 6 位码）。
2. 服务器将你的账号和这串秘密种子绑定存库（好比把“绑定手机号”换成了“绑定种子”）；你的验证器 App 在手机本地也保存同一串种子。
3. 以后每次登录，手机本地用 **`当前时间戳 + 秘密种子`** 算出一个 6 位验证码，服务器也用同一套输入算出当前应得的验证码；两边一致即通过。
4. **为什么不在应用内部自己发短信，而要独立一个验证器 App？** 核心原则是**把安全凭证与被登录应用及运营商短信通道解耦**，信任锚点落在“只有绑定时存过种子的物理设备才能算出这个码”。

### 2. Passkey（WebAuthn）：第三代无密码登录

Passkey 的底层是 W3C 标准的 **Web Authentication API（WebAuthn）**，直接把非对称加密搬到了用户登录上：

- **注册创建 Passkey 时**：你的设备本地生成一对公私钥——**私钥永远留在本地安全芯片（或端到端加密的钥匙串）里，绝不发给网站**；只把**公钥**上传给网站服务器存起来。
- **登录时**：网站服务器发来一段随机挑战数（Challenge），你通过 Face ID / Touch ID 在本地解锁私钥对挑战数签名，发回服务器；服务器用当初存好的公钥验签通过即可登录。
- **为什么连虚拟货币应用也力推 Passkey？**
  1. **服务器脱库也不怕**：服务端只存公钥，黑客偷走整个数据库也伪造不出你的签名；
  2. **域名硬绑定，天生免疫钓鱼**：浏览器在底层严格校验证书域名，哪怕黑客做了一个长得一模一样的假域名 `g00gle.com`，浏览器根本不会把 `google.com` 的 Passkey 私钥拿出来签名。

> **关于后量子时代的延伸**：量子计算（Shor 算法）对当前主流的 RSA / ECC 非对称密码体制存在理论威胁。长期演进方向是向 **NIST 标准化的抗量子密码（PQC，如 ML-KEM / ML-DSA）** 迁移，同时在对称加密和哈希侧维持足够密钥长度（如 AES-256、SHA-256/512，受 Grover 算法影响可通过翻倍密钥长度抵消）。

## 六、Web 高频安全攻击与开发防线速查

把日常开发和 Review AI 代码时最容易踩的 5 类安全雷集中收口：

| 攻击类型 | 攻击本质 | 必须守住的代码防线 |
| :--- | :--- | :--- |
| **XSS（跨站脚本攻击）** | 攻击者把恶意 `<script>` 注入到你的网页里，在受害者浏览器中执行（偷 `localStorage`、伪造用户操作） | React/Vue 默认会转义文本，**严禁把用户输入或不可信 Markdown 原样塞进 `dangerouslySetInnerHTML` / `v-html`**（必须先经 DOMPurify 清洗）；登录凭证放 `HttpOnly` Cookie；配 `Content-Security-Policy`（CSP）响应头 |
| **CSRF（跨站请求伪造）** | 受害者已登录 A 站，误点恶意 B 站代码，B 站借受害者浏览器向 A 站发请求，浏览器默认附带 A 站 Cookie 导致误操作 | Cookie 必加 **`SameSite=Lax`（或 `Strict`）**；状态修改类操作只用 POST/PUT/DELETE（绝不用 GET）；高敏操作配合 CSRF Token 或改用自定义 Header 携带凭证 |
| **IDOR（水平越权）** | 改请求里的资源 ID（如 `/orders/101` → `/orders/102`）读写他人数据 | 后端**每一条涉及个人/租户数据的接口**，数据库查询和更新条件必须强制校验 `owner_id == current_user.id`（绝不能只信前端传来的 `user_id`） |
| **SQL 注入** | 把用户输入直接字符串拼接到 SQL 里，篡改查询逻辑 | **永远使用参数化查询（Prepared Statements）或 ORM（SQLAlchemy / Prisma）**，严禁 f-string 拼 SQL |
| **SSRF（服务端请求伪造）** | 接口接收用户传入的 URL 并由后端去抓取（做 **AI 联网搜索 / 网页总结 / Webhook** 时极高发），攻击者传入 `http://127.0.0.1:6379` 或云元数据地址 `http://169.254.169.254/` 探测内网 | 后端发起抓取前先解析目标域名对应的 IP，**严格拒绝私网（RFC 1918）、回环（`127.0.0.0/8`）、链路本地（`169.254.0.0/16`）和 CGNAT 网段**，并关闭无限制重定向跟随 |
