# 软件架构、控制反转与测试驱动开发

把关于“库与框架的区别”、“依赖倒置与六边形/整洁架构”、“TDD 测试驱动开发”以及“Qt Model-View-Delegate 架构踩坑”合并到同一篇里。这些概念看似分散，其实都在回答同一个软件工程核心问题：如何切分模块之间的控制流与依赖关系，不让业务逻辑、UI 界面和底层数据库死死缠在一起。

---

## 一、框架（Framework）与控制反转（IoC）

### 1. 用“库（Library）”还是用“框架（Framework）”？

两者的核心区别在于控制流（Control Flow）掌握在谁手里：
- 使用各种库（Library）：你自己是程序的主人，由你的主函数决定什么时候去调用别人的函数（传统 C 语言工程基本上都是自己决定控制流）。
- 使用框架（Framework）：会发生控制反转（Inversion of Control, IoC）。框架定义了整个应用程序的运行主循环和生命周期，你写的函数反而退化成了“回调函数（Callback）”——你把函数注册给框架，等合适的时机到了，由框架反过来调用你的代码。

最典型的例子就是 GUI 框架（如 Qt）和现代前端 JS 框架：
- 在 Qt 里，主函数一旦调用 `app.exec()` 就把控制权彻底交给了 Qt 的事件循环；你通过继承重写虚函数，或者把自己的函数绑定到信号槽（Signals & Slots）上。当你点击界面上的按钮时，是 Qt 框架在底层捕获了鼠标事件，再通过信号槽机制回调到你写的槽函数里。
- 框架往往还自带一套构建脚手架或元对象工具链（比如 Qt 的 `qmake` / `moc`）。

### 2. 依赖注入（Dependency Injection, DI）

控制反转在模块组装层面的具体体现就是依赖注入：
- 传统写法：类 A 内部需要用到类 B 的能力，于是 A 在自己的构造函数里直接 `new B()`。结果就是 A 和 B 的具体实现死死绑在一起，想单独测试 A 或者把 B 换成另一种实现都极难。
- 依赖注入写法：A 只声明“我需要一个具备某种接口能力的对象”，至于这个对象是谁构造的、怎么传给 A，由外部的组装层或 DI 框架负责创建好 B 并塞（注入）给 A。
- 本质：模块内部的耦合解开了，但组装的复杂度从类 A 内部转移到了外部框架或启动入口上。

## 二、测试驱动开发（TDD）与两大学派

### 1. 从传统开发到 TDD

传统开发模式是单向线性的：

```text
分析需求 --> 设计 --> 编码 --> 最后写测试（甚至不写）
```

这种模式下，测试的唯一目标是“事后找 Bug”。一旦写测试时发现代码结构根本没法测（比如所有逻辑都绑死了全局变量和真实数据库连接），此时开发早已完成，木已成舟，重构代价极大。

2002 年提出的 TDD（Test-Driven Development，极限编程 XP 的 12 个核心实践之一）把顺序倒了过来，让测试不再只是事后的验证工具，而是成为事前的“设计反馈工具”：

```text
先写一个会失败的测试 (Red) --> 写最简代码让测试通过 (Green) --> 在测试保护下重构代码 (Refactor)
```

一个非常敏锐的工程直觉是：测试问题最终都会演化成架构问题。如果你发现仅仅想测试一条很简单的“订单折扣计算规则”，却不得不先启动 MySQL 数据库、建表、启动网络服务、初始化一整套框架容器、跑完还要清理脏数据——这直接证明系统的依赖关系写乱了。

### 2. TDD 的两个方向：Chicago 学派 vs London 学派

到底该怎么写测试？社区分化出了两种截然不同的测试风格（注意：这两种风格描述的是如何看待对象协作与 Mock，与单元测试/集成测试/端到端测试的粒度划分是正交的）：

| 维度 | Chicago School (Classicist 经典状态派) | London School (Mockist 协作行为派) |
| :--- | :--- | :--- |
| 演进方向 | 由内向外（从小模块开始，逐步拼装扩展到整个系统） | 由外向内（从用户最外层入口开始写，逐层向内发现需要的协作者角色） |
| 断言核心 | 测状态（State）：运行完之后，函数的返回值、对象的最终状态对不对？ | 测行为（Behavior）：运行过程中，这个对象有没有按预期的顺序和参数去调用它依赖的邻居？ |
| 对待 Mock 的态度 | 尽量用真实对象协同测试，只有遇到真正笨重的外部依赖（如真实数据库、外部网卡接口）才做替身 Mock | 严格隔离：测单个对象时，把它周围依赖的所有其他对象一律 Mock 掉 |
| 思考出发点 | “运行后的业务计算结果对不对？” | “这个对象有没有正确履行它自己的协调职责？”（例如写结账服务时，先发现需要一个“收款者”接口角色并 Mock 它，后面再去实现真实的支付网关） |
| 最适合的场景 | 算法实现、值对象、核心领域模型、数据格式转换、纯业务规则计算 | 工作流编排、应用层服务（Application Service）、Controller、多外部系统集成、事件与消息驱动系统 |

### 3. TDD 的滥用陷阱与真实工程经验

用了 TDD 绝不等于就自动拥有了敏捷或好代码。尤其是当团队教条式地过度使用 London 风格（万物皆 Mock）时，测试会迅速退化成沉重的负担：
- 为每一个毫无逻辑的 `getter / setter` 写测试；
- 内部稍微重构一下函数拆分，业务结果根本没变，却导致几十个校验调用顺序的 Mock 测试全线飘红崩溃；
- 测试代码写得比生产代码还要复杂晦涩；
- 为了能塞进测试，生造出一大堆全工程只有一个实现类的无意义接口；
- 把“测试先行”当成机械的宗教仪式，甚至对生命周期只有两天的临时探索原型也要求配套完整的测试体系。

最核心的一条实战教训：
- 现象：项目还在早期探索阶段，需求一天一变，结果每天一多半的时间不是在改业务，而是在痛苦地跟着改永远跑不通的 test 代码。
- 根因：其实不是“测试写早了”，而是“把尚未稳定的内部实现细节，过早当成了稳定的对外契约来写测试”。在架构和需求边界还没收敛之前，测试应该只卡住最外层确定不变的核心输入输出，绝不能把随时会推倒重来的中间过程锁死在测试里。

## 三、解耦架构演进：六边形架构、洋葱架构与整洁架构

前面提到：要想让核心业务逻辑不依赖数据库和 UI 就能独立编译、独立跑通测试，在架构上到底该怎么切？过去二十年里出现的三个著名架构名词，说的其实是同一件事。

### 1. Hexagonal Architecture（六边形架构 / 端口与适配器架构）

六边形架构跟数字“6”其实没有任何关系，画成六边形只是为了打破人们脑子里根深蒂固的“上下分层（UI 压着业务，业务压着数据库）”的刻板印象。它更准确的名字叫 Ports and Adapters（端口与适配器架构）。

- 要解决的痛点：业务逻辑、UI 界面、自动化测试脚本、MySQL 数据库死死缠绕在一起，不连数据库、不起界面就没法跑业务。
- 破局思路：计算机科学里没有什么耦合是增加一层中间接口解决不了的。把“应用核心”放在正中央，在核心与外部世界之间只定义纯粹的接口——称为 Port（端口）：

```text
驱动端 (谁来调业务)：REST 控制器 / CLI 命令行 / 自动化 Test 脚本 --> [输入 Port 接口] --> 应用核心业务逻辑
被驱动端 (业务去调谁)：应用核心业务逻辑 --> [输出 Port 接口] --> MySQL 适配器 / 内存 Fake 假数据库 / PostgreSQL 适配器
```

一旦在业务核心和数据库之间隔了一道“输出 Port 接口”，平时跑单元测试时，只需要挂一个几十行代码写的 `In-memory Fake`（内存字典假数据库适配器），一毫秒就能跑完几百个业务测试，完全不需要启动真实的 MySQL（顺带一提，使用前面说的 London TDD 由外向内写测试时，会非常自然地逼着你把这些 Port 接口设计出来。）

### 2. Onion Architecture（洋葱架构）与 Clean Architecture（整洁架构）

1. 洋葱架构（Onion Architecture）：
   传统三层架构最大的毛病是“上层依赖下层”——UI 依赖业务层，业务层直接依赖数据访问层（ORM / 数据库驱动），导致最核心的业务代码反而间接绑死了最容易变动的基础设施。洋葱架构把领域模型（Domain Model）放在最内层的圆心，把数据库、网络、UI 等基础设施统统赶到最外圈，规定所有依赖箭头必须由外向内指。
2. 整洁架构（Clean Architecture，Robert C. Martin 于 2017 年将上述思想统一整理）：
   把这套同心圆归纳为一条铁律——Dependency Rule（依赖规则）：源代码中的依赖关系必须只指向内层，内层绝不能知道外层的任何名字（内层不能 `import` 外层的类、框架或数据库结构）。
   典型由内向外的四层同心圆：
   - `Entities`（企业级核心业务实体与不随项目改变的底层规则）
   - `Use Cases`（当前应用的具体业务流程编排）
   - `Interface Adapters`（接口适配器：把内层数据转换成外层数据库或 Web 需要的格式，如 Presenter / Gateway 实现）
   - `Frameworks & Drivers`（最外层的易变细节：Web 框架、Qt GUI、MySQL 驱动、第三方 SDK）

## 四、GUI 架构实战：Qt Model-View-Delegate 的设计机制与踩坑记录

桌面 GUI 开发是“框架控制反转”与“分层解耦”最集中的试验场。这里记录在使用 Qt 的 `QAbstractItemView`（Model-View-Delegate 架构）开发包含海量数据的复杂表格时踩过的真实深坑。

### 1. `QAbstractItemView` 的按需渲染机制与轻量级 Model 设计

Qt 的视图控件（如 `QTableView` / `QTreeView`）底层有两个非常关键的运行特征：
1. 双重缓冲区绘制；
2. 懒加载按需访问（只向 Model 请求当前屏幕可见区域的数据）：
   假设你要展示一个有 5 万行数据的庞大表格，把架构拆成 Model-View 分离之后，你会发现 Qt 的 View 并不会一上来就遍历读取全部 5 万行的数据，只有当某几行滚动到屏幕可见区域内时，View 才会高频调用那几个可见单元格的 `Model::data()`（但调用的频率并不固定，鼠标划过、重绘都会触发）。

基于这个特性的高性能设计思路：
- 不要在 Qt 的 `Model` 里把业务层的全部字符串和显示对象深拷贝存一份；
- 把 Qt 的 `Model` 做得极度轻量，每个节点占用内存越少越好：当底层业务数据 Model 传过来时，只遍历提取原始业务对象的指针存放在 Qt Model 里；
- 等到屏幕真正滚动到某一行、触发 `data()` 回调时，再通过指针现场去取或计算那十几行可见单元格需要显示的字符串。因为屏幕上同时可见的也就几十行，既省下了海量内存，现场格式化那几十个字符串的 CPU 计算压力也几乎可以忽略不计。

### 2. `QStyledItemDelegate`（自定义单元格绘制与内嵌编辑器）

当表格单元格里的花活比较多（比如选中时不能让默认的深蓝底色把里面的自定义图标盖住，或者双击单元格要弹出下拉框 `QComboBox` / 数字微调框 `QSpinBox`），就必须用到委托类 `QStyledItemDelegate`。

它是挂载在每个 Item 上的渲染与编辑代理人，核心重写三个钩子函数（典型的框架控制反转）：
1. `paint()`：接管单元格背景与内容的绘制（比如专门处理选中态的蓝底与图片图层关系）；
2. `createEditor()`：当用户双击进入编辑态时，由你 `new` 一个 `QComboBox` 或 `QSpinBox` 控件返回给框架；
3. `setEditorData()` 与 `setModelData()`：前者在打开编辑器时把当前数据填进下拉框，后者在编辑完成时作为回调把新值写回底层的 Model。

### 3. 最大深坑：`QStyleOptionViewItem` 的版本演进与 `rect` 为 0 惨案

如果要兼容维护包含 Qt4 到 Qt5 演进的老工业软件代码，`QStyleOptionViewItem` 绝对是让人最抓狂的巨坑：

1. Qt4 的 `V4` 强转陷阱：
   在 Qt4 时代，样式参数类是按 `QStyleOptionViewItem` --> `V2` --> `V3` --> `QStyleOptionViewItemV4` 逐级继承打补丁的；到了 Qt5，官方直接把 `V4` 的所有成员合并进了基础类里，并废弃了 `V4` 的显式声明。
   如果你在维护需要兼容 Qt4 的 `QStyledItemDelegate`，会看到它的虚函数形参给的都是基类 `const QStyleOptionViewItem &option`。注意：在 Qt4 里，哪怕你根本不用 `V4` 扩展出来的那几个新字段，你也绝对不能直接拿形参里的 `option` 去调绘制，那样根本画不出来！必须在函数第一行先拷贝构造转换成 V4：

   ```cpp
   QStyleOptionViewItemV4 optv4 = option;
   initStyleOption(&optv4, index);
   ```

2. 千万不要在 Delegate 外部自己凭空伪造 `QStyleOptionViewItem`：
   所有由 Qt 框架在调用 `QStyledItemDelegate::paint(...)` 时通过形参传进来的那个 `option`，框架在底层已经帮它把当前单元格在屏幕上的几何坐标与大小（特别是 `option.rect` 矩形区域）完整算好并初始化完毕了，只有 `rect` 不是 0，绘制和定位才能正常工作。
   当时踩过的一个大坑是：试图在外部其他地方自己 `new` 一个空的 `QStyleOptionViewItem`，再把 `Delegate` 取出来试图调 `initStyleOption`（这甚至是受保护方法）或者通过 `ItemView` 去手动初始化它——实测无论怎么折腾，自己在外面造出来的 `option`，它的 `rect` 成员变量永远是空的（宽高全为 0），根本无法使用！一切绘制和尺寸计算，必须老老实实留在 Delegate 自己的生命周期回调内部，使用框架传进来的那个原生 `option`。

### 4. `QProxyStyle`（全局控件外观与拖拽指示线微调）

如果不只是改某一个单元格的内容，而是想修改整个控件的通用原生外观（比如边距、焦点框颜色、或者树形列表拖拽排序时的那条提示横线），写子类继承 `QProxyStyle` 是最干净的方案。例如当时为了把树控件拖拽插入时的默认细线改得更粗更醒目，就是通过重写 `QProxyStyle::drawPrimitive` 拦截 `PE_IndicatorItemViewItemDrop` 搞定的。
