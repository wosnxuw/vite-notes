收集并记录 AI 写代码容易犯的问题

### 简单代码复杂化

a or b or c 写成 sum (a, b, c) > 1

任何简单功能复杂化，一个 a + b，要抽离成两行的函数，即便后续再也不会出现任何“➕”的需求

（不过从这一点来讲，AI 不会写一个超过 100 行，甚至 200 行的超大函数）

反复微调格式，自己刚写了一个函数的某一行过长，过一会就又要手工调整为三行，而不是等着调用格式化工具

### 临时任务代码化

只是希望迁移一个配置文件的位置（我的预期可能是执行类似 mv 到命令），但是 AI 误以为是仓库需要具备迁移能力，把迁移这个事情直接写到代码里，然后进行迁移，还给迁移代码补了测试代码

### 喜欢写 test 代码

只要仓库里有 test 文件夹，它不去看以往的 test 是否是假的（只有几个零星代码），即这个仓库是否真的使用 test 机制，就给新的代码添加一个新的 test 文件

解决：最小化长期复杂度 + 符合仓库惯性，而不是维护旧系统

### 测试代码无用

测试只能证明，当前方案内部逻辑自洽，不能证明，当前方案可以解决真实问题

无论你是否采取 TDD 开发，测试先写还是后写，Agent 永远能确保 test 全部通过

### 测试代码不合理

比如用 Agent 开发 Harness 产品，Agent 把提示词作为测试，用字符串匹配的方式测试，或者把升级点作为测试，专门测试不允许出现的老提示词

### 测试代码奉为圭臬

测试写早了，或者测试的范围不对，仓库还在开发中，但是固定了太多东西

由于写了很多测试代码，下一次修改的时候，部分测试就变成了强力约束，AI 不敢修改测试，转而添加兼容层

信息论：测试是功能需求的一种有损压缩

### 文档偏离

文档在逐步迭代过程中，变成一个对于仓库功能的说明，它配合仓库，而是不是它指导仓库

变成一个删掉文档，再请一个 AI 做 Code Review 后一样可以产出的无效产物

### 偶然复杂度提升

比如你要求可以传递数组，你没有说长度，AI 觉得需要限制一下才安全，所以一开始给了 10，但是当仓库迭代一周，10 这个字眼出现在仓库各处，变成金科玉律，任何工具、提示词，都需要符合小于 10 这个标准

本质 10 也是类似于测试的一种约束，它出现后，地位逐步抬升

### 是最优秀的设计，但是不符合仓库惯性

比如一个类，它构造函数是空的，所有参数都通过 Set 和 Get 来传递

此时你要求添加一个新的参数，这个参数目前没有需要后续修改的点

AI 会直接把这个参数加到构造函数里，并且坚持认为，这个参数不需要反复 Set，这样是最优秀的

但是我的担心是，一旦开了构造函数可穿入参数的口子，系统后续的演化，可能会参数左一个右一个，原来的设计被逐渐侵蚀

### 过度设计/概念多

过度考虑软件工程的概念/过度谨慎，拖垮项目开发速度

举例：仓库基本功能还没实现，就考虑幂等、TTL、重试、超时、回滚等等

举例：你如果需要一个点，上来就要考虑它的所在位置、边界、区域、连续性等等

综合前面两个例子，你的仓库变成一个检查高手，多个检查之间如果是多次开发甚至可能矛盾，函数永远执行失败，因为你要检查的点过多

而事实上，很多事情并不应该由你来处理，AI 在仓库内严格遵守软件工程的实践，但是把其他功能，比如其他模块的失败，它甚至要写代码来追踪人家为什么失败，人家明明返回值里不公开内部实现

### 设计不符合主流实现

它需要参考现有开源实践，或者已有的库

比如你的目标是有一个审批功能，它把审批做成一个工具，而不是靠类似于钩子的机制去触发

或者你已经有两个仓库，A 去使用 B，你再写一个仓库 C 去使用 B，它不参考 A 如何用，又造了一套全新而复杂的方案（虽然可能仍符合软件工程学），但是实际的可维护性极差，根因是 Agent 有时候不知道 A，或者你也没叫它参考

### 必须说的很详尽

你说参考 A，把 B 旋转 90 度，它专注于旋转 90 度，但是最后顺逆时针搞错

### 启动问题

如果你的项目可以启动，那么 AI 很愿意启动它给你看一下，但是启动的东西生命周期不对，它自己又不回去关掉，需要我手动关掉

启动命令不合理，把所有参数堆砌到命令行里，最正常的启动需要输入好几行参数

关闭方式不合理，比如又是 docker，又是本地进程的混合，它只写启动，不写关闭，你自己关掉很费劲，请它来关掉，它也得关一会
