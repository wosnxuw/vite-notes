# Agent 落地实战与反思

这篇文章记录在实际工程中落地两类典型 Agent 产品（一类是理解自然语言并向底层系统提交参数干预的**操作类 Agent**，另一类是结合日志、源码与配置定位异常的**故障诊断类 Agent**）的过程，重点复盘开发顺序、评测方案的演变，以及反复踩过的工程坑。

---

## 一、两类产品的演进脉络

### 1. 最小底座阶段

操作类 Agent 一开始没有急着接大模型，而是先直接加载底层核心计算库，构造基线请求和干预请求做对照，验证输入到底能不能让底层算出预期结果；跑通之后才加上最小的自写 `AgentLoop`。

确立了开发顺序：先确认业务的输入、输出，跑通一条最小确定性链路，然后再用大模型替代这条链路。

### 2. 交互改造与模块解耦

根据 1 的最小启动，你会迅速把模型插入进入，但是早期体验是“运行完去翻日志”，体验差。然后改造为 CLI/REPL 多轮交互，直接看关键步骤。随后把原本耦合在一起的代码拆成了三个独立部分：只管生产 HTTP 服务的 Server、负责本地编排与仿真的 Lab，以及直接读运行态做展示的 Viewer。

工具的粒度会反复摇摆：范围窄了做不了事，范围大了返回全是噪声；甚至出现过先把“撤销”功能设计出来了，回头才发现底层协议根本不支持的情况（依旧没看清输入输出）。

### 3. 做减法与收缩边界

随着联调深入，发现包装和兼容层越多，AI 很喜欢在检查上发力，原始事实被遮住。eg：预览环节里加的额外几何限制（gpt-5.6-sol），反而把本来可行的请求判成了不可行；生产环境里从来没人去点的审批流程，也一直留在代码和界面里当包袱。

### 4. 重建控制流与盯死返回值

接手旧版诊断助手时，最初的架构是外层用代码写死循环和固定轮数（workflow），查不出再去调外部工具（转 agent）。为了把调查顺序和何时停止的控制权真正交还给模型，决定用 Pi 的公开 SDK（严格要求不维护上游 fork，只用 SDK，减少“维护成本”）重新搭建底座。

重建后很快又撞上了问题：工程上 SDK、预算控制、归档和契约都已经很完整了（设想的很宏大），结果一看某个核心查询工具的实际输出——整整一千三百行 JSON，同一个环境名字重复了 48 次，却唯独缺少核心的活动事实。我彻底悟了：工具调通了、测试全绿，但是实际返回值恶心且没意义；验收工具时，人和模型必须看近似同一份真实输出。

### 5. 从强隔离走向开放共享环境

一开始初为了安全，给诊断 Agent 的 Bash 加上了容器内 `bwrap` 隔离，严禁联网，不安装 git。结果实际使用时工具调用频频失败：常用工具找不到、自定义工具不好使，禁止联网导致模型连最新源码都拿不到，模型很快就意识到啥也做不到，就停下了。

诊断的本质是信息发现，取不到材料时模型再聪明也没法推理。吸取教训后，果断大幅化简约束：开放共享只读源码与工作目录，配齐网络和常用命令行工具，让模型自己用 Git 查差异，同时接入领域排障 Skill、MCP 与 CodeMode，把沙盒退回到单纯的本地空间隔离。

## 二、Agent 测评方案的演进与思考

LLM 本身是概率性的，结果呈现方式和解决过程都不唯一。

### 1. 单元测试与 Mock 替身（最容易产生错觉）

早期为了快速推进，用过录制数据回放、假下游服务（Mock）、临时 adapter，甚至出现过“只运行测试脚本的单元测试，却被当成端到端验证”的情况。

这种方案只能验证接口格式没写错。一旦涉及真实请求、协议消费和下游执行，Mock 极易制造“测试套件十二项全过、图上路径看似正常，但真实下游根本没按预期执行”的错觉。

同时，写死的测试断言如果太紧（比如硬性要求结果必变），又会把正常的 Agent 判成失败。

### 2. 黑盒 CLI 试用与冻结现场测试（操作类 Agent 主力方案）

即时操作类 Agent 有个天然矛盾：大模型推理一次要好几秒甚至更久，而外部现场状态一直在变，等你算完现场早就变了，失败了也没法复现。

但是我发现，即时操作类 Agent 的能力没有那么通用，我可以让通用 Agent 去操作它。

（1）我要求求本机另一个 AI 通过 CLI 入口直接黑盒试用产品（严禁看源码）

（2）我设计了“强 Agent 观察小 Agent”的冻结调查：测试时把现场状态冻结（固定位置、任务、地图参数和随机种子），由外部强 Agent 自动完成布置现场、发送自然语言指令、等待回复、读取状态和保存证据的全套动作。

这样做把人从重复劳动里解放了出来，既消除了模型耗时与状态变化的干扰，又能保证每次对比的是同一个场景；而真实连续运行、状态变更和到期清理，则另外单独设动态场景验证。

经验是：最好是把测试的 Agent 严格限制在测试流程内，模范用户真实使用的方式来体验，不要靠搜索代码的方式“假体验”，即多跑 e2e 测试。

### 3. 多维矩阵对照实验（摸清模型脾气与提示词边界）

在日志诊断场景下，为了搞清楚“完整加载提示词 vs 按需加载 Skill”、“给专用工具 vs 纯给 Bash”、“不同模型底座（如 gpt6 vs qwen3.8-flash）”到底谁起作用

我设计过几组控制变量的矩阵实验，让它们去查同一个状态异常问题。

从实验轨迹里能非常直观地看到不同模型的脾气：
gpt6 喜欢先看一眼 skill，然后直接现场写复杂的 python 脚本去捞日志、解析字段，7~10 轮内快速给出一个满足你提示词的最小回答（方向对，但细节常不够全）；而 qwen 更倾向于用小工具多轮组合，40 多轮还在摸索端口和命名空间、不断扩大时间片，虽然慢且容易越界，但如果给对背景提示词，把所有东西都限制好，抓到的细节差异反而比 gpt 更完整。

这类对照实验还暴露了提示词的“停止标准”难题：给详细的背景信息能帮模型少走弯路，但会诱导模型反复验证、试图彻底解决所有问题而停不下来；可一旦在提示词里加上严厉的“不要反复调试抓取脚本”，聪明的模型又会因为过度保守，连核心字段都没拿到就草草结束。

一个奇怪结论：“python: python3”比“请使用现有工具，不要安装新工具，版本按照当前实际提供处理...”好的多，直接就能解决模型第一次尝试 python，而后尝试 python3，原因我暂定为信息密度高。

### 4. 本机满血 Agent 同题对照（诊断类 Agent 找差距最快的方法）

再后来遇到一个复杂的排队预测偏差问题，专用诊断机器人答偏了，而且也没有速度优势，狠狠的打击我的信心。我干脆把同一道题同时丢给本机的 Codex 和 pi 去独立调查。

翻看两边的原始轨迹就能发现：本机 Codex 和 pi 能顺着日志一路追到源码、配置和地图数据，自己现场复算，精准定位到预测位置与实际汇入口的差异。

这种“同题对照”虽然因为两边记忆、提示词和权限不同，不能直接用来证明哪个框架更好，但它是一个极佳的参照系——本机强 Agent 走通了、而专用 Agent 缺失的那一步，直接照出了产品当时最真实的短板（**环境导致信息发现受限**）。

### 5. 信息论假说

一个假说：多步取证链条里，就算单步成功率有 95%，十步独立乘下来也只有六成左右。强大的模型，每一步的成功率更高，那么自然总体下来成功率更高。

环境信息（沙盒、联网、工具）导致信息受阻，会严重的影响单步成功率，比如模型发现无法 git fetch，commit 也对不上，很可能放弃看代码（然后你又需要提示词引导，那还不如放开 fetch）

## 三、反复踩坑的几个工程教训

### 框架完成度替代了业务完成度

无论是在 Python 还是后续重建的技术栈里，都反复出现过“外围机制（SDK、预算、归档、测试套件）越来越工整，但核心工具还没连上真实数据源、返回值依然没法用来查问题”的现象。推进顺序必须反过来：先跑通一个真实问题的最短链路，只有当某类操作反复出现时，再提炼工具或增加机制。

### 跨系统协议缺口（写端成功 ≠ 执行端生效）

跨仓库联调时，遇到过 Agent 和网关侧看起来都已经成功写入，但下游执行端完全没按预期走（字段被忽略，或者任务标识对应错位）。设计涉及外部模块的功能时，必须先确认协议持有者、生产者和消费者的状态反馈，把跨仓改动列为显式依赖，绝不能用本地桩代码掩盖还没对齐的协议。

### 单个失败推动连续打地鼠

诊断答错一个案例，就往提示词或工具里塞一个补丁，结果往往是按下葫芦浮起瓢，甚至提示词开始自相矛盾（我的观点：核心提示词必须由人严格把关，甚至手写，并且跑测试，禁止模型随意的往里添油加醋）

旧案例退化，而且没完没了地把本机能力往专用机器人里搬也没有终点。

后来形成的习惯是遇到失败先做归类：到底是没拿到数据、信息在摘要时丢了、领域语义理解错了、缺停止标准，还是最后交付格式有问题？偶发的数据整理先交给脚本，领域线索先放进 Skill，不要一上来就改核心循环或加专用工具。

### 两类产品的最终验收底线

操作类 Agent 的底线是**不能出现“假成功”和“过期干预残留”**，它的核心价值是降低从自然语言意图到有效系统操作的转换成本；而诊断类 Agent 最忌讳的是**在证据不足时自信地给出错误确定性结论**（这会迫使使用者花双倍时间重新核验一遍），它相对于本机 Coding Agent 的真正优势，在于免环境准备成本、团队可随时在 IM/Web 追问，以及留存可回查的证据链。
