### 量化

Qwen3.5-35B-A3B-Q4_K_S 以这个模型为例

1、参数量 35B

参数量越大，智慧越高，1B 就是 10 亿

2、蒸馏

蒸馏（`Distillation`）注意这个英文，有的模型可能包含这个字眼

通过训练一个较小的模型（称为 **学生模型**）来模仿一个较大的、通常更复杂的模型（称为 **教师模型**）的行为。减小体积，提升速度。

例子：DeepSeek-R1-Distill-Qwen-7B-Q4_K_M

如果不蒸馏，则叫做 UD（Un-Distilled）

例子：Qwen3.5-35B-A3B-UD-IQ3_S

3、激活参数 A3B

对于混合专家模型（MoE）来说，可以设置推理时，启用所有参数的一部分

4、Q 量化

数字越小，模型文件越小，但脑力损失也越大

Q4 是最主流的，将 16 位参数压缩到 4 位

5、K 量化变体

K-Quants（K-量化）是 llama.cpp 作者开发的一种分组量化技术：

允许对不同层使用不同的量化位深，K 后面的字母（S/M/L）表示量化块大小
    - S = small，使用更小的量化块，精度更高但文件更大
    - M = medium
    - L = large，块更大，精度稍低但文件更小

可以认为是 Q4 量化上的具体等级，分为大中小

6、IQ 量化

和 K-Quants 是并列的两种量化方法

IQ 是比 Q 更激进的量化方式，如果 Q 不行，就考虑 IQ，专门优化了某些层，推理速度可能更快

7、FP8

使用 8 位浮点数来表示权重或激活值，正常是 16 位

8、整数量化 Int4

使用 4 位整数来表示模型

一般消费级显卡跑大模型的主流格式

9、W8A8

这是一种混合标注方式，权重（Weight）量化为 8 位，激活值（Activation）也量化为 8 位

模型运行时，中间计算产生的“激活值”也会占用大量显存

W8A8 意味着整条计算链路都变“瘦”了，计算效率极高，且精度非常接近原版（FP16）

Int4 等量化方法同样会量化激活值

10、Instruct

表示不是 Base 模型，而是经过了微调（基本上都有微调吧，才能遵循指令去干活）

**排序：**

 - FP16 / BF16（基准，无量化）
 - FP8 / INT8 / W8A8（轻度量化：体积减半，精度几乎无损）
 - Int4 / W4A16（中度量化：目前性能与体积的最佳平衡点）
 - IQ3 / Q3（重度量化：体积仅剩原版的 $1/5$ 左右，逻辑能力开始有明显下降）
 - Int2 / 1.5-bit（极重度量化：目前多处于实验室阶段，通常会有明显的语病或逻辑混乱）

### 部署

目前有两种格式

`.safetensors` 和 `.gguf`

前者是 `Hugging Face` 社区推出的安全容器，用于取代传统的 Python 打包格式 Pickle

后者是 llama.cpp 引擎专用的格式，但是占用资源更少，更适合本地使用

部署有很多软件可选：

1、Ollama 一个羊驼图标，本身只是一个 CLI，但是有非常多的开源前端 WebUI。现在的 Ollama 不是单纯的“本地跑模型”，而是转向“开源本地运行时 + 云端推理服务”

争议：（1）修改了 llama.cpp，但是未包含许可证和版权声明（2）卖点转移，以前强调本地化、隐私，现在转向商业订阅

2、LM Studio 一个免费但闭源的软件，自带 GUI 窗口。它基于内核 lms 制作，内核是开源的。正常情况下也 llama.cpp，即默认跑 gguf，在 Apple 下也支持 MLX。

争议：（1）开源内核 + 闭源软件（2）和 Ollama 一样也可以使用云端模型

3、直接使用 llama.cpp，但是需要手动编译，以适配你的机型，达到最佳效果

4、oMLX，基于 Apple MLX，仅限 mac 上，并且仅限 MLX 格式（safetensor），追求极限性能的工具（不过也有人认为，在某种并发等条件下不如跑 gguf）

情况：全部开源，但是项目处于快速发展中，bug 可能略多

oMLX 的优点是，不提供冗余服务，比如 LM Studio 集成了内置的对话，又自带 Ollama 的社区版 WebUI，性能监控很强大。

5、vLLM，一个企业级多卡多用户的方案，引擎是自研的 PagedAttention

6、SGLang（Structured Generation Language）也是一个 LLM 推理引擎，并且比 vLLM 更复杂，还包括一些和 LLM 整个生命中各种调用并行的管理之类的。

### MLX

MLX ≈ CUDA

Apple Silicon / Metal <--> MLX

mlx-lm 基于 MLX，但是专注于 LLM，类似 llama.cpp

mlx-vlm 仍基于 MLX，但专注多模态，同时复用 mlx-lm

vllm-mlx 服务端产品，处理并非请求，API，paged KV cache 等等，借鉴 vLLM 的思想和架构

### 速度

我们发现一个现象，就是跑 Qwen3.8-27B 这个模型

在 Apple M4 pro 和 4080S 上的 tps 区别不大，都是 10+ tps

但是明明 4080S 的显存早就爆掉了

（1）这个 10 tps 当时属于 Decode 的速度，只看输出

根据：Decode 阶段，瓶颈在带宽；Prefill 阶段，瓶颈在算力

M4 Pro 带宽 273 GB/s；RTX 4080 带宽 717 GB/s；DDR5 内存带宽粗算 70 GB/s

理论极限，Mac 跑 Q4_K_M 量化，17.74 GB 模型，不管上下文，极限也就 15 tps

而假设 4080 按照 70%，DDR 5 按照 30%，也就类似了

（2）coding 场景

其 Fresh Prefill token 和 Decode token 的比例是 7.7 : 1

账面 Input : Output 为 131 : 1（cache hit rate 94.2%）

Prefill 耗时 和 Decode 耗时相近（Prefill 一个 token 比 Decode 一个 token 快很多）

并且：在上下文反复填充，压缩的过程中。一开始快速增长，后续则速度放缓。一开始是探索/阅读代码，Prefill 主导，中期是编码，再后小修改/运行，以 Decode 为主

所以跑一个 37B 的 dense 模型和一个激活量是 37B 的 MOE 差不多快，无非后者所需的显存更多
