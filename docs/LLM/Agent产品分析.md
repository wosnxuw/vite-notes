### Harness

我经常有一种这样的观点，一个 LLM + 随意一个 Harness，直接开始工作，效果基本差不多

所以我经常性的认为：Harness 没用

实则我错了，我只是在几款“大浪淘沙”后的精品产品里挑选

### 产品分类

一个明确的分界线是**控制权**归谁？

控制权归模型，则称之为 Agent（真正的 Agent）

控制权不归模型，则称之为 Workflow（当然有时候也管它叫做 Agent）

控制权的本质是什么？我的理解是 LLM 是发散的，所以人们在这里加了两层约束

（1）后训练（你无法控制）

（2）底座（后续施加的另一层约束）

在底座上，如果你就是要模型往某个方向发力，那就偏向 workflow；如果要做成通用助手，那就偏向 Agent

### 现代 Harness 提升效果

这是一个困难的话题

你可以随意研究开源的 PI 和 Codex，但是你只能知道“现在的设计是什么”

或者你通过分析异同，甚至你分析 git history，你可以大致分析来时的路

但是，今天你的目标是：让你魔改 PI，让它在“原有设计目标”上提高性能，你就没有思路了

所以，天下文章一大抄也是办法之一，前沿 Harness 怎么设计，你就怎么设计

### 对比试验

LLM 本身是概率的东西

很多时候，你没有办法，通过一些固定的函数来检查结果

（1）结果的呈现方式不唯一，如果是完成某个确定的数值，还算好说，如果是修复 bug、做出回复，很多是无法用函数测试的

（2）过程不唯一，你不能假设模型必须用某种方式解决问题
