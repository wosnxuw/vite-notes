### bash 即一切？

自从看到了 PI + LLM 在各种 benchmark 上跑分 > Codex/Claude Code + LLM，这让我怀疑 Harness 的重要性，即后者是否有些过于“臃肿了”

一个以前看到的观点也在脑子里浮现“模型越是强大，就越不需要约束，最后 Harness 只剩下一个 bash 入口”

再加上 prime-agent 这种，一个 IPython Kernel 的 Harness，让我觉得 bash 是一切

包括 A\ 之前在跑分、很多 benchmark 的时候也只给模型一个 bash

这让我觉得，一个 bash 就够了，提高 Agent 自主性，提高灵活性

### 选择合适的场景

我没有仔细思考我的场景，它不是一个编写代码，自由探索仓库，运行构建命令的 Coding Agent

我需要的是一个，搜寻日志 + 必要时检索相关代码片段的 Agent

一个 bash，确实能做到一切，但是只是把“复杂度”隐藏到模型运行的 bash 脚本、系统提示词里

根据我的对比，一个简易 while 循环 + 写死的工具（内置一些正则表达式和去重逻辑）+ 大量基于规则的流程判断，只需要 4 次即可检索

而把所有流程、规则写系统提示词里，并辅以一个 bash，模型甚至会行动 20+ 次，无论速度，还是 token 的消耗，都远远差于前者

### 为什么？

A\ 早就意识到这一点，甚至我还阅读过那篇博客，不过我被极简循环冲垮了头脑

https://www.anthropic.com/engineering/writing-tools-for-agents

尤其是日志是那种内部日志，字段并不常见，将复杂度留在工具内，可以有效化简 bash 的长度

### 封装 CLI 还是 tools

有一种想法是，既然还是要封装一大堆 tools，不如直接做成一个 CLI，然后让模型继续在 bash 里使用

工具的优势是，每一个参数，工具的作用都定义的比较清晰。而一个你自己写的 CLI，它的工具实际上仍然是 bash，你依旧需要在提示词里写丰富的样例来教会 LLM 如何用，并且一旦无法覆盖，LLM 则开始尝试 -h，让迭代轮次增多

### bash 还留不留

我暂时认为，依旧要留，但是不是唯一。因为搜索代码仓库，bash 的灵活性（管道、git 命令等）不便于被特定工具替代掉
