### bash 即一切？

自从看到了 PI + LLM 在各种 benchmark 上跑分 > Codex/Claude Code + LLM，这让我怀疑 Harness 的重要性，即后者是否有些过于“臃肿了”

一个以前看到的观点也在脑子里浮现“模型越是强大，就越不需要约束，最后 Harness 只剩下一个 bash 入口”

再加上 prime-agent 这种，一个 IPython Kernel 的 Harness

包括 A\ 、很多 benchmark 跑分的时候也只给模型一个 bash

这让我觉得，一个 bash 就够了，提高 Agent 自主性，提高灵活性

### bash 适合跑分

A\ 早就意识到这一点，甚至我还阅读过[那篇博客](https://www.anthropic.com/engineering/writing-tools-for-agents)，不过我被极简循环冲垮了头脑

尤其是日志是那种内部日志，字段并不常见，将复杂度留在工具内，可以有效化简 bash 的长度

### 选择合适的场景

思考你的 Agent 会做什么

一个编写代码，自由探索仓库，运行构建命令的 Coding Agent，适合单 bash

一个搜寻日志 + 必要时检索相关代码片段的 Agent，可能就更适配固定的流程

### 不可能三角

灵活性 <--> 快速 <--> 正确性 <--> 稳定性

灵活性：即通用性，能不能处理更多、覆盖面更广的问题，遇到一个全新问题，是不可用还是会尽力

快速：主要指模型得运行多少轮次，轮次多 = 慢 = 成本偏高

正确性：遇到问题后，能不能综合所有要素，给出尽量全面、正确的回复，而不是停留在某个片面的回答

稳定性：同类型的问题，每次解决的路子相近吗？会不会一次成功一次失败

（大概是这几种问题）

### 总共能设想的方案

A：通用 Agent(bash) + 一大套提示词（说白了就是无设计，纯堆 skill）

B：A 再引入工具/MCP（说白了外挂一个插件）

C：砍掉自主循环，做状态机、工作流 + 辅以各种工具，每一步都由代码来机械式的决定方向

D：多 Agent 系统

E：DSL 系统

F：多模式混合，先走工作流，再用通用兜底

点评：

A：最为“灵活”，shell 可做到“一切”，但是容易偏慢。想提速，需要堆砌提示词。但是提示词又和模型的脾气挂钩，大模型三个月换一套，提示词也得跟着更新，不过提示词更新其实比较快，一段文本文档而已。（比如，gpt6 的脾气是喜欢现场写 python，做快速满足你提示词的最小回答；而 qwen 的脾气可能是有先用小工具组合，并尽量多轮完整交付）

复杂度在：模型脾气，现场的 python/bash，提示词

B：同 A，但是（1）工具/MCP 的编码与维护是更高的成本（2）工具必须做的很好，一旦效果不如现场写的 python，则工具没有任何存在的意义。甚至模型为了使用工具，减少了现场编写脚本，导致负效果

复杂度：试图将现场脚本的复杂性，封装到工具里

C：最为“快”，但是“灵活性”最窄，一旦稍微越界，就无法回答。速度最快，但是代码复杂度也随之而来的变得很高。模型只负责局部，成本更低。（但是搭建的成本甚至最高）

复杂度：试图将复杂度用代码解构，以便于提速，但是一旦环境、问题数量开始增长，则显得臃肿

D：每个 Agent 的上下文和能力空间更窄，但是整体系统复杂性并不低，评估套件也更加难以设计，试图将复杂步骤拆到子 Agent 里

E：发明一套 DSL，让 Agent 写 DSL，把执行流程卡住。试图用 DSL 来简化 python 的复杂度

F：既要又要的方案。问题是：怎么才能看出来是需要兜底了呢？以及如果两个都有，那不是约等于做了两个产品吗？

### 方案简评、两个点

1、控制流归谁？只要控制流归模型（依靠 finish_reason = tool_calls 自主开启下一轮），那么想要把流程的长度控制住，必辅以大量提示词，并摸清脾气

2、执行层面归谁？归 bash 就灵活但慢，归 tool 可能会好，可能会坏，但是代码复杂度必上升。

备注：先跑 100 轮真实 bash，然后逐步清洗路径，然后再抽 tool，否则上来就抽 tool 可能会导致负面效果（当然也可以分析 tool 使用频率）

### 一个实验

我做了一个实验，大概是：


A：Codex + gpt6 + 简陋提示词

B：Codex + gpt6 + 详细提示词 2

C：Codex + qwen3.8-flash + 简陋提示词

D：Codex + qwen3.8-flash + 详细提示词 1

E：Codex + qwen3.8-flash + 详细提示词 2

我的实验很不严谨，比如 Codex 遇到 gpt 时，本身就会换一套提示词，而 qwen 则跌落到默认提示词，gpt 还会默认注入 memory，而 qwen 不行。所以提示词只是个大概，但是最终目标则每次都一样，详细提示词就是给出各种背景、调查的路径方式等。（均配置针对业务场景的简单 skill）

A：7 次 exec，先查 memory 和 skill，然后直接编写复杂 python 去自己捞日志，再自己解析字段，得出的结论对，但是细节不够全

B：10 次 exec，依旧先查 memory 和 skill，但是被提示词里的不要“反复调试抓取脚本卡住”，甚至没有拿到“route_task_state”

C：40+ 次 exec，花了一些时间在摸索端口、命名空间等，时间片扩大到很大，最后我叫停之间，摸到错误的边

D：40+ 次 exec，依旧扩大时间片（没有遵循指令），最后我叫停，但是结论比 gpt 完整，抓到真正差异

E：14 次 exec，完成任务，但是丢失部分细节

暴露的问题：详细提示词 1 的背景信息能帮模型减少找到端口在哪里的轮次，但会诱导模型反复验证问题、试图彻底解决问题，缺"停止标准"，因此修改为第二版，这次终于停下

对比：一个简易 while 循环 + 写死的工具（内置一些正则表达式和去重逻辑）+ 大量基于规则的流程判断，需要 4～6 次调用，即模型只负责整理，但是覆盖面也是最窄的，同上面的问题，细节丢失最严重

### 封装 CLI 还是 tools

有一种想法是，既然还是要封装一大堆 tools，不如直接做成一个 CLI，然后让模型继续在 bash 里使用

工具的优势是，每一个参数，工具的作用都定义的比较清晰。而一个你自己写的 CLI，它的工具实际上仍然是 bash，你依旧需要在提示词里写丰富的样例来教会 LLM 如何用，并且一旦无法覆盖，LLM 则开始尝试 -h，让迭代轮次增多

针对产品半衰期很短的这件事情，只能这样做：让工具缠绕住 CLI，一个是方便人直接调试，另一个是，即使技术更迭，也可以从 CLI 里再次导出别的工具/功能
