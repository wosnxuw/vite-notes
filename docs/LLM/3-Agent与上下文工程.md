# Agent 架构与上下文工程

这篇文章记录大模型落地后，整个外围应用层的建筑，以及我个人对 AI Agent、上下文工程与控制权演进的理解。

---

## 一、行业演变与鞍具（Harness）哲思

### 重心转移

重心从 Pre Training 到 Post Training，现在似乎都认为 A\ 的思路是对的

Pre 只能解决模型知识量的问题，但是无法解决现实世界复杂的问题（所谓指令遵循？）

### 鞍具（Harness）有用吗？

我经常有一种这样的观点，一个 LLM + 随意一个 Harness，直接开始工作，效果基本差不多。所以我经常性的认为：Harness 没用。

实则我错了，我只是在几款“大浪淘沙”后的精品产品里挑选。

随着大模型本身的能力不断变强，前几个月合适的方法，今天就不合适了。所以一个方法是否好，你要问一句：**如果半年后模型能力提高，你这个方法还有效吗？你今天精细搭建的手脚架还有意义吗，是辅助还是限制？**

根据 Harness 的意思，模型如马匹，Agent 框架如鞍具，如果马匹越来越智能，就需要减少鞍具的约束。（这句话也指导着后续 harness 的设计）

### 产品分类：控制权归谁？

一个明确的分界线是**控制权**归谁？

- **控制权归模型**，则称之为 **Agent**（真正的 Agent）
- **控制权不归模型**，则称之为 **Workflow**（当然有时候也管它叫做 Agent）

控制权的本质是什么？我的理解是 LLM 是发散的，所以人们在这里加了三层约束：

（1）后训练（你无法控制）

（2）硬约束（代码级别的门禁，CI、Harness 沙箱）

（3）软约束（提示词，AGENTS.md）

在底座选择上，如果你就是要模型往某个方向发力，那就偏向 workflow；如果要做成通用助手，那就偏向 Agent。

### 现代 Harness 提升效果与对比试验

这是一个困难的话题。你可以随意研究开源的 PI 和 Codex，但是你只能知道“现在的设计是什么”；或者你通过分析异同，甚至分析 git history，可以大致分析来时的路。

但是，如果今天你的目标是：让你魔改 PI，让它在“原有设计目标”上提高性能，你就没有思路了。所以，天下文章一大抄也是办法之一，前沿 Harness 怎么设计，你就怎么设计。

**对比试验的难点：**
LLM 本身是概率的东西，很多时候你没有办法通过一些固定的函数来检查结果：
（1）结果的呈现方式不唯一，如果是完成某个确定的数值还算好说，如果是修复 bug、做出回复，很多是无法用函数测试的（因为很多文字，是无法点评的，你很难靠 AI 来检查，肉眼看是最有效的，但是最累，A\ 也提到过，所谓的真实测试，所以既然很累，那么大家都在提 RSI）
（2）过程不唯一，你不能假设模型必须用某种方式解决问题。如果你这几一大批测试框架、埋点，你很可能测错位置，最终的目标如果是 fix bug，那么确保 CI 通，但是你可能不能检测到底新增几个类，这种“品味”上的问题，靠检查很难办到。

## 二、上下文管理与腐烂/中毒

### 上下文管理的三个阶段

一开始，是提示词阶段，比如“你是数学博士”，自己写提示词，优化大模型的输入，进而导向更合理的输出，或者 context learning，自己学。后来甚至把环境说的很清楚，但是还是没脱离 chat，没有进入到 Agent 的思路里。

A\ 它的本质是如何用模型，也就是上下文工程，所以 Harness 就是顶级的上下文管理？

有一个理论认为，在 LLM 时代，**大模型好比 CPU，上下文好比内存**，我们需要做的事情，你就是内存管理员，你决定内存里放什么，不放什么。

#### 1、大窗口时代

- Gemini 首先提出 1M 上下文，暴力的提高上下文的长度，这样你可以放更多的内容（比如：整个文档丢进去，不管了）
- 缓存复用：不要渐进式披露工具，因为工具在上下文最头部，一旦变化，则缓存失效
- 提高“内存”大小：用文件系统当作上下文的“外置硬盘”
- 维护 `TODO.md`，以免 Agent 走着走着不知道自己要干嘛了（Manus 5 月）（随机研究生梯度下降）

#### 2、精细化 Token 预算

A\ 认为，所有大模型，注意力预算有上限，标称 1M，实际上 50k 就开始涣散了。所以，我们要在这个预算内，精打细算的放入每一个 token：

- 拿掉了 `TODO.md`，因为反复写它，很浪费 token，将这件事情交给子 Agent（Manus 12 月）
- 拿掉过多的工具定义，只保留核心工具（如 Shell），让 Agent 模仿人，依靠命令行解决问题
- 拿掉模仿人类组织架构的 AgentTeam，即 PM Coder Reviewer，互相聊天协作，其认为 LLM 不是人，这些事情应该交给子 Agent，传参数，拿结果。这块好像确实是这样子，我又看了篇 A\ 的博客。
  - 他们认为：（1）你的上下文腐烂，降低性能（2）并行（3）利用专业工具聚焦于任务的某个重点。
  - 常见的错误是，按照角色来划分 Agent，但是这样会浪费很多 token 在解释身份、解释工作上。反而应该是，**谁掌握这一块的上下文，谁去工作。只有上下文变了，才换人。**（这其实都是最近的实践检验，也许半年以后就换了）

#### 3、交给 AI 决定

- 让 AI 自己决定是否开启子 Agent，自己折叠上下文
- ACE 让 AI 决定每次执行后往执行手册里写什么东西
- A\ 提出 Skill，渐进式披露，让 AI 自己决定看什么

#### 4、未来

所以是否真的印证了那句话，如果 AI 本身够强，只需要给一个 bash 入口，其它一切都不需要了？行业这块有争论，有人认为，只要 AI 就够了，不需要鞍具；有人认为，必须有鞍具。

### 上下文腐烂（Context Rot）与中毒（Context Poisoning）的演变

#### 1、25 年中：上下文中毒与死循环

Context Rot 这个词来源于 Chroma 的一篇研究。即：这次对话怎么改都改不对，换个更笨的模型，或者直接开一个新对话，反而一次做对？你会发现越改越烂的原因有的时候并不是注意力被稀释了，你还没到 5 万 token 就改不对了。

**context poisoning（上下文中毒）**：模型会执着于完成不可能或者无意义的目标。
- 第一次 AI 没改对，说明 AI 已经走错了方向，你叫它重新改，它还是站在了错误的视角上改，反而越来越加强了错误的视角
- AI 陷入循环，是因为它在试图调和 context 里互相矛盾的约束（原始 bug 修复的失败，新的报错混杂在一起）
- 即使 `/compact` 也不管用，这只能在长上下文、注意力稀释的情况下有效，而不是中毒了
- 中毒了，就好比陷入流沙，让 AI 自救，反而越来越差，AI 自己走不出来，只能重开
- 当时的解法：要么重开对话，要么靠 sub-agent（孩子死了无所谓，因为它是干净的）把脏数据隔离在子会话里。

#### 2、现在：中毒解决了，新问题接踵而至

问题的解决：
1. **长程 Agentic RL / RLVR 后训练**：模型后训练的过程中，在权重层面学会了推翻前文错误假设，会否定和质疑自己。甚至有过头的趋势，比如 gpt 会异常谨慎，没看到的事情从来不说死，ds 更甚，用户明确说过的东西它都不一定信，要执行 bash 把事情做实下来，才敢推进。
2. **Sub-agent 与 CodeMode 普及**：以前就提出过想法，把大量探索性的脏活隔离在了主对话流之外。

新的常见毛病：
- **最小修改**：RL 里拿分的标准是“当前报错消失 + 现有单测全过 + 别改崩别的地方”。改架构极易挂单测，所以模型学会了最稳妥的刷分策略——打局部 `if-else` 特判补丁糊弄过去。在一句话的简单提示词下，它不再“改不对”，但代价是破坏整体架构的可维护性，也不会优先思考可维护性。
- **验证强迫症（不会停）**：后训练重罚了“改完不验证就交差”。尤其是在查日志、开放式排查等没有明确终止信号的场景下，模型内置的验证习惯就会失控，不断扩大范围查枝节，缺少“停止标准”。越是小的模型反而越严重（比如谈论的很广的，gpt-6-astra 调整 qwen 0.8 B 的脑细胞的实验）

#### 3、补充：Thinking 到底折不折叠？（与 KV-Cache 命中率的 Trade-off）

如果每调一次工具就把上一步的 `thinking` 折叠/删掉，历史前缀（Prefix）每一轮都会变，KV-Cache 命中率会直接归零。现在工程上对 `thinking` 的处理分为三层：

1. **同一个 Turn 内部（连续调用工具循环中）：绝不折叠，死保缓存**
   只要模型还没最终停下（还在 `tool_calls` 循环里），无论是 DeepSeek 的 `reasoning_content`、OpenAI Responses API 的加密 `reasoning` 块，还是 Claude 的交错思考（Interleaved Thinking），都必须原封不动拼回历史传给下一轮，确保这十几二十次高频工具调用 100% 命中前缀缓存。
2. **跨 Turn 边界（用户发起下一句新提问时）：默认丢弃旧 Turn 的思考**
   当模型完成当前大回合回答、用户输入新问题时，上一大轮的中间 `thinking` 就被丢弃了（只留最终动作和回复），让新一轮对话在更短的上下文基座上重新建缓存。
3. **超长 Turn 内部的阈值触发式清理（类似 GC）**
   如果单轮工具调用极长（几十上百步），Anthropic 在 [Context Editing 文档](https://platform.claude.com/docs/en/build-with-claude/context-editing) 中给出了服务端清理策略（`clear_thinking_20251015` 与 `clear_tool_uses_20250919`）。为了不破坏每一步的缓存，它不是滑窗式每步清理，而是设一个高水位阈值（`trigger`，比如累计超过 100k tokens 才触发一次）：平时不动历史以复用缓存；撞线时一次性批量剃掉早期几十轮的 `thinking` 和旧工具结果——主动承受这一次 Cache Miss 重算 Prefill，换取后续几十步调用重新回到干净短小的上下文上。

## 三、Agent 方案选型：Bash vs Tools vs Workflow

### bash 即一切？

自从看到了 PI + LLM 在各种 benchmark 上跑分 > Codex/Claude Code + LLM，这让我怀疑 Harness 的重要性，即后者是否有些过于“臃肿了”。

一个以前看到的观点也在脑子里浮现：“模型越是强大，就越不需要约束，最后 Harness 只剩下一个 bash 入口”。再加上 prime-agent 这种，一个 IPython Kernel 的 Harness，包括 A\ 、很多 benchmark 跑分的时候也只给模型一个 bash，这让我觉得，一个 bash 就够了，提高 Agent 自主性，提高灵活性。

### bash 适合跑分，但未必适合所有业务

A\ 早就意识到这一点，甚至我还阅读过[那篇博客](https://www.anthropic.com/engineering/writing-tools-for-agents)，不过我被极简循环冲垮了头脑。

尤其是日志是那种内部日志，字段并不常见，**将复杂度留在工具内，可以有效化简 bash 的长度**。

思考你的 Agent 会做什么：
- 一个编写代码、自由探索仓库、运行构建命令的 Coding Agent，适合单 bash
- 一个搜寻日志 + 必要时检索相关代码片段的 Agent，可能就更适配固定的流程或精炼工具

### 不可能三角

- **A：开放、灵活、通用的功能**
- **B：执行约束**
- **C：长期维护成本**

### 六种架构方案对比

- **A**：通用 Agent(bash) + 一大套提示词（说白了就是无设计，纯堆 skill）
- **B**：A 再引入工具/MCP（说白了外挂一个插件）
- **C**：砍掉自主循环，做状态机、工作流 + 辅以各种工具，每一步都由代码来机械式的决定方向
- **D**：多 Agent 系统
- **E**：DSL 系统
- **F**：多模式混合，先走工作流，再用通用兜底

**点评：**

- **A**：最为“灵活”，shell 可做到“一切”，但是容易偏慢。想提速，需要堆砌提示词。但是提示词又和模型的脾气挂钩，大模型三个月换一套，提示词也得跟着更新，不过提示词更新其实比较快，一段文本文档而已。（比如，gpt6 的脾气是喜欢现场写 python，做快速满足你提示词的最小回答；而 qwen 的脾气可能是先用小工具组合，并尽量多轮完整交付）
  - *复杂度在*：模型脾气，现场的 python/bash，提示词
- **B**：同 A，但是（1）工具/MCP 的编码与维护是更高的成本（2）工具必须做的很好，一旦效果不如现场写的 python，则工具没有任何存在的意义。甚至模型为了使用工具，减少了现场编写脚本，导致负效果
  - *复杂度*：试图将现场脚本的复杂性，封装到工具里
- **C**：最为“快”，但是“灵活性”最窄，一旦稍微越界，就无法回答。速度最快，但是代码复杂度也随之而来的变得很高。模型只负责局部，成本更低。（但是搭建的成本甚至最高）
  - *复杂度*：试图将复杂度用代码解构，以便于提速，但是一旦环境、问题数量开始增长，则显得臃肿
- **D**：每个 Agent 的上下文和能力空间更窄，但是整体系统复杂性并不低，评估套件也更加难以设计，试图将复杂步骤拆到子 Agent 里
- **E**：发明一套 DSL，让 Agent 写 DSL，把执行流程卡住。试图用 DSL 来简化 python 的复杂度
- **F**：既要又要的方案。问题是：怎么才能看出来是需要兜底了呢？以及如果两个都有，那不是约等于做了两个产品吗？

### 核心判断与封装策略

**1、两个核心问题**
- **控制流归谁？** 只要控制流归模型（依靠 `finish_reason = tool_calls` 自主开启下一轮），那么想要把流程的长度控制住、稳定住，其实很难，模型脾气占关键，不可能依靠同一段提示词通用
- **执行层面归谁？** 归 bash 就灵活但慢，归 tool 可能会好，可能会坏，但是代码复杂度必迅速上升。
  - *经验*：**先跑真实 bash，然后逐步清洗路径，然后再抽 tool**，否则上来就抽 tool 可能会导致负面效果（当然也可以分析 tool 使用频率）

**2、封装 CLI 还是 tools？**
有一种想法是，既然还是要封装一大堆 tools，不如直接做成一个 CLI，然后让模型继续在 bash 里使用。
- 工具的优势是，每一个参数、工具的作用都定义的比较清晰。而一个你自己写的 CLI，它的工具实际上仍然是 bash，你依旧需要在提示词里写丰富的样例来教会 LLM 如何用，并且一旦无法覆盖，LLM 则开始尝试 `-h`，让迭代轮次增多。
- 针对产品半衰期很短的这件事情，只能这样做：**让工具缠绕住 CLI**，一个是方便人直接调试，另一个是，即使技术更迭，也可以从 CLI 里再次导出别的工具/功能。

**3、做 Agent 的基本准则**
- 选型之前，先搞清楚目标：（1）给谁用？（团队、个人）（2）数据多大、怎么存（文件很少用向量数据库是大炮打蚊子，Claude Code 的记忆系统就是纯文本系统，已经够用）（3）数据需要怎么取出来（精确匹配、模糊搜索向量、多跳联想图谱）
- （1）用户能做到，它能做（2）给它的工具不多不少（3）开局把背景喂饱（4）任务说明书要人来写（5）接口给的越底层的，Agent 的想象空间才大，才能摆脱人工干预。

## 四、外围产品形态与商业哲思

### AI 与 SaaS

做 ToC 的 AI 产品的哲思：
- 传统 SaaS 软件，多一个用户，服务器基本没什么压力，所以用户越多越好，一个月 10 块钱的 QQ 会员，实际上腾讯不需要多费什么力气
- 但是 AI 时代，每多一个用户，显卡是实打实的费电、消耗硬件折损费用，用户越用厂家越亏
- Agent 时代，个人/小团队产生小产品的速度迅速提高了，但是无法达成护城河，你花两个月构思，别人看到你还不错之后，只需要一周便可抄过来。甚至，大模型厂家本身也在抄各种外围生态上的功能。
- 私有数据是壁垒吗？自己训练肯定是不行，没那个财力。不如通用模型 + 鞍具。

### Vibe Coding 工具分类

感觉现在基本上 CC 和 Codex 已经成为标准，其它都没啥用了。

我还留着 vscode 纯属是远程比较方便，至少有个 GUI。

对比如下几类：

（1）**VSCode 本身 + 各种插件**：各种插件毕竟是第三方的，UI 不是那么美好（其实就是内嵌一个网页，高分辨率下，很多字体大小都不统一）

（2）**VSCode 分叉版**：
- Cursor：刚火的时候试过。我看 Cursor 应该是有点黑科技的，尤其是读他们的博客。应该是内置了编译器数据库，据说是先跑小模型理解你的意愿，再找内容，输入给 AI 要看的内容很准，也省 Token。
- Trae、Antigravity

（3）**Zed**：应该是没有 Cursor 那种黑科技的，但是 AI 确实内置到了侧栏，UI 不赖。和 IDE 内置的类似，也是通过查看文件的方式来工作

（4）**命令行**：比如 Claude Code、Codex、Qwen Code、Gemini CLI、Open Code。这类工具的思路是，给 AI 提供工具，让 AI 真正的像人类一样，先 `ls` 查看项目结构，然后再 `grep` 查看关键点。

总结：受限于训练成本，大模型本身确实是 AI 时代的护城河。但是外围生态有点隐约成为城墙的趋势。现在一看模型答题评分都巨高，但是实际体验确实是差距。

### Agent（非 Coding 工具）与其它观察

- **Hermes**：宣传自己是下一代 Agent 工具，原因在于“进化”，你的每一次对话，它都会自动积累经验为 skill，不需要你调教，它自动就反思，号称越来越强大。但是问题同样存在，这些 skill 由 AI 写 AI 存 AI 调，相当于 AI 一个人写完代码，质量无法保证。所以这个项目里还用什么遗传算法来解决 skill 的过期问题。
- **其它**：Manus、Browser-Use、OpenClaw（龙虾）
- **情绪？**：似乎 A\ 认为 AI 是有情绪的，情绪向量会影响结果
