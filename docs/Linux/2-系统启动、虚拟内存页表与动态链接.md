## 一、Linux 启动全流程拆解：从按下电源到挂载 `/`

在虚拟机里用 Arch Linux ARM 跑了一遍从分区、拷内核、配 `systemd-boot` 到进系统的完整手动安装流程后，大学操作系统教材里抽象的启动章节就全部对上号了。

整个开机链路只有以下 6 步接力：

```text
1. 主板固件 UEFI (只认识 FAT32 格式的 ESP 分区，去里面找 .efi 引导程序)
  --> 2. Bootloader (如 systemd-boot 或 GRUB，读取启动项配置，把磁盘上的内核与 initramfs 读进内存 RAM)
        --> 3. 内核 Kernel 启动 (接管 CPU 与内存，但此时它还没有磁盘/文件系统驱动，读不了真正的根分区。)
              --> 4. 挂载 initramfs 作为临时根目录 / (在这个内存小系统里加载 NVMe/VirtIO 磁盘驱动、解锁加密、挂载真正根分区)
                    --> 5. switch_root 切换根文件系统 (丢弃临时 initramfs，把真正的 ext4 根分区切换为 /)
                          --> 6. 启动 /sbin/init (即 PID 1 的 systemd，读取 /etc/fstab 挂载其余分区，拉起各项服务)
```

下面把每一步里最容易卡壳的“鸡生蛋、蛋生鸡”问题拆开：

### 1. UEFI 与 Bootloader（为什么进系统后默认看不到 `.efi` 引导文件？）

- **BIOS vs UEFI**：BIOS 是早年烧录在主板芯片上的一段古老固件程序；UEFI 则是现代主板全面采用的固件规范（虽然大家口头上还是习惯把开机按 Del 进的界面叫“进 BIOS”，但现在进去的其实都是 UEFI）。
- **UEFI 的硬性规定**：UEFI 固件本身不懂复杂的 `ext4` 或 `NTFS`（或者只带极简驱动），标准规定它开机只去硬盘上一个格式为 `FAT32` 的小分区（称为 ESP, EFI System Partition，通常几百 MB）里，寻找后缀为 `.efi` 的可执行引导文件（如果 NVRAM 里没记录启动项，UEFI 就会去读默认的兜底路径：x86_64 是 `/EFI/BOOT/BOOTX64.EFI`，ARM64 是 `/EFI/BOOT/BOOTAA64.EFI`）。
- 三大常见 Bootloader（那个 `.efi` 文件到底是谁？）：
  1. Windows 自带的引导器：名叫 `bootmgfw.efi`；
  2. **GRUB（`grubx64.efi`）**：GNU 项目的老牌默认引导器，绝大多数 Linux 发行版默认用它。功能很庞大复杂，甚至自己内置了 `ext4 / btrfs` 文件系统驱动，支持花哨的双系统菜单；
  3. **`systemd-boot`**：`systemd` 项目出品的现代轻量级引导器。很简洁，配置就是几行纯文本，但它自己不带 `ext4` 驱动，只能读取 UEFI 本身认识的那个 FAT32 ESP 分区。
- 为什么进了 Windows 或 Linux 后，平时看不到 `.efi` 文件？
  因为进入 Windows 后，系统只把主分区（NTFS）挂载成了 `C:` 盘，前面那个几百 MB 的 FAT32 ESP 分区根本没分配盘符隐藏起来了；Linux 同理，取决于你把 ESP 分区挂载到了 `/boot` 还是 `/boot/efi`。

### 2. `/dev` 块设备、硬盘分区与单根挂载模型（`/` 的鸡生蛋问题）

在 Linux 里，一块物理硬盘以及上面的分区，在 `/dev`（Device 虚拟目录）下都表现为一个块设备文件：
- `/dev/sda`：第一块 SATA / SCSI / USB 物理磁盘（后面的数字 `/dev/sda1`、`/dev/sda2` 代表该盘上的第 1、第 2 个分区）；
- `/dev/vda`：KVM / QEMU 虚拟机里的 VirtIO 半虚拟化磁盘；
- `/dev/nvme0n1`：现代 NVMe M.2 固态硬盘（分区叫 `nvme0n1p1`）；
- `/dev/sr0`：光驱或挂载的 ISO 光盘映像；
- 特殊字符设备：`/dev/tty`（当前终端）、`/dev/null`（黑洞）、`/dev/random`（随机数源）。

平时排查磁盘分区、文件系统格式（`ext4` 通用稳定、`xfs` 大吞吐服务器常用、`btrfs` 支持快照与子卷）和当前挂载点，最清楚的一条命令是：

```bash
lsblk -o NAME,MODEL,SIZE,TYPE,FSTYPE,MOUNTPOINTS
```

Windows 多根 vs Linux 单根，以及一个经典的“鸡生蛋”疑惑：
- Windows 是多根系统：装了系统的分区叫 `C:\`，插上第二块盘自动叫 `D:\`，平级并列。
- Linux 是单根树状系统：整台机器只有唯一一个顶点 `/`（根目录）。它把装了 Linux 主系统的那个分区（比如 `/dev/sda2`）挂载为 `/`；其他所有分区或第二块硬盘，都必须挂载到 `/` 下面的某个子文件夹上（比如挂到 `/boot`、`/home`、`/data` 或 `/mnt`，注意：一旦把一个新分区 `mount` 到某个已有目录上，该目录原本里面装的文件就会被暂时遮盖住看不见了）。
- 常见问题：既然根目录 `/` 是从 `/dev/sda2` 挂载来的，可 `/dev/sda2` 这个路径本身又在 `/` 下面，还没挂载 `/` 的时候内核是怎么找到 `/dev/sda2` 的？
  答案是：`/dev/sda2` 只是系统启动后展示给你看的文件路径；在开机引导阶段，内核和 Bootloader 根本不是按路径找硬盘，而是扫描硬件总线，按分区唯一的 `UUID`（或内核内置的设备号）直接定位到那块磁盘分区，把它挂载成 `/`，可以随时用 `findmnt /` 查看当前根目录到底来自哪个底层设备。

### 3. `/boot` 怎么挂？`systemd-boot` 与 `GRUB` 的分区差异

内核本身其实就是一个存放在 `/boot/vmlinuz-xxx`（或 ARM 下的 `/boot/Image`）的普通压缩可执行文件（`vm` 代表支持 Virtual Memory 虚拟内存，`z` 代表经过 gzip 压缩）。

为什么有时候大家讨论把 ESP 分区挂在 `/boot`，有时候又挂在 `/boot/efi`？这直接取决于你选了哪个 Bootloader：

```text
方案 A：使用轻量级的 systemd-boot (因为 systemd-boot 只认识 FAT32，不认识 ext4。)
  - /dev/sda1 (FAT32 格式的 ESP 分区) --> 直接挂载到 /boot
  - /dev/sda2 (ext4 格式的 Linux 主分区) --> 挂载到 /
  --> 结果：引导程序 (/boot/EFI/...)、内核 (/boot/vmlinuz) 和 initramfs 全部放在同一个 FAT32 分区里。
  --> 装系统时的覆盖小坑：如果你先解压了自带 /boot/Image 内核文件的 rootfs 到 ext4 分区，然后再把空的 FAT32 分区 mount 到 /boot 上，原本的内核就被盖住了。必须先把内核拷到 /tmp 暂存，挂好 FAT32 的 /boot 后，再把内核拷回 /boot（即真正写进 FAT32 分区里）。

方案 B：使用全能的 GRUB (因为 GRUB 自己内置了 ext4 驱动，能跨分区读 ext4 里的内核。)
  - /dev/sda1 (FAT32 格式的 ESP 分区) --> 挂载到 /boot/efi (里面只放 grubx64.efi 引导器本体)
  - /dev/sda2 (ext4 格式的根分区)     --> 挂载到 / (里面的 /boot 子目录直接躺在 ext4 上，存放内核与 initramfs)
```

以 `systemd-boot` 为例，当 UEFI 启动了它之后，它会去读 ESP 分区下的 `/loader/entries/arch.conf` 启动项配置文件：

```ini
title   Arch Linux ARM
linux   /Image
initrd  /initramfs-linux.img
options root=/dev/vda2 rw console=ttyAMA0,115200 console=tty0
```

注意这里写的是 `linux /Image` 而不是 `/boot/Image`——因为对 Bootloader 来说，它的眼界里只有那一个 FAT32 ESP 分区，它根本不知道进入 Linux 后你会把这个分区挂载到 `/boot` 还是哪里，这里的 `/` 指的就是 ESP 分区自己的根目录。

### 4. `initramfs` 与 `mkinitcpio`（破解驱动的鸡生蛋问题）

现在 Bootloader 已经把内核 `vmlinuz` 读进内存跑起来了，并且通过 `options root=/dev/vda2` 告诉了内核：“真正的根分区在 `/dev/vda2`（一块格式化为 `ext4` 的 VirtIO 虚拟硬盘）上，你快去挂载它吧。”

此时内核遇到了开机路上最大的第二个“鸡生蛋”死锁：
- 内核要想读取 `/dev/vda2`，就必须先加载 VirtIO 磁盘驱动（`virtio_blk.ko`）和 `ext4` 文件系统驱动（`ext4.ko`）（甚至如果硬盘做了 LUKS 全盘加密或 RAID，还需要解密工具）；
- 可是这些 `.ko` 驱动模块文件，恰恰就存放在 `/dev/vda2` 根分区的 `/lib/modules/` 目录下。（没有驱动就打不开硬盘，打不开硬盘就读不到驱动，死锁了。）
- 为什么不把天下所有的硬盘驱动、RAID 驱动、加密工具全静态编译进内核 `vmlinuz` 本体里？那样内核文件会膨胀得很臃肿。

破局方案就是 `initramfs`（Initial RAM Filesystem，初始内存文件系统，即配置里的 `initrd /initramfs-linux.img`）：
1. 在装系统（或每次更新内核）时，系统会调用 `mkinitcpio`（或 Ubuntu 下的 `update-initramfs` / `dracut`），按配置文件里的 `HOOKS` 顺序，像装修工种进场一样把开机早期必需的最小集合打包成一个几十一百 MB 的压缩包 `initramfs-linux.img`：
   - `base`（放 BusyBox 最小 shell） $\rightarrow$ `udev`（设备探测） $\rightarrow$ `autodetect`（探测当前这台电脑到底用了什么硬件，只打包当前机器需要的驱动以缩小体积） $\rightarrow$ `modconf` $\rightarrow$ `block`（放入磁盘控制器驱动如 `virtio_blk.ko` / `nvme.ko`） $\rightarrow$ `filesystems`（放入 `ext4.ko` 等文件系统驱动） $\rightarrow$ `keyboard`（如果要输密码解锁加密盘则提前加载键盘驱动） $\rightarrow$ `fsck`（磁盘检查工具）。
2. 开机时，Bootloader 把内核和这个 `initramfs.img` 一起读进内存 RAM；
3. 内核启动后，先把内存里的 `initramfs` 解压当成临时的根目录 `/`，从里面加载好磁盘驱动和 `ext4` 驱动，顺利认出并挂载真正的硬盘分区 `/dev/vda2`；
4. 最后执行 `switch_root`：把临时内存根卸载扔掉，正式切进真正的硬盘根文件系统 `/`，并把控制权移交给 PID 1 的 `systemd`（由它读取 `/etc/fstab` 自动挂载表把剩下的分区全挂好）。

## 二、操作系统内存管理：虚拟地址、多级页表与 TLB

复习一下操作系统最核心的虚拟内存机制：为什么每个进程打印自己变量的地址看起来都在差不多的高位区间，却完全不会互相覆盖？

### 1. 为什么必须按“页（Page，4KB）”来映射，而不是按字节映射？

1. 每个进程都需要自己独立的虚拟地址空间（让每个进程都以为自己独占了整台机器的内存，且 A 进程绝不能直接读写 B 进程的内存）。
2. CPU 执行指令时拿到的是虚拟地址（Virtual Address），必须由 CPU 内部的硬件 MMU（内存管理单元）查表翻译成内存条上的物理地址（Physical Address）。
3. 为什么不能一个字节对应一个字节地建映射表？
   如果每 1 个字节建一条映射，64 位系统哪怕只管 4GB 内存，光存这张映射表本身就要吃掉几十 GB 的内存。所以必须把虚拟内存和物理内存都切成固定大小的“块”来整块映射——这个块就叫“页（Page）”。
4. 在 Linux 下，默认一页的大小是 `4KB`（即 $2^{12} = 4096$ 字节）。
   因此，任何一个内存地址在二进制上都被天然切成了两截：高位的“页号” + 最低 12 位的“页内偏移量（Offset）”：

```text
虚拟地址 (VA) = [ 虚拟页号 VPN (Virtual Page Number) ] + [ 页内偏移 Offset (固定占最低 12 bits) ]
  --> 通过查该进程的页表 (Page Table)，将 VPN 替换为物理页号 PFN（页内偏移 12 bits 原样保留）
物理地址 (PA) = [ 物理页号 PFN (Page Frame Number)  ] + [ 页内偏移 Offset (固定占最低 12 bits) ]
```

### 2. 页表项（PTE）与两种缺页异常（Page Fault）

如果我们先把页表（Page Table）想象成一个记录 `虚拟页号 VPN --> 物理页号 PFN` 的大字典，这个字典里的每一条记录就叫一个 页表项（PTE, Page Table Entry）。

注意：PTE 的 Value 里不仅存着物理页号 `PFN`，还利用剩余的 bit 位存了很关键的 状态位与权限位（如 `Present` 是否在物理内存中、`R/W` 是否允许写入、`U/S` 用户态还是内核态可访问、`NX` 是否禁止当作代码执行）。

当 CPU 试图访问某个虚拟地址，但 MMU 去查页表发现不对劲时，CPU 硬件会自动触发一次 缺页异常（Page Fault）中断陷入内核，主要分两种截然不同的下场：
1. 非法越界访问（异常终止 `SIGSEGV` 段错误）：
   比如 C 语言里解引用了空指针 `NULL (0x0)` 或者野指针。内核去查该进程的虚拟内存区域表（`struct mm_struct` 里的 VMA，记录了代码段、堆、栈、`mmap` 到底合法占了哪些区间），发现这个虚拟地址压根就没有建立过任何合法映射。内核直接向该进程发送 `SIGSEGV` 信号将其杀死（`Segmentation fault`）。
2. 合法但物理页暂不在内存中（按需分配或 Swap 换入，正常恢复）：
   虚拟地址是合法的（比如刚 `malloc` 申请了内存但第一次往上写数据，或者这页内存太久没用被内核临时置换 Swap 到了硬盘上），只是 PTE 里的 `Present` 位为 `0`。此时内核在后台默默分配一块真实的物理内存页（或从硬盘 Swap 把数据读回物理内存），填好 PTE 映射并把 `Present` 置为 `1`，然后让 CPU 重新执行刚才那条指令——整个过程对用户程序完全透明。

### 3. 为什么内核页表不用 HashMap，也不用单级大数组，而是用“多级页表”？

这是理解底层硬件数据结构最精妙的一个点：

1. 为什么不能像写业务代码那样用 HashMap 或红黑树存页表？
   因为查页表不是由软件代码做的，而是由 CPU 硬件电路（MMU）在执行每一条内存读写指令时现场自动查的。HashMap 需要算哈希、处理哈希碰撞链表/开放寻址探测，红黑树需要多次分支比较，硬件电路做这种不定长跳转既复杂又慢；硬件最喜欢的是“用二进制位直接当数组下标 `array[index]`，一步到位偏移寻址”。
2. 既然数组下标最快，为什么不用一个一维大数组？
   算一笔账：哪怕在 32 位系统（4GB 地址空间，共 $2^{20} \approx 100\text{ 万}$ 个 4KB 页）下，如果用一个完整的一维数组存所有页表项，每一个进程一启动，不管它实际只用了 1MB 还是 10MB 内存，内核都得先为它分配一张连续 4MB 的完整页表数组；到了 64 位系统（48 位有效虚拟地址，共 $2^{36}$ 个页），一个进程的一维页表数组更是高达 512GB。而实际上绝大多数进程只用了零星几块内存，大数组里 99.99% 的格子全是空的。
3. **多级页表（硬件友好的树状按需稀疏数组）**：
   Linux 在 64 位下采用 4 级（或 5 级）页表（PGD $\rightarrow$ PUD $\rightarrow$ PMD $\rightarrow$ PTE）。
   它的原理很简单：把高位的虚拟页号 VPN 切成 4 段（每段 9 个 bit，正好对应 $2^9 = 512$ 个元素的数组下标）。
   - 第一级目录（PGD）只占 1 个 4KB 物理页（装 512 个指针）；
   - 如果某一大片虚拟地址区间进程根本没用到，那么第一级目录对应的格子直接填 `NULL`，它底下的第二、三、四级页表根本不需要分配内存。
   - 只有真正用到了哪块地址，才按需长出哪条分支的叶子数组。这就用很微小的内存代价，换来了硬件可以直接按固定 9-bit 位切片连跳 4 次下标的确定性寻址。

### 4. TLB（快表）与进程的 `mm_struct`

- TLB（Translation Lookaside Buffer，页表缓存）：
  虽然 4 级页表省了内存，但意味着 CPU 每读写一次内存里的变量，MMU 都要先去物理内存里连跳读 4 次页表，等于内存访问慢了 4 倍。为此，CPU 芯片内部专门集成了一块极高速的硬件缓存 TLB，把最近刚查过的几十到几百条 `VPN --> PFN` 映射直接缓存在 CPU 核心旁。99% 的情况下直接命中 TLB（0 额外内存访问），只有 TLB Miss 时才去内存里走一遍 4 级页表。
- **为什么不同进程可以用一模一样的虚拟地址？**
  因为在 Linux 内核里，每个进程（线程组）都有自己独立的内存描述符 `struct mm_struct`，里面存着属于该进程自己的顶级页表根物理地址（装入 CPU 的 `CR3 / TTBR0` 寄存器）。当操作系统发生进程上下文切换时，内核顺手把新进程的页表根地址刷进 `CR3` 寄存器（并刷新非全局 TLB），同样的虚拟地址 `0x400000` 查的就是另一套页表，自然映射到完全不同的物理内存页上。

## 三、Linux 动态链接机制：`.so` 查找顺序、`SONAME` 与 `-dev` 包

### 1. 动态链接的设计理念与“把应用依赖提升为系统状态”的代价

Linux 发行版传统的核心哲学是：一台机器上的所有程序，尽量共享系统里的同一份动态链接库（`.so`，Shared Object，对应 Windows 的 `.dll`），由发行版包管理器（`apt / dnf`）统一维护升级。
- **四大好处**：① 省磁盘空间、省物理内存（多个进程在物理内存里共享同一份 `libc.so` 代码段）；② 安全漏洞集中修复（比如 OpenSSL 出了高危漏洞，只需 `apt upgrade libssl` 更新一个 `.so` 文件，全机几百个依赖它的软件直接全部修好，不用挨个重编译）；③ 发行版能做全系统依赖图集成测试；④ ABI 稳定时体验极佳。
- **最大的代价**：它把原本属于“单个应用的私有依赖”，提升成了“整台操作系统的全局共享状态”。
  你的程序能不能跑起来，不再只取决于你的代码，而是取决于目标机器上的 `/usr/lib`、`ld.so.cache`、`LD_LIBRARY_PATH`、编译器 C++ ABI、特别是底层 `glibc` 的版本（在 Ubuntu 24.04 上编译出来的 C/C++ 程序，直接拷到 Ubuntu 20.04 上跑，十有八九会报 `GLIBC_2.38 not found`）。
  （注：Docker 容器虽然能把用户态的 `/usr/lib` 和 `glibc` 一起打包隔离，解决了 90% 的依赖冲突，但一旦涉及宿主机 Linux 内核模块、NVIDIA GPU 驱动与 CUDA Runtime 映射，依然会撞上底层的 ABI 边界。）

顺带一提现代 Linux 的 `/usr` Merge（目录合并）：
在远古 Unix 时代，因为第一块小硬盘装不下所有东西，系统把开机急救必需的库和命令放在 `/lib` 和 `/bin`，把普通用户态程序放在另一块盘挂载的 `/usr/lib` 和 `/usr/bin`。而在现代 Linux（如 Ubuntu 24.04 / Arch）中，单盘容量极大，系统已经通过顶层软链接把它们彻底合并了——现在的 `/bin` 就是指向 `/usr/bin` 的软链接，`/lib` 就是指向 `/usr/lib` 的软链接。

### 2. 一个程序启动时，到底按什么顺序去哪找 `.so` 动态库？

当你运行一个动态链接的程序报错 `error while loading shared libraries: libxxx.so: cannot open shared object file` 时，先用 `ldd <程序路径>` 查看它到底缺哪个库。

Linux 的动态链接器在寻找 `.so` 时，严格按以下优先级从高到低搜索：

1. 编译时焊死在二进制 ELF 内部的 `DT_RPATH`（旧） / `DT_RUNPATH`（现代）路径：
   - 安全铁律（与 Windows 最大的不同）：在 Windows 上，双击一个 `.exe`，系统默认会优先加载“`.exe` 所在同级目录以及当前工作目录”下的 `.dll`；但在 Linux 下，默认不会去当前工作目录（`.`）或可执行文件同级目录下找 `.so`。
   - **为什么 Linux 禁止默认搜当前目录？** 为了防止“动态库劫持”：试想如果默认搜当前目录，黑客在 `/tmp` 下放一个伪造的恶意 `libc.so.6`，管理员一旦 `cd /tmp` 敲了一下 `ls`，`ls` 就会加载 `/tmp/libc.so.6`，服务器直接被夺权。
   - 如果你确实想让自己发布的 Linux 程序自动加载它自己旁边 `./lib` 目录下的私有 `.so`，必须在编译链接时显式传入特殊变量 `$ORIGIN`（代表可执行文件自身所在的目录）：`gcc main.c -Wl,-rpath,'$ORIGIN/lib'`。
2. 环境变量 `LD_LIBRARY_PATH`（日常本地调试临时加路径最常用）：
   ```bash
   export LD_LIBRARY_PATH=/my/custom/lib:$LD_LIBRARY_PATH
   ```
3. 系统全局动态库缓存 `/etc/ld.so.cache`：
   当你往 `/etc/ld.so.conf.d/` 下新增了库目录后，执行一次 `sudo ldconfig`，系统就会扫描这些目录生成的哈希索引缓存。
4. **操作系统兜底默认库目录**：
   - 在 RedHat / CentOS 系上，主要放在 `/lib64` 和 `/usr/lib64`；
   - 而在 Ubuntu / Debian 系（支持多架构 Multiarch）上，`/lib64` 里其实孤零零地只放了唯一一个动态链接器文件 `ld-linux-x86-64.so.2`，真正成千上万个 `.so` 库全部存放在 `/lib/x86_64-linux-gnu/` 和 `/usr/lib/x86_64-linux-gnu/` 下。

### 3. 解读 `ldd` 的输出：谁来加载动态链接器自己？

以在 Ubuntu 上执行 `ldd /usr/bin/git` 为例，输出里有三个非常特殊的细节：

```text
$ ldd /usr/bin/git
    linux-vdso.so.1 (0x0000782999c2e000)
    libpcre2-8.so.0 => /lib/x86_64-linux-gnu/libpcre2-8.so.0 (0x0000782999766000)
    libz.so.1 => /lib/x86_64-linux-gnu/libz.so.1 (0x000078299974a000)
    libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x0000782999400000)
    /lib64/ld-linux-x86-64.so.2 (0x0000782999c30000)
```

1. 最后一行 `/lib64/ld-linux-x86-64.so.2`（动态链接器本身）：
   你会发现上面三个普通库（`libz.so.1`）左边只写了文件名，靠 `=>` 动态去找路径；唯独最后这一个直接写死了绝对路径 `/lib64/ld-linux-x86-64.so.2`。
   因为它是动态链接器（Program Interpreter）本身——所有其他的 `.so` 都是由它负责去磁盘上找并加载进内存的。为了解决“谁来找动态链接器自己”的鸡生蛋问题，每个动态链接的 ELF 可执行文件在编译时，都会在 ELF 头部的 `.interp` 段里把动态链接器的绝对路径硬编码写死（可用 `readelf -l /usr/bin/git` 看到 `[Requesting program interpreter: /lib64/ld-linux-x86-64.so.2]`）。内核执行 `execve` 启动程序时，会先直接把这个链接器读进内存，再由它接手加载其余的 `.so`。
2. 第一行 `linux-vdso.so.1`（找不到磁盘文件的虚拟库）：
   它后面没有 `=>` 路径，因为它根本不是磁盘上的文件，而是 Linux 内核在启动每个进程时，自动映射进进程虚拟内存里的一小段内核代码页（vDSO, Virtual Dynamic Shared Object）。它的作用是让 `gettimeofday()`、`clock_gettime()` 这类高频获取时间的调用直接在用户态内存里读内核维护的时间变量，省去真正陷入内核态系统调用的昂贵上下文切换开销。

### 4. `SONAME` 三级软链接命名法与 `-dev` 开发包的秘密

如果你去 `/usr/lib/x86_64-linux-gnu/` 下搜一个库（比如 `libz` 或 `libgflags`），常常会看到同一个库居然同时存在 三个名字长短不一的文件（其中两个是软链接）。这套设计是为了配合 SemVer 语义化版本（`MAJOR.MINOR.PATCH`，主版本不兼容修改 . 次版本向下兼容新增 . 补丁版本修复），实现多版本共存：

| 名称层级 | 文件名示例 | 它是谁？ | 什么时候被谁用？ |
| :--- | :--- | :--- | :--- |
| 1. 真实物理文件 (Real Name) | `libgflags.so.2.2.2` | 真正占磁盘空间的二进制动态库本体，带着最完整的三级版本号 | 软链接的最终指向目标 |
| 2. 运行时接口名 (SONAME) | `libgflags.so.2`（或 `.2.2`） | 一个指向真实文件的软链接；同时这个名字作为 `SONAME` 字段被直接焊死在 `.so` 内部头信息里 | 程序运行期（Runtime）的唯一寻找依据。刚才 `ldd git` 里显示的 `libz.so.1` 就是 SONAME |
| 3. 编译期链接裸名 (Linker Name) | `libgflags.so`（不带任何版本数字） | 一个指向当前系统默认版本的软链接 | 仅在写代码编译链接期（`gcc -lgflags`）使用。编译完生成的程序里只记它指向的那个 SONAME（`libgflags.so.2`），运行期根本不再看 `libgflags.so` 这个裸名 |

看懂这张表，Linux 下两个最让人困惑的包管理现象就很容易理解了：

1. 为什么系统里可以同时安装 `libgflags v2` 和 `libgflags v3` 的运行库而完全不冲突？
   因为它们的 SONAME 不同（一个叫 `libgflags.so.2`，一个叫 `libgflags.so.3`）。它们躺在 `/usr/lib` 下就像两个名字完全不同的普通文件一样和平共处：老软件启动时按自己的记录去找 `.so.2`，新软件启动时去找 `.so.3`，井水不犯河水。
2. 为什么 Ubuntu 的 `apt` 把每个库都拆成不带后缀的 `libxxx`（运行包）和带后缀的 `libxxx-dev`（开发包），且不同主版本的 `-dev` 包往往不能同时安装？
   - 不带 `-dev` 的包（如 `zlib1g`）：里面只装了运行期需要的真实库文件和 SONAME 软链接（`libz.so.1`）。如果你只是运行别人编译好的程序，装这个就够了。
   - 带 `-dev` 的包（如 `zlib1g-dev`，RedHat 系叫 `-devel`）：是专门给需要写 C/C++ 代码做编译（`#include <zlib.h>` 和 `gcc -lz`）的人装的。里面只装三样编译期配件：
     ① `/usr/include/` 下的 `.h` 头文件；
     ② `/usr/lib/` 下那个不带任何版本号的裸名软链接 `libz.so`；
     ③ `pkg-config` 用的 `.pc` 元数据文件与 `.a` 静态库。
   - 正因为那个不带版本号的裸名软链接 `libxxx.so`（以及 `/usr/include/xxx.h`）在整个系统里只能有一份、只能指向唯一的默认版本，所以不同主版本的运行包可以共存，但它们的 `-dev` 开发包就会因为争抢同一个裸名软链接而互斥。
