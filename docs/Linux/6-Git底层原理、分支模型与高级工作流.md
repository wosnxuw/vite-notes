# Git 底层原理、分支模型与高级工作流

扔掉“Git 是用来对比保存文件差异的”这种表面印象，从底层数据结构的视角看过去，整个 Git 仓库本质上就只是一个“节点不可变的单向有向无环图（DAG）”加上“几个贴在节点上的轻量级便签纸指针（Branch 与 HEAD）”。把这张图和指针怎么跳搞明白，所有高级命令都是在图上挪便签纸而已。

---

## 一、Git 的四个底层原子概念：分布式、提交图（DAG）、Branch 与 HEAD

### 1. 什么是真正的“分布式”版本控制？

在老一代集中式版本控制（如 SVN）里，完整的历史库只存在于公司的中心服务器上，你电脑上拿到的只是一份当前版本的文件拷贝，断了网连看历史或建分支都干不了。
而在 Git 里：你电脑本地的那个 `.git/` 文件夹，就已经是一座 完整的 Git 仓库了。GitHub 或 GitLab 服务器上的仓库，地位和你本地的仓库是完全平级的另一个副本——你执行 `push / pull` 只是在把你本地图上的节点同步给它，而不是你从属于它。

### 2. Commit Graph（提交图）：只认亲爹、不认儿子的单向图

整个 Git 的提交历史是一张 DAG（有向无环图）：
- 每当你执行一次 `git commit`，Git 就会把当前代码树拍个快照，算出一个全球唯一的 40 位 SHA-1 哈希值（如 `a1b2c3d...`），在图上生成一个新的 Commit 节点（Node）；
- **最核心的指针方向**：每个 Commit 节点内部，都用死锁的哈希值记录了“我的父节点（Parent，即我是在哪次提交的基础上改出来的）是谁”。
- 注意这个单向链表的方向：每个节点只知道自己的亲爹是谁，而父节点完全不知道自己后面生了哪几个儿子。并且因为父节点的哈希也被算进了子节点的哈希里，任何一个已经生成的 Commit 节点，它的内容和它的父节点指针是永远不可被篡改的（任何试图“修改历史”的操作，在底层其实都是放弃旧节点、在旁边偷偷新建一个长得很像的新节点）。

```text
Git 提交图的真实指针方向（总是从新节点反向指回老节点）：

[Commit A (根提交)] <-- [Commit B] <-- [Commit C] <-- [Commit D]
```

### 3. Branch（分支）：只是一张 41 字节的“路标便签纸”

千万不要把 Git 的分支（Branch）想象成 SVN 那样“在服务器上把整个项目文件夹复制了一份”。
在 Git 里，一个名叫 `main` 或 `feature` 的分支，在 `.git/refs/heads/` 目录下真的就只是一个只有一行 40 位 Commit 哈希值的纯文本小文件。
- **分支的本质**：就是一个贴在某个 Commit 节点上的可变指针（路标）。
- 为什么需要分支？因为在一张分叉繁多的 DAG 图上，如果没有贴着 `main`、`dev`、`bugfix` 这些路标便签纸，你根本分不清哪条分叉树枝是干嘛的；更关键的是，如果某个分支树枝上没有任何一张路标便签纸指着它（也没法从任何便签纸顺着父指针回溯找到它），那这截树枝上的 Commit 就成了“悬空孤儿节点（Dangling Commits）”，默认过 30 天左右就会被 Git 的垃圾回收（`git gc`）彻底清理掉。

### 4. `HEAD` 指针与一次 `git commit` 到底挪动了谁？

既然一个仓库里可以同时有 `main`、`dev`、`feature` 十几个分支便签纸，Git 怎么知道你现在敲键盘写的代码到底是在哪个分支上干活？
靠唯一的全局当前指针 —— `HEAD`（本地仓库、远端仓库、以及每个附加的 `worktree` 都有各自独立的 `HEAD`）：

1. 正常状态（`HEAD` 指向某个 `Branch`，`Branch` 再指向 `Commit` 节点）：

   ```text
   提交前：
   [Commit A] <-- [Commit B] <-- [Commit C]  (main 分支指向 C，HEAD 指向 main)

   当你执行一次 git commit 生成新节点 D 时：
   [Commit A] <-- [Commit B] <-- [Commit C] <-- [Commit D]  (D 的父节点设为 C；HEAD 依然指向 main，main 自动前移指向 D)
   ```

   看清楚这步操作的精髓：当你提交代码时，`HEAD` 依然指着 `main` 没变，是 `main` 这张分支便签纸自动往前跳了一格，贴到了最新的节点 `D` 上。
2. 游离状态（`Detached HEAD` —— 当你直接 `git checkout <某次历史 Commit 的哈希值>` 时）：
   此时 `HEAD` 脱离了任何 `Branch` 便签纸，直接指在了某个具体的历史 Commit 节点上。
   - 为什么一般严禁在 `Detached HEAD` 状态下直接提交代码并切走？
     因为此时没有 `main` 或 `dev` 这类分支便签纸跟着你往前走。你在游离状态下哪怕 `commit` 了三个新节点，一旦你随后敲了一句 `git checkout main` 把 `HEAD` 挪走，你刚才在游离态写的那三个新节点身后就没有任何分支路标指着它们了，直接变成悬空孤儿从 `git log` 里消失。（万一不小心干了这事，唯一能救命的就是趁着 30 天垃圾回收期没到，赶紧敲 `git reflog` 查出本机 `HEAD` 刚才跳过来的历史哈希值，再在那个哈希上补建一个 branch 把它拴住。）

> 顺带一提 `master` 与 `main`：两者在技术上没有任何区别，纯粹是 `git init` 初始化仓库时的默认第一个分支名字。2020 年“Black Lives Matter”运动后，GitHub 与新版 Git 将默认初始分支名从 `master` 改为了 `main`。

## 二、远端同步的真相：`remote`、`origin/main` 与 `push` 的前置条件

### 1. `remote`（`origin` vs `upstream`）与认证协议（SSH vs HTTPS）

- **`remote` 是什么？** 它跟你在 `git config` 里配的 `user.email` 一样，本质上只是配置文件（`.git/config`）里的一个键值项，用来给一长串远端仓库 URL 起个简短的别名：
  - **`origin`**：当你执行 `git clone <URL>` 时，Git 默认自动给这个克隆来源地址起的别名就叫 `origin`；
  - **`upstream`**：开源协作的惯例命名。如果你在 GitHub 上点 `Fork` 把别人的开源仓库拷到了自己名下，再 clone 你自己的仓库到本地，那么你自己的远端仓库叫 `origin`，为了拉取原作者的最新更新，你通常会手动 `git remote add upstream <原作者仓库URL>`，把原作者的仓库起名叫 `upstream`。
- SSH (`git@github.com:...`) vs HTTPS (`https://github.com/...`)：
  GitHub 等平台早已禁止直接输入账号明文密码来推送代码。Git 会根据你的 `remote` URL 前缀自动走两套完全不同的认证通道：
  1. 如果 URL 以 `git@`（或 `ssh://`）开头：走 SSH 协议。直接复用你电脑 `~/.ssh/` 下的私钥与 `config` 配置（需要在 GitHub 网页设置里粘贴你的 `.pub` 公钥）；
  2. 如果 URL 以 `https://` 开头：走 HTTPS 协议。Git 会调用系统中配置的凭据管理器（`credential.helper`，如 macOS 钥匙串、Windows 凭据管理器或 Git Credential Manager）自动获取你登录过的个人访问令牌（Personal Access Token, PAT）。

### 2. 极具迷惑性的 `origin/main`：它不是一个网络网址，而是你本地的一张“只读快照分支”。

很多初学者看到 `origin/main`，以为一提到它就会联网去查远端服务器。
完全不是。`origin/main`（远程跟踪分支）也是真真实实存在你本地电脑 `.git/refs/remotes/origin/main` 下的一个本地指针。
- 它的唯一作用是：记录“上一次你跟远端 `origin` 联网通信（`git fetch / pull / push`）的那一直接，远端服务器上的 `main` 分支指在哪个节点上”。
- 如果你三天没敲过 `git fetch`，哪怕同事这三天往远端服务器上推了 100 个新 Commit，你本地电脑上的 `origin/main` 指针也纹丝不动，依然停在三天前的位置（注：`origin/xxx` 也不一定非得对应远端的 `HEAD` 默认分支，每个同步下来的远端分支在本地都有对应的 `origin/dev`、`origin/feature` 快照指针）。

### 3. `git push` 成功必须满足的两个铁律与“传出的更改（Outgoing Changes）”

在默认不加 `--force` 强推的情况下，你敲 `git push` 想要把本地分支推上远端，Git 服务端会严格检查两条规则：
1. 你本地待推送的分支与远端目标分支名字对得上（防止你在本地测试分支手滑直接推到了远端的 `main` 上）；
2. **Fast-Forward（快进）祖先约束**：远端那个分支当前指向的 Commit 节点，必须是你本地分支最新节点的“直系祖先（父节点或爷爷节点）”。（如果不是——比如同事在你之前往远端推了一个新节点，导致远端节点不在你的历史链条里，Git 就会拒绝推送，逼着你先把远端的变更拉下来合并或变基。）
   而且 `git push` 只会推动远端对应的分支指针往前走，不会去乱改远端仓库的 `HEAD` 默认分支指向。

借此解释一个在 VS Code / Lazygit 里很常见的困惑——什么是“传出的更改（Outgoing Changes）”？

“传出的更改”定义为：已经存在于你当前本地分支历史里、但还不存在于它所跟踪的那个远程分支（如 `origin/main`）历史里的所有 Commit。

平时在单分支上，它就是你本地 `main` 比 `origin/main` 多出来的那几个新提交；但一旦你做了 本地分支合并（Merge），就会出现一个让很多人吓一跳的画面：

```text
假设你在本地 feature 分支开发了 D 和 E，并且已经把 D 和 E 推送到远端的 origin/feature 上了。
随后你在本地切回 main 分支，执行了 git merge feature，生成了合并节点 M（此时还没 push main）：

feature 支线 (origin/feature 已停在 E)：       [D] <-- [E]
                                             /           \
main 主线 (origin/main 仍停在 C，main 在 M)： [A] <-- [B] <-- [C] <------- [M]
```

这时候你在 `main` 分支上看 VS Code 的“待推送 / 传出的更改（Outgoing Changes）”，列表里居然会同时列出 `D + E + M` 三个提交。
- 你可能会纳闷：“`D` 和 `E` 我刚才明明已经在 `feature` 分支上 `push` 到服务器过了啊，怎么切到 `main` 它又说待传出？”
- **原因**：因为 Git 算“传出的更改”时，只对比当前分支 `main` 与它绑定的 `origin/main` 之间的历史差集（`git log origin/main..main`），完全不管别的分支。虽然远端的 `origin/feature` 认识 `D` 和 `E`，但从 `origin/main`（停在 `C`）顺着父指针往回找，根本找不到 `D` 和 `E`。所以站在 `origin/main` 的视角看，`D`、`E`、`M` 全都是即将通过这次推送并入 `main` 主干的新历史。（顺带一提：在 Lazygit 或 VS Code 的 Git Graph 里，默认往往只展示“从当前选中分支能回溯抵达的节点历史”；如果你想排查仓库里有没有被遗忘的死分支或全貌，记得把视图过滤器从“当前分支/自动”切到“全部（All）”，让它把整张 DAG 图完整画出来。）

## 三、分支整合与手术刀工具：`merge`、`rebase` 与 `cherry-pick`

### 1. 分支图轨道的视觉假象：Commit 节点里根本没记“我出生在哪个分支”。

看各种 Git GUI 工具画出来的彩色分支轨道图时，一定要破除一个最大的幻觉：某一个 Commit 节点曾经是在 `bugfix/foo` 分支上提交出来的——这个信息根本就不存在于 Commit 节点的数据结构里。

因为刚才说过，Branch 只是一张贴在末端节点上的临时便签纸。一旦两个分支完成了合并，你把 `bugfix/foo` 这张便签纸删掉了，单看留下的菱形分叉图：

```text
节点拓扑图：
          [D] ◀── [E]
         /           \
[A] ◀── [B] ◀── [C] ◀── [F (合并节点)] ◀── [G]
```

你习惯性地以为上面那条 `B -> C -> F -> G` 是 `main` 主线，下面那条 `D -> E` 是功能分支；但完全有可能当年真实发生的是：`D -> E` 才是当时的 `main`，后来因为分支删除、重命名、`reset` 移动指针，最终把 `main` 便签纸贴到了 `G` 上。
（唯一的线索是：像 `F` 这种由 `merge` 产生的合并节点，它内部记录了两个具有先后顺序的父节点指针：`First Parent` 是执行 `git merge` 时你正站在的那个主分支末端，`Second Parent` 是被你合进来的那个分支末端。）

### 2. `git merge` vs `git rebase`（捏合分叉 vs 移花接木）

当你的 `feature` 分支和 `main` 主干分叉成了一个“Y”字形，要把两边合到一起时，有两种截然不同的图手术：

1. `git merge`（老老实实捏合，保留真实分叉历史）：
   直接生成一个新的拥有两个亲爹的合并节点 `M`，把“Y”字形的两根叉捏在一起。优点：绝不篡改任何已有 Commit 节点，保留真实的开发时间线与分叉轨迹；缺点：多人高频合并时，图上会布满交错纵横的合并线。
2. `git rebase`（变基：把我的分叉剪下来，嫁接到主干最新节点的屁股后面，拉成一条直线）：
   很多人以为 `rebase` 是直接把原来的节点 `D` 和 `E` 揪下来挪了个位置。
   记住前面的铁律：已经生成的 Commit 节点，它的亲爹指针是永远改不了的。
   所以 `git rebase main` 在底层干的其实是“克隆重写 + 抛弃旧节点”：

   ```text
   Rebase 之前（在 C 处分叉，main 走到了 F，你的 feature 走到了 D -> E）：
   main:     [A] ◀── [B] ◀── [C] ◀── [F (main)]
                               \
   feature:                     [D] ◀── [E (feature)]

   在 feature 分支执行 git rebase main 之后：
   main & feature 变成了一条笔直的线：
             [A] ◀── [B] ◀── [C] ◀── [F (main)] ◀── [D'] ◀── [E' (feature)]
                               \
   (被抛弃的孤儿旧节点)：          [D] ◀── [E]  (失去任何分支指针引用，30 天后被 GC 销毁。)
   ```

   Git 把你在 `D` 和 `E` 里做的代码修改抽出补丁，以 `F` 为新的亲爹，重新创建了两个哈希值完全不同的全新节点 `D'` 和 `E'`，然后把 `feature` 便签纸贴到了 `E'` 上，而原来的旧节点 `D` 和 `E` 就被原地抛弃了。（这也解释了为什么绝对不要对已经推送到公共远端、且别人也在上面接着写代码的公共分支做 `rebase`——因为你把旧节点扔了换成新哈希节点，别人的提交还认旧节点当爹，一合并就会出现两份一模一样的重复历史。）

### 3. `git cherry-pick`（外科手术式摘取单个提交）

场景：主线 `main` 分支已经往前狂奔迭代了 `C -> D -> E -> F` 一大堆尚未发布的新功能，突然在最新的提交 `X` 里发现并顺手修好了一个致命的线上 Bug；而线上的稳定发布分支 `release` 还停留在老版本 `B -> R1 -> R2`。
现在你只想把 `X` 这一个修 Bug 的提交单独移植到 `release` 分支上，不能把 `C/D/E/F` 那些半成品新功能带过去（所以绝不能用 `merge`）。

这时候就切到 `release` 分支，直接执行 `git cherry-pick <节点 X 的哈希值>`：

```text
main 分支：     [A] <-- [B] <-- [C] <-- [D] <-- [E] <-- [F] <-- [X (修好了某 Bug)]
                         \
release 分支：             [R1] <-- [R2] <-- [X' (单独把 X 的改动摘过来重放生成的新提交)]
```

底层本质：Git 抽出节点 `X` 相对于它父节点 `F` 的那份代码差异补丁（Diff），在 `release` 分支的末端 `R2` 上重新应用一遍，生成一个父节点为 `R2` 的全新提交节点 `X'`。
注意：从 `cherry-pick` 完成的那一秒起，`X` 和 `X'` 在 Git 的 DAG 图结构上没有任何血缘关系（只是默认沿用了相同的 Commit Message，工程上建议加 `-x` 参数，让 Git 自动在 `X'` 的提交说明末尾附上一行 `(cherry picked from commit xxx)` 留作人工溯源线索）。

## 四、多模块与多工作区进阶：`submodule`、`worktree` 与日常审阅工具

### 1. `git submodule`（在大仓库里嵌套引用另一个独立的 Git 子仓库）

当一个大项目需要引用另一个独立维护的 Git 仓库作为子目录（且支持多重嵌套）时，使用 `submodule` 的核心机制是“`.gitmodules` 配置文件 + `gitlink` 特殊指针”双轨配合：

1. `.gitmodules` 文件（普通文本文件，随代码一起提交）：
   只负责记录“这个子模块叫什么名字、放在哪个本地子目录路径下、去哪个远端 URL 下载它”——注意，`.gitmodules` 里面完全不记录子模块当前用的是哪一个具体版本（Commit）。
2. `gitlink`（父仓库树对象里记录的特殊条目）：
   父仓库并不会把子模块里的几百个源码文件存进自己的库里，而是在父仓库的 Git 树里，把子模块那个文件夹标记为一个特殊的 `gitlink` 条目，里面只存着一个 40 位的 Commit 哈希值（在 VS Code 提交更改列表或 `git diff` 里，你会看到子模块目录显示为 `Subproject commit <哈希>`）。
3. **克隆含子模块的仓库时的标准操作**：
   直接 `git clone` 父仓库下来时，子模块的文件夹里面默认是空的。必须执行初始化与递归拉取命令——它会先读 `.gitmodules` 去把子模块仓库下载下来，再读父仓库里的 `gitlink` 哈希值，把子模块精确 `checkout`（以 `Detached HEAD` 状态）到父仓库锁定的那一次 Commit 上：

   ```bash
   # 拉取并递归初始化所有层级的子模块
   git submodule update --init --recursive
   ```

### 2. `git worktree`（同一个仓库同时在多个文件夹检出不同分支干活）

平时开发最烦的一个场景是：你正在 `feature` 分支改代码改到一半（或者正在跑耗时半小时的编译/Agent 任务），突然线上出紧急 Bug 需要你切去 `hotfix` 分支改两行代码；或者你想让 两个 AI Agent 同时在同一个仓库的两个不同分支上并行写代码。
- 如果在同一个目录里强行 `git stash` + `git checkout`，不仅你正在编译的中间文件全乱了，另一个正在跑的 AI Agent 脚下的文件直接被换掉更是会当场错乱；
- 如果笨手笨脚地把整个仓库文件夹 `cp -r` 复制一份（或者重新 `git clone` 一份），两个文件夹里的 `.git` 数据库是彻底割裂的——你在 A 文件夹里新建的分支和提交，如果不推上远端再从 B 拉下来，B 文件夹里根本看不见。

官方正解就是 `git worktree`：它允许你在不复制底层 `.git` 对象数据库的前提下，为同一个本地仓库额外挂载出一个或多个平级的工作文件夹。

```bash
# 在当前仓库旁边的 ../my-repo-hotfix 路径下，基于 hotfix 分支（或加 -b 新建分支）额外挂载一个工作目录
git worktree add ../my-repo-hotfix hotfix

# 查看当前仓库总共挂了哪几个工作目录
git worktree list

# 干完活后移除附加的工作目录
git worktree remove ../my-repo-hotfix
```

`worktree` 的四个底层特性：
1. 共享同一个 `.git` 心脏，提交秒级互通：附加的 worktree 目录下也有一个 `.git`，但你打开一看会发现它不是文件夹，而是一个只有一行路径的文本指针文件，直接指回主仓库的 `.git/worktrees/xxx`。因为大家读写的是硬盘上同一份 Git 数据库，你在 A 目录里刚 `commit` 了一个节点，切到 B 目录敲 `git log` 或是 `cherry-pick` 当场 0 延迟立即可见，完全不需要经过远端服务器中转。
2. 各自拥有独立的 `HEAD`、独立的暂存区（Index）和独立的工作区文件。
3. **分支独占保护锁**：同一个 Branch 分支，在同一时刻最多只能被一个 worktree 检出占用（防止两个目录同时在同一个分支名下提交把指针搞乱）。
4. 理论上所有挂载在同一个 `.git` 数据库上的 working tree 在操作上都是平权的。

### 3. 日常状态审阅四剑客与 GUI 看图小技巧

最后用四句话分清日常看状态的四个命令，以及 GUI 面板里的两个实用按钮：
- **`git status`**：只看当前工作区和暂存区的摘要清单（告诉你哪几个文件被改了、哪几个是新建未跟踪的，但不显示具体改了哪一行代码）。
- **`git diff`**：看具体每一行代码从什么改成了什么（在 VS Code 等 GUI 里看很多文件的 Diff 时，右上角可以切换“以列表形式查看（Flat List）”还是“以目录树形式查看（Tree View）”——只改了两三个文件用列表最直观，如果一次重构改了三十几个跨模块文件，切到目录树视图能直接理清模块分布）。
- **`git log`**：顺着当前分支往回看 DAG 提交历史图（当仓库有几千条提交、你在图形历史列表里滚得太远迷路时，点一下面板上的“🎯 转到当前历史记录项 / Jump to HEAD”按钮，就能直接滚回并高亮当前 `HEAD` 所在的那个节点）。
- **`git reflog`**：看你这台电脑本地的 `HEAD` 和分支指针过去每一步是怎么跳过来的（本地操作黑匣子，专门用来找回被 `reset --hard`、错误 `rebase` 或 `Detached HEAD` 弄丢的孤儿提交）。
