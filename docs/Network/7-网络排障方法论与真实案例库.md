# 网络排障方法论与真实案例库

遇到棘手网络问题时容易越查越乱，通常不是因为工具用得少，而是因为**没有按协议栈分层隔离，一边猜一边同时改好几处配置**。

这一篇先总结一套可直接照着执行的分层排障清单，再用四个完整经历过的真实案例（按“现象 → 拓扑与排查经过 → 根因 → 解法 → 知识点串联”）把前面所有底层原理融会贯通。

---

## 一、分层排障方法论：如何避免陷入盲猜

### 两条核心纪律

1. **自底向上或自顶向下逐层切割，不跳步猜根因**
   - 没确认流量从哪张网卡出去之前，不要急着调应用参数；
   - 没抓包看到真实报文之前，不要把一切卡顿都归咎于“双层 TCP”或“服务器不行”。
2. **对照组 + 单变量证伪（A/B 测试）**
   - 优先找一条“环境相近但表现正常”的链路作对照（例如同内网机器 vs 跨公网机器、UDP 直连 vs TCP 中继、绕开代理直连 vs 经代理）；
   - 每次只改一个开关（如关闭某个内核参数），并用日志或抓包明确证伪或证实。

### 分层排障命令速查

| 排查层级 | 要回答的核心问题 | 常用验证命令 |
| :--- | :--- | :--- |
| **L7 代理与环境** | 请求是不是被僵尸代理变量或系统代理拐走了？ | `env \| grep -i proxy`、`scutil --proxy`（macOS） |
| **L7 证书与服务** | DNS 解析对不对？TLS 证书链完整吗？反代日志报错了吗？ | `curl -v`、`openssl s_client -connect host:443 -servername host -showcerts`、查看 Nginx `error.log` |
| **L3 路由与隧道** | 包实际从哪张网卡发出？VPN 走直连还是中继？ | `ip route get <IP>`（Linux）、`route get <IP>`（macOS）、`route print`（Windows）、`tailscale ping <节点>` |
| **L4 内核状态** | 发送/接收队列堵没堵？有没有持续重传或 SACK？ | `ss -tnpi 'dst <IP>'`（Linux）、`sysctl net.inet.tcp`（macOS） |
| **L4 线缆抓包** | 线上到底发了什么包、缺了哪一段、谁先停发的？ | `sudo tcpdump -i <网卡> -nn -vvv -S 'host <IP> and tcp port <端口>'` |

## 二、案例一：家庭 Mac 经 Tailscale DERP 跑 SSH 频繁假死

这是一次几乎把 **NAT 拓扑、L3 隧道封装、MTU/PMTUD、TLS 证书链、Nginx 反代长连接、TCP SACK/RACK 状态机、网卡 TSO 卸载、ProxyJump 与 Mosh** 全部考了一遍的典型综合故障。

### 1. 起因与核心现象

- **故障机器**：家里的一台 Mac（`pro`，Tailscale IP `100.64.0.36`，`macOS 27.2.1 / xnu-13432.41.4`）。
- **核心症状**：Tailscale 进程没有崩溃，本机正常上网，但从公司 Linux 机器（`work`，`100.64.0.40`）无法 SSH 连进来，正在使用的 SSH 会话也会突然卡住“假死”。
- **触发规律**：空闲挂机可稳定保持 12 小时以上不死；但只要通过 SSH 连续上传或输出较多流量（约 10–20MB / 10 分钟），每 10~15 分钟就会稳定复发一次。
- **对照组与临时恢复**：
  - 公司内网的 `work` ↔ `air`（`100.64.0.38`）从来不假死，唯独家里这台 `pro` 频繁假死；
  - 退出重开 Tailscale，或者执行 `break-derp-conns` 强行换一条新的 DERP TCP 连接，1 秒内立刻恢复正常。

### 2. 网络拓扑拆解：为什么唯独 `pro` 踩坑？

基础设施采用自建 Headscale + DERP：
- **上海核心节点（`aliyun-sh`，`100.64.0.6`）**：四合一节点，运行 `headscale`、`headplane`、`headscale-derp`（DERP 194 cnsh，~11ms）以及 Nginx Proxy Manager；
- **北京热备节点（`aliyun-bj`，`100.64.0.39`）**：独立 DERP（193 cnbj，~30ms）+ 第二台 STUN 节点。

两端 NAT 实测结果：
- **公司 `work`**：对称 NAT（`MappingVariesByDestIP: true`），且无法控制公司路由器；
- **家里 `pro`**：双层 NAT——`pro (192.168.0.195)` → 二级路由器（`192.168.0.1`，WAN `192.168.1.112`）→ 运营商光猫（`192.168.1.1`，下挂多台路由无法改桥接且无超管密码）。虽然二级路由本身表现为锥形 NAT，但双层防火墙拦截外部入站包。

对照三条实际链路，差异一目了然：
1. **`work ↔ air`**：同在公司内网 → 走 UDP 直连 → 从不经过 DERP TCP → **永不假死**；
2. **`pro ↔ aliyun-sh` / `work ↔ aliyun-sh`**：上海节点有公网 IP → 两端到上海均为 8–10ms WireGuard UDP 直连；
3. **`work ↔ pro`**：对称 NAT + 未放行双层 NAT → P2P 打洞 100% 失败 → 回退到上海 DERP 443 的单条长连接 TCP（形成“内层 SSH TCP 套 外层 DERP TCP”）→ **100% 命中故障**。

### 3. 外围排雷：修掉真实隐患，并逐一证伪干扰项

在锁定最终真凶前，先顺藤摸瓜排查并清理了周边所有真实隐患与疑似嫌疑：

- **修复的真实外围问题**：
  1. **上海节点 Nginx Proxy Manager**：原 80 默认站点存在 `/favicon.ico → 127.0.0.1:80` 无限自循环，每隔 10~40 分钟把默认 `512` 个 `worker_connections` 打爆踢人，并残留 8 个历史僵尸 worker；同时 DERP 反代未关 `proxy_buffering` 且超时仅 `90s`。修复为默认站点 `return 444`、`worker_connections 4096`、`worker_shutdown_timeout 30s`、DERP 反代加 `proxy_buffering off` + `86400s` 超时，此后反代错误日志连续保持 0 报错。
  2. **北京热备 DERP 节点**：原停用原因是证书缺中间链（导致 Linux 端 `work` 报错 `curl 60`）且临近过期。改为 `acme.sh` 签发 EC-256 完整 4 级链 + 自动续签重载钩子，重新启用热备。
  3. **家里二级路由器**：开启 UPnP/PCP（因前级光猫双层 NAT 暂无法单独打通 P2P，先保持就绪）。
- **通过实测证伪的非原因**：
  1. **本机代理（v2rayN / Xray `127.0.0.1:10808`）**：Tailscale 流量直走物理网卡 `en0`，完全不经过本地代理；
  2. **链路 MTU（宽带 `1500 → 1492`）**：抓包确认全链路 TCP 协商出 `mss = 1388`，整包 ≤ 1440 字节，远未触及 1492 上限；
  3. **macOS `pmtud_blackhole_detection`**：通过开关 A/B 实测，开启时抓包缺口为 `500B`，关闭后缺口变为 `1388B / 1211B`，两种状态下均照样复发，彻底排除 PMTUD 黑洞。

### 4. 现场抓包锁定核心真凶

在一次故障发生后**不重启 Tailscale、保留现场**，直接在上海服务端执行 `ss -tnpi` + `tcpdump -vvv -S`（累计捕获 9 次真实复发样本），拿到了确凿证据——真凶是 **`macOS 27.2.1`（XNU 内核）的 TCP 发送端状态机死锁**：

1. **抓包铁证**：
   - 每次 `pro` 经由 DERP TCP 向上上传 10–80MB 后，只要公网丢掉 1 个包，上海服务端立刻回发 **SACK** 报告缺口；
   - 紧接着 `pro` 本机内核进入**单向发送死锁**：
     - **上海 → `pro` 下行一直完全正常**：`pro` 正常回 ACK，接收窗口 `win` 也会随应用层读空从 `2028` 恢复到 `2048`（证明包确实由本机内核正常发出）；
     - **`pro` → 上海上行永久 `0` 字节**：既不重传 SACK 报出的缺失段，也不触发 RTO 超时断连（实测僵死超过 21 分钟），反而以 `60ms → 120ms → 240ms` 指数退避反复发送 `seq = ack - 1, length 0, flags [none]` 的空探针。
2. **为什么 Tailscale 自己察觉不到断线？**
   - 下行方向仍在源源不断收到上海发来的控制信令和对端心跳，所以应用层读超时永远被重置；
   - 上行方向写入内核发送队列时起初不报错，直到队列彻底塞满开始静默丢弃（实测内部指标 `magicsock_send_derp_dropped` 飙升到 `25,423`），Tailscale 始终误判这条长连接健康。

### 5. 关键辨析：根因是“双层 TCP（TCP Meltdown）”吗？

**不是直接根因。** 从协议栈行为上两者截然不同：
- **经典双层 TCP 问题（TCP Meltdown）**：公网丢包后，外层 TCP 触发重传并缩小窗口，内层 TCP 误判超时也跟着重传并砍半窗口，结果是内外两层疯狂重传、延迟飙升，最终往往因达到最大重传次数（RTO）而断连。
- **本次抓包实际行为**：外层 TCP 收到 SACK 缺口后，**永久拒绝重传且永不超时**，死循环在 `length 0, flags [none]` 空探针里。因为外层 XNU 协议栈对载荷完全盲视，在它眼里发往上海 443 的只是一串普通 TLS 字节流，根本不知道里面套着 SSH TCP——这是标准的**单层内核协议栈状态机缺陷**。

**那“走 DERP（双层 TCP）”扮演了什么角色？它是触发器与故障放大器**：
1. 被迫引入了经物理网卡 `en0` 的公网长连接外层 TCP（`work ↔ air` 走 UDP 直连，压根不碰外层 TCP 状态机）；
2. 放大爆炸半径：Tailscale 把经该 DERP 的全部流量复用到同一条 TCP 443 长连接上，这条连接单向死锁直接拖垮整个节点的双向通信；
3. 掩盖故障：下行存活掩盖上行僵死，阻止应用层触发自愈重连。

### 6. 兜底保护与阶梯式治本路线

**已部署的兜底自愈（看门狗）**：
- 编写直连 Tailscale LocalAPI 的看门狗脚本（通过读取 `/Library/Tailscale/ipnport` + `sameuserproof` 走本地 HTTP API，绕过 `launchd` 下调用 Tailscale CLI 报错的问题），挂成开机自启 `LaunchAgent`；
- 每 10 秒探测节点连通性（多对端交叉验证 + 外网存活校验），连续 2 次超时即自动抓包留证并调用 `break-derp-conns` 在 1 秒内换新连接拉活（冷却 60 秒）。
- 效果：彻底杜绝“出门在外被锁死”，但高频 SSH 时仍有 ~20–25 秒卡顿，属于治标兜底。

**按验证成本从低到高的治本三步走**：

1. **第一步（最低成本验证内核算法）：关闭 `net.inet.tcp.rack = 0`**
   - 验证死锁是否由苹果 XNU 的 RACK 丢包恢复算法在 SACK 边界触发（注意：`sysctl` 修改只对**新建 TCP 连接**生效，必须刷新现有 DERP 连接后再做高流量压测）。若复发次数直接归零，做开机持久化即彻底根治。
2. **第二步（绕开外层 DERP TCP）：`ProxyJump` 经上海中转**
   - 利用已实测畅通的两段链路：`work → <上海公网IP>`（公网原生 10ms）+ `<上海公网IP> → pro`（WireGuard UDP 直连 8ms），总延迟仅 ~18ms，彻底消灭外层 DERP TCP。
   - **提前预判的逻辑分叉与价值**：
     - 风险：WireGuard UDP 隧道内层跑的 SSH 依然是同一台 `pro` 的 XNU TCP，若纯算法 Bug 仍可能在 UDP 丢包触发 SACK 时偶发；
     - 两个关键工程变量会改变：① **网卡卸载路径不同**——外层 DERP 走开启硬件 TSO 的物理网卡 `en0`，而内层 SSH 走无硬件 TSO 的虚拟网卡 `utun`（BSD/XNU 历史上不少发送端卡死正是 RACK/SACK 与物理网卡 TSO/驱动交互共同触发的）；② **故障隔离**——即便单条 SSH 偶发死锁，也不再拖垮整个 Tailscale 节点。
   - **顺手证伪实验**：切 ProxyJump 前，也可直接从 `pro` 绕开 Tailscale 向上海公网 IP 跑一次纯单层 TCP 上传压测（如 `scp` 或 `iperf3`），一步就能把“是否与 DERP / 双层封装有关”彻底证伪。
3. **第三步（终极物理免疫）：Mosh 或打通 P2P**
   - 改用 **Mosh** 让终端交互全程走纯 UDP（0 字节 TCP），物理层面彻底绕开内核 TCP Bug；或后续获取光猫超管权限配置 DMZ 打通直连，或等待 macOS 系统更新修复 XNU TCP 状态机。

### 7. 本案例串联的底层知识点

| 排障环节 | 对应的底层基本功 |
| :--- | :--- |
| 为什么 `work ↔ pro` 必然走 DERP | 对称 NAT + 未放行双层 NAT 导致 UDP 打洞必败 |
| 为什么排除 `en0 MTU 1492` 与 `500B` 缺口 | MTU / MSS 换算与 `pmtud_blackhole_detection` 兜底探测机制 |
| 为什么修完 Nginx 和北京 DERP 才方便继续查 | Nginx `proxy_buffering off` / 长超时 / `444` 防自循环 + TLS 完整证书链 |
| 为什么能从抓包排除“双层 TCP 雪崩” | 载荷盲视、SACK / RACK 丢包恢复、空探针与 TCP Meltdown 行为差异 |
| 为什么 `ProxyJump` 换到 `utun` 仍具验证价值 | L3 封装 vs 分段跳板、物理网卡 TSO 硬件卸载 vs 虚拟网卡无 TSO 路径 |

## 三、案例二：海外 VPS 线路劣化、UDP 阻断与风控死锁教训

### 1. 起因与排查经过

1. 最初使用一台普通海外 VPS，不同地点、不同运营商连接体验分化明显。
2. 家里电脑使用 VLESS（TCP）连接时，TCP 握手频繁失败、持续卡顿；升级到基于 QUIC/UDP 的 Hysteria2 后短期速度极佳，但**两周后整台 VPS 的回程 UDP 全端口被阻断**，被迫退回 VLESS。
3. 随后 TCP 可用性进一步恶化，处于半死不活状态。通过多机多网连通性测试，并连续新购多台 VPS 测速选优，发现新机刚开时略好，但很快同样劣化。

### 2. 根因结论

- **物理骨干网拥塞无法靠换协议解决**：家庭电信宽带默认出境走 **163 骨干网**，国际出口严重拥塞。更换加密协议只能改善协议特征伪装，无法提高物理链路可用度；即便换用 AWS、Azure 等大厂常规线路，只要依然落回普通骨干网，照样卡顿。
- **多运营商访问需三网优化或专线**：跨家宽、公司网、蜂窝网多端使用时，只针对单一运营商优化（如单电信 CN2 GIA）会导致其他网络绕路；真正稳定的解法是三网优化线路或专线中转。

### 3. 血泪换来的四条运维生存铁律

代理或公网入口彻底失联时，最怕陷入“需要代理才能修代理”的死锁，日常基建必须提前留好后路：

1. **优先选择国内 IP 可直连管理面板的机房**：避免服务器挂了之后连控制面板都打不开，陷入鸡生蛋、蛋生鸡的死局。
2. **VPS 账号绑定国内直连可达的邮箱（如 Outlook），不要只绑 Gmail**：
   - 主力 VPS 挂掉后，换备用线路或国内直连登录 VPS 面板必然导致登录 IP 变化，从而触发风控要求邮箱验证码；
   - 如果绑定 Gmail，为了收验证码又得换备用机场登录 Google，同样因 IP 变化触发 Google 手机号风控，再叠加低质量共享 IP，极易死循环在 Cloudflare 与风控验证里寸步难行。
3. **部署脚本与排障工具链必须保留国内直连可用的 AI / 诊断兜底**：梯子失效瞬间，海外模型接口全线失联，必须有国内直连可达的辅助手段来快速定位与修复。
4. **排障前立刻清理僵尸代理环境，并用手机热点做最终兜底**：
   - 一旦确认节点失效，第一时间把代理客户端切到 **“清除系统代理”**，并清空终端里的 `http_proxy` / `all_proxy` 环境变量，避免测新 VPS 连通性时被死端口误导；
   - 紧急情况下直接开手机热点切换运营商出口，往往能最快破局。

## 四、案例三：公司内网域名与 Tailscale 网段在代理下报 `502` / 超时

### 1. 现象

- 公司内网有自建 DNS，把内部明文域名（HTTP / WebSocket / OpenAI-compatible 接口）解析到私有 IP；同时本机运行 Tailscale（`100.64.0.x`）与桌面代理软件（V2RayN 白名单模式）。
- 现象分裂：`ssh 100.64.0.x` 始终丝滑直连；但终端 CLI 或 Python 访问 `http://100.64.0.22:3000` 和部分公司内网接口却卡死超时或返回 `502`。

### 2. 根因拆解（三层叠加）

1. **应用层截胡早于内核路由**：`ssh` 不读 `http_proxy`，直接命中内核 `tailscale0` 路由；HTTP 客户端受环境变量引导，在 L7 就先发往了 `127.0.0.1:10808`。
2. **`100.64.0.0/10` 漏过默认私网规则 + 客户端 CIDR 盲区**：Tailscale 网段属于 RFC 6598（CGNAT），不在白名单默认的 `geoip:private` 中，因此被错送去远端公网节点导致 `502`；而 Python `urllib` 自身又不支持 `NO_PROXY` 里的 CIDR 写法，单配环境变量兜不住。
3. **代理内部 DNS 查不到公司内网域名 + 规则语法失效**：流量进了代理内核后，默认走公网 `DirectDNS`（如 `119.29.29.29`）且关闭了系统 hosts，查不到内部域名；同时在路由规则里误把 `domain:company.com` 写成了无效的 `*.company.com`。

### 3. 标准解法

- **双保险分流**：同时配置 `no_proxy` / `NO_PROXY`（写 `.company.com`）与代理软件自身的 `direct` 规则（加入 `100.64.0.0/10` 和 `domain:company.com`）；
- **DNS 职责单一**：给内网域名配置内部自定义 DNS（或确保绕过代理直走系统解析），并关闭 Tailscale 接管全局内部 DNS，彻底消除多套 DNS 冲突。

## 五、案例四：同办公网两台机器连同一海外节点，一台全线超时、另一台畅通

### 1. 现象

- 同处公司办公网同一子网（`/23`）的两台开发机（Linux 工作机与 MacBook），均运行相同代理客户端、连接**同一个海外 VPS 节点**。
- 某几分钟内出现诡异分裂：
  - **Linux 工作机**：国内白名单直连完全正常，但所有走代理的海外请求在代理 `CONNECT 200` 之后卡死超时；
  - **MacBook 对照组**：同一时刻走同一个海外 VPS 节点却完全畅通；
  - 几分钟后，未重启代理进程也未改任何配置，Linux 工作机自动恢复正常。

### 2. 拓扑实测与对照组验证

办公网与机房网段的真实出口结构：

1. **办公网段：双线运营商 + L3 `(源 IP, 目的 IP)` 哈希分流**
   - 办公网出口挂着一条**电信**线路和一条**移动**线路；
   - 实测发现它**不是**按目标运营商路由表分流，也**不是**每次新建连接随机轮询，而是典型的 **三层 `(源 IP, 目的 IP)` 哈希负载均衡**：
     - 同一台机器连续多次访问同一个公网目标 IP，出口 100% 稳定在同一运营商；
     - 同一台机器访问同一个公网 `/24` 下的两个不同 A 记录 IP，一个稳定落到电信、另一个稳定落到移动；
     - 换另一台办公网机器（源 IP 改变），访问相同的目标 IP 时哈希结果发生变化，落到了另一条运营商出口。
2. **公司内服务器/机房网段：固定单出口**
   - 不同机房网段各自绑定固定单条运营商出口（有的复用公司电信专线，有的走独立移动专线），无论国内国外或重复请求均不切换。

### 3. 根因锁定

对两台办公网机器到同一个海外 VPS 做路由追踪（`traceroute`），第 3 跳直接一锤定音：
- **Linux 工作机 → 该海外 VPS**：经公司网关哈希到了**电信出海出口**；
- **MacBook → 同一海外 VPS**：因为源 IP 不同，被哈希到了**移动出海出口**。

故障那几分钟其实是**电信出海方向到该海外机房的短暂抖动/丢包**，导致走电信的 Linux 工作机代理建连后卡死超时，而走移动的 MacBook 完全不受影响；线路恢复后，Linux 工作机无需任何操作即自动恢复。
