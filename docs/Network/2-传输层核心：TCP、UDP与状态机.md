# 传输层核心：TCP、UDP 与状态机

网络层（L3）的 IP 协议只负责把数据包尽力送到目标主机，既不管包会不会丢、会不会乱序，也不管送到主机后交给哪个程序。**传输层（L4）** 在 IP 之上补齐了两件事：用**端口号**把数据精准交给对应进程，并按业务需要提供**可靠的字节流（TCP）**或**轻量的报文传输（UDP）**。

这一篇从连接建立与关闭、滑动窗口与拥塞控制讲起，一直落到真实内核里的丢包恢复算法（SACK / RACK）、硬件卸载（TSO）以及如何直接读懂 `tcpdump` 抓包输出。

---

## 一、TCP 与 UDP 的核心差异

| 维度 | TCP | UDP |
| :--- | :--- | :--- |
| **连接状态** | 面向连接（通信前必须握手，维护复杂状态机） | 无连接（直接发包，无状态） |
| **数据形态** | **面向字节流**：应用写入的一段数据可能被拆分或合并发送，无天然消息边界 | **面向报文**：应用交下去一个包就按一个包发，保留边界 |
| **可靠性** | 可靠（靠序列号、确认、重传、校验保证应用层最终拿到完整有序的字节） | 不可靠（尽力交付，丢了不管、乱序不管） |
| **通信模型** | 仅支持 1 对 1（单播） | 支持单播、多播、广播 |
| **头部开销** | 至少 **20 字节**，带选项最多 **60 字节** | 固定 **8 字节** |
| **典型上层协议** | HTTP/1.1、HTTP/2、SSH、FTP/SFTP | DNS、QUIC（HTTP/3）、WireGuard、Mosh |

> 理解“可靠”的准确含义：TCP 的可靠**不是**指网络里每个包都不会丢，而是指通过确认、重传与排序机制，**确保接收端应用层最终读到的是完整、无差错、按顺序排列的字节流**。

## 二、TCP 头部关键字段与状态机基础

看懂一切 TCP 行为（以及后面的抓包输出），核心只需要盯住头部里的几个字段：

- **源端口 / 目的端口**：与 IP 一起构成唯一标识一条 TCP 连接的**四元组**（源 IP、源端口、目的 IP、目的端口）。
- **序列号（`seq`）**：本报文段所携带数据中**第一个字节的编号**。
- **确认号（`ack`）**：期望对方**下一次发送的第一个字节编号**（意味着 `ack - 1` 及之前的所有字节我全都按序收齐了）。
- **控制标志位（Flags）**：
  - `SYN`：请求建立连接并同步初始序列号（ISN）。
  - `ACK`：表示确认号字段有效（握手之后几乎所有包都带 `ACK`）。
  - `PSH`：提示接收方内核尽快把缓冲区数据推给应用层，别攒着。
  - `FIN`：本端数据已发完，请求优雅关闭这个方向的发送通道。
  - `RST`：强制复位/立即中断连接（异常关闭，不走四次挥手）。
- **接收窗口（`win`）**：接收方告诉发送方“我现在接收缓冲区还剩多少空闲空间”，用于流量控制。
- **选项（Options）**：扩展字段，常见的有 `MSS`、时间戳 `TS`、窗口扩大因子 `wscale`、以及 `SACK`。

## 三、三次握手与四次挥手

### 1. 三次握手（建立全双工连接）

服务端持续监听端口，由客户端主动发起连接：

1. **第一次握手（客户端 → 服务端）：`SYN`**
   - 客户端发送 `SYN` 报文，携带随机生成的初始序列号（ISN）`seq = x`，进入 **`SYN_SENT`** 状态。
   - 视角变化：客户端只知道自己能发；服务端收到后确认“客户端能发、自己能收”。
2. **第二次握手（服务端 → 客户端）：`SYN + ACK`**
   - 服务端同意建立连接，回复 `SYN`（携带自己的初始序列号 `seq = y`）+ `ACK`（`ack = x + 1`），进入 **`SYN_RECV`** 状态。
   - 视角变化：客户端收到后，从自己的视角已经确认“双方都能收能发”；但**服务端还不知道客户端到底能不能收到自己发的包**。
3. **第三次握手（客户端 → 服务端）：`ACK`**
   - 客户端回复 `ACK`（`ack = y + 1`），进入 **`ESTABLISHED`**；服务端收到后也进入 **`ESTABLISHED`**。
   - 视角变化：服务端终于确认“客户端能收”，双向通信正式就绪。

**为什么不能两次握手？**
- 核心是双方必须各自确认“自己和对方都能收能发”；
- 此外，如果一个在网络里迷路很久的旧 `SYN` 突然到达服务端，三次握手下客户端收到莫名其妙的 `SYN+ACK` 可以直接发 `RST` 拒绝，避免服务端白白建立一条幽灵连接浪费资源。

### 2. 四次挥手（关闭全双工连接）

关闭连接是对称的，任何一方都可以先提出（假设客户端先发起）：

1. **客户端 → 服务端：`FIN`（`seq = u`）**
   - 客户端表示“我这边没数据要发了”，进入 **`FIN_WAIT_1`**。
2. **服务端 → 客户端：`ACK`（`ack = u + 1`）**
   - 服务端先回复“收到你的关闭请求，但我这边可能还有没发完的数据，稍等”，进入 **`CLOSE_WAIT`**；客户端收到后进入 **`FIN_WAIT_2`**。
   - 此时连接处于**半关闭（Half-Close）**状态：客户端 → 服务端方向已关闭，但服务端 → 客户端方向依然可以继续发数据。
3. **服务端 → 客户端：`FIN`（`seq = y`）**
   - 服务端把剩余数据全部发完后，发出 `FIN`，进入 **`LAST_ACK`**。
4. **客户端 → 服务端：`ACK`（`ack = y + 1`）**
   - 客户端回复最后一个 `ACK` 后进入 **`TIME_WAIT`**，服务端收到后直接 **`CLOSED`**；
   - 客户端等待 **`2MSL`**（两倍最大报文段生存时间）后才彻底进入 **`CLOSED`**。

**为什么主动关闭方必须等 `TIME_WAIT`（2MSL）？**
- 确认阶段同样可能丢包：客户端发出第 4 次 `ACK` 后，不确定服务端有没有收到。如果这个 `ACK` 丢了，服务端会超时重发第 3 次的 `FIN`，客户端在 `TIME_WAIT` 期间还能接住并补发 `ACK`；若 `2MSL` 内没再听到服务端重发 `FIN`，就说明对方已经安稳关闭。
- 同时保证这条旧连接残留在网络里的延迟数据包彻底消散，不会污染稍后复用同一端口的新连接。

## 四、流量控制与拥塞控制

TCP 发送数据时，发多快受两个窗口共同约束：**实际发送上限 = `min(接收窗口 rwnd, 拥塞窗口 cwnd)`**。

### 1. 流量控制（面向对端：防止把接收方打爆）

接收方的内存缓冲区和处理速度有限，通过每次回复报文里的 **`win`（接收窗口 `rwnd`）** 字段，动态告诉发送方自己当前还能接多少字节。

站在发送方的字节流视角，所有数据被划分为四段：

```text
[ 1. 已发送且已确认 ] | [ 2. 已发送但未确认 ] [ 3. 窗口内允许立即发送 ] | [ 4. 窗口外暂不允许发送 ]
                      |<---------------- 发送窗口大小 ---------------->|
```

随着新的 `ACK` 和 `win` 不断回来，发送窗口向右滑动（即**滑动窗口**）。

**零窗口与探针（Zero Window Probe）**：
- 如果接收方应用层来不及读数据，缓冲区被塞满，就会通告 `win = 0`，发送方必须暂停发送。
- 之后接收方读空缓冲区会发一个“窗口更新”包，但这个更新包本身可能丢在路上导致双方死等。为了打破僵局，发送方会定期发极小的**零窗口探针**试探窗口是否重新打开。
- 类似地，TCP 还存在 **Keepalive 保活探针**（常表现为 `seq = ack - 1, length 0`）：故意发一个已经确认过的旧序号空包，正常对端收到后会立刻回复当前的 `ACK` 以证明连接仍存活。正常情况下这类空探针只按保活间隔触发，或探测到窗口恢复后便恢复正常数据发送。

### 2. 拥塞控制（面向整条网络：防止把中间路由器打爆）

即使接收方胃口很大，中间链路带宽和路由器队列也可能发生拥堵。发送方在本地维护一个**拥塞窗口（`cwnd`）**来探测网络承载上限：

- **经典基于丢包的演进（Reno / CUBIC）**：
  1. **慢开始（Slow Start）**：初始 `cwnd` 较小，每经过一个 RTT（往返时间）翻倍增长（指数增长），直到达到慢开始门限 `ssthresh`。
  2. **拥塞避免（Congestion Avoidance）**：超过 `ssthresh` 后转为线性增长（每个 RTT 加 1 个 MSS），缓慢试探带宽天花板。
  3. **发生丢包时的回退**：
     - 轻度丢包（触发快重传）：进入**快恢复（Fast Recovery）**，`ssthresh` 减半、`cwnd` 降到新门限附近继续线性增长（Linux 默认的 **CUBIC** 算法在此基础上用三次函数更快爬回之前的带宽峰值）。
     - 严重丢包（触发 RTO 超时）：判定网络极度拥塞，`ssthresh` 减半，`cwnd` 直接打回初始值重新慢开始。
- **现代基于带宽和延迟的算法（BBR）**：
  - 传统丢包派算法的缺陷是“非要把路由器队列塞满直到丢包才知道减速”，在高延迟、偶发随机丢包的跨国公网链路上很容易误把随机丢包当成拥堵，导致速度断崖式暴跌。
  - Google 提出的 **BBR** 不再把丢包当唯一拥塞信号，而是持续测量链路的**最大瓶颈带宽（BtlBw）**和**最小物理往返延迟（RTprop）**，按估算出的真实速率平滑发包（Pacing），在弱网和长肥管道（高带宽高延迟链路）上吞吐显著优于 CUBIC。

## 五、丢包恢复机制的演进：RTO → 快重传 → SACK → RACK

这是教科书里最容易一笔带过、但真实排障现场最常撞见的一块核心状态机。每一代机制都是为了解决上一代的痛点：

### 1. RTO（Retransmission Timeout，超时重传）

- **机制**：最原始、也是最终的兜底机制。每发出一批数据，发送方基于历史 RTT 及其抖动动态算出一个超时时间 **RTO**。如果定时器到期仍未收到对应 `ACK`，就判定丢包并重传。
- **指数退避**：如果重传后继续超时，RTO 会成倍拉长（例如 `200ms → 400ms → 800ms → 1.6s...`），直到达到系统设定的最大重传次数后放弃并断开连接。
- **痛点**：等待时间太长。即便只丢了 1 个包，也要干等一个完整的 RTO 周期，链路吞吐瞬间归零。

### 2. 快重传（Fast Retransmit）

- **机制**：不等定时器超时，而是靠**重复确认（Duplicate ACK）**提前感知丢包。
- 假设发送方连续发了分段 `1, 2, 3, 4, 5`，其中 **`2` 丢了**：
  - 接收方收到 `1` → 回 `ack=2`；
  - 收到 `3`（发现缺 `2`）→ 只能继续回 `ack=2`（第 1 个 Dup ACK）；
  - 收到 `4` → 回 `ack=2`（第 2 个 Dup ACK）；
  - 收到 `5` → 回 `ack=2`（第 3 个 Dup ACK）。
- 发送方连续收到 **3 个重复 ACK**，立刻明白 `2` 大概率丢了，不等 RTO 直接重传 `2`。
- **痛点**：传统的累计确认（Cumulative ACK）信息量太少，只告诉发送方“连续收到的位置停在 `2`”，发送方**并不知道后面 `3, 4, 5` 到底收到了哪些**。如果同一轮里同时丢了 `2` 和 `4`，发包方要么保守地每轮只重传一个（拖慢恢复），要么把 `2, 3, 4, 5` 全重传一遍（浪费带宽）。

### 3. SACK（Selective Acknowledgment，选择性确认）

- **机制**：在 TCP 头部选项里增加一块列表，让接收方把**“已经乱序收到的完整区间”**明明白白汇报给发送方。
- 沿用上面的例子，如果 `2` 和 `4` 丢了、`3` 和 `5` 到了，接收方回复的包里会带上：
  - `ack = 2`（我连续收齐到 2 之前）
  - `SACK = [3], [5]`（但 3 和 5 我已经替你存好了，不用重发）
- **效果**：发送方拿到 SACK 块后，在本地记分板（Scoreboard）上一目了然，精准只重传缺口里的 `2` 和 `4`。

### 4. RACK（Recent Acknowledgment，基于时间的最新丢包检测）

- **痛点**：快重传依赖“攒够 3 个重复 ACK”这个计数阈值，但在两种常见场景下会失效：
  1. **尾部丢包 / 小流量交互**：比如 SSH 敲命令或请求末尾总共只发了 1~2 个包，后面压根没有新包了，永远凑不齐 3 个重复 ACK，只能傻等漫长的 RTO；
  2. **网络路径乱序**：多路径路由导致后发的包比先发的包早到，容易误触发 3 个 Dup ACK 导致白白重传和窗口砍半。
- **核心思路**：**不再数“收到了几个后续包”，而是改用“时间”判断丢包**。
  - 发送方记录每个包发出的精确时间戳。只要一个**更晚发出**的包已经被确认（通过 ACK 或 SACK），并且经过一个短暂的乱序容忍窗口（Reordering Window）后，**更早发出**的包依然没被确认，RACK 就判定那个早发的包已经丢了，直接触发重传（通常配合 **TLP 尾部丢包探测** 处理彻底没有后续包的情况）。
- **工程现状**：RACK-TLP（RFC 8985）已成为现代操作系统（Linux、FreeBSD、macOS XNU）的默认或核心丢包恢复机制（例如 macOS 可通过 `sysctl net.inet.tcp.rack` 查看或开关）。不过相比老式计数重传，RACK 与 SACK 记分板交互的状态机逻辑要复杂得多，边界情况下更容易暴露内核协议栈自身的 Bug。

```text
演进主线：
RTO (死等超时，最慢但最终兜底)
  → 快重传 (数 3 个重复 ACK 提前发现单个丢包)
    → SACK (报出已收区间，精准补传多个缺口)
      → RACK (改用时间戳判定丢包，兼顾乱序容忍与小流量快速恢复)
```

## 六、两个容易混淆的性能陷阱：HOL Blocking 与 TCP Meltdown

在分析代理、VPN 和多路复用协议时，这两个词经常被混为一谈，但它们的成因完全不同：

### 1. HOL Blocking（Head-of-Line Blocking，队头阻塞）

- **发生场景**：**单条 TCP 连接**里同时承载多个相互独立的逻辑请求（多路复用），例如 HTTP/2 在一条 TCP 上并发传 JS、CSS、图片，或者某些代理客户端把多个网页连接复用到同一条公网 TCP 隧道里。
- **成因**：TCP 保证的是整条连接的**严格全局有序**。假设请求 A 的第 1 个包在公网上丢了，而请求 B 和 C 的包已经完好到达接收端内核，但因为 TCP 协议栈看不到里面分了 A/B/C 三个流，它只能死死扣住 B 和 C 的数据不交给应用层，直到 A 的那 1 个包重传成功。**一个包卡住，整条连接上的所有并发流一起干等**。

### 2. TCP Meltdown（双层 TCP 拥塞雪崩）

- **发生场景**：**真正的 TCP over TCP**——一条端到端的内层 TCP 连接，被完整打包进另一条同样跨公网的外层 TCP 隧道里（典型如走 TCP 模式的 L3 VPN）。
- **成因**：公网上同时跑着**两套互不知情的 TCP 状态机**。一旦公网轻微丢包：
  1. 外层 TCP 暂停向上交付并开始重传；
  2. 内层 TCP 对外层正在重传一无所知，只看到延迟突然飙升，于是误判超时，触发自己的 RTO 重传，同时把内层拥塞窗口砍半；
  3. 内层重传的新包被原封不动塞进已经堵塞的外层 TCP 发送队列里，进一步加剧外层拥堵，导致延迟更高、内层继续疯狂重传，形成正反馈死循环，最终吞吐归零甚至断连。

| 对比维度 | HOL Blocking（队头阻塞） | TCP Meltdown（双层 TCP 雪崩） |
| :--- | :--- | :--- |
| **公网 TCP 层数** | 1 层（单条外层 TCP 上做应用层多路复用） | 2 层（内层 TCP 与外层 TCP 同时跨公网） |
| **核心矛盾** | 一个逻辑流丢包，连累同连接里的其他流排队干等 | 内外两套独立的重传与拥塞控制互相误判、互相打架 |
| **典型场景** | HTTP/2、基于单条 TCP 多路复用的 L4/L7 代理 | 基于 TCP 传输的 L3 VPN（OpenVPN TCP、中继模式隧道） |

## 七、网卡硬件卸载：TSO 与 GRO

内核协议栈和物理网卡之间有一个很容易被忽略的协作机制——**硬件卸载（Offloading）**。

### TSO（TCP Segmentation Offload，发送端分段卸载）

- **没有 TSO 时**：应用程序调用 `send()` 写入 64KB 数据，操作系统内核必须在 CPU 里亲自把这 64KB 按 MSS（例如 1448B）切成四十多个标准 TCP 包，逐一拼装 IP/TCP 头部、计算校验和，再分几十次交给网卡发出。高带宽下 CPU 开销极大。
- **开启 TSO 后**：内核偷了个懒——它只做一次大致封装，把一个 64KB 的“超级大包”连同模板头直接丢给**物理网卡硬件芯片**，由网卡芯片在发送上线的瞬间，硬件自动按 MSS 切成标准小包、填入递增的 `seq` 并计算校验和。
- **接收端对称技术（GRO / LRO）**：收包时网卡或驱动先把连续到达的多个小包拼成一个大包再一次性交给内核协议栈，减少中断次数。

### 为什么排障时要知道 TSO？

1. **抓包会看到“超过 MTU 的超大包”**：在发送本机抓包时，由于 `tcpdump` 抓包的挂钩点位于内核发往网卡驱动之前、硬件还没切片，所以经常会在本地抓出 `length 4344` 甚至几万字节的“假大包”——并不是真的超 MTU 发上去了，只是还没过网卡 TSO 切片。
2. **物理网卡与虚拟网卡的发送路径不同**：
   - 物理网卡（如 macOS 的 `en0`、Linux 的 `eth0`）默认通常开启 TSO 和硬件校验和卸载；
   - 虚拟网卡（如 `utun` / `tun0`）背后没有硬件芯片，通常**不走硬件 TSO 卸载路径**。
   - 因此同一台机器的内核协议栈，发往物理网卡和发往虚拟网卡经过的代码分支不完全相同。在 BSD / macOS / Linux 历史上，不少棘手的 TCP 发送卡死或校验异常 Bug，恰恰是内核丢包恢复算法与物理网卡 TSO/驱动交互共同触发的。

## 八、UDP 与现代传输层的演进

UDP 本身极简（固定 8 字节头部：源端口、目的端口、长度、校验和），但近十年越来越多的新协议反而放弃 TCP、改在 UDP 上重建传输层：

1. **绕开操作系统内核僵化**：TCP 写在操作系统内核里，发明一个新特性要等客户端、服务端和沿途所有中间盒子（防火墙/NAT 设备）花十几年更新；基于 UDP 在用户态实现协议（如 **QUIC**），App 发个版本就能升级传输算法。
2. **彻底消灭跨流队头阻塞**：HTTP/3（基于 QUIC）在单条 UDP 会话里把多个流彻底解耦，A 流丢包只重传 A 流，B、C 流照常即时交付。
3. **承载隧道时避免 TCP Meltdown**：像 **WireGuard** 这类 L3 VPN 把外层放在 UDP 上，外层不重传、不做拥塞控制，只管加密转发；可靠传输和拥塞控制全部留给内层原本的 TCP 自己处理（即 **TCP over UDP**），既干净又低延迟。
4. **原生支持网络切换不断连（Connection Migration）**：TCP 死死绑定四元组，手机从 Wi-Fi 切到 5G 导致本地 IP 变化时，所有 TCP 连接必然断开重连；而 QUIC、WireGuard、**Mosh**（基于 UDP 的弱网远程终端）用连接 ID 或公钥识别对端身份，换了 IP 甚至休眠唤醒后会话依然丝滑延续。

## 九、从理论落到抓包：读懂 `tcpdump` 与 `ss`

学完上面的字段和状态机后，命令行里的抓包输出就不再是天书。

### 1. `tcpdump` 最常用的排查参数

```bash
# 抓取指定网卡上、与某主机某端口相关的 TCP 流量
sudo tcpdump -i en0 -nn -vvv -S 'host 203.0.113.10 and tcp port 443'
```

几个最关键的开关：
- `-i <网卡>`：指定抓哪张网卡（如 `en0`、`eth0`、`utun4`、`any`）。
- `-nn`：不做 DNS 域名反查，也不把端口号翻译成服务名（直接显示原始 IP 和数字端口，快且清晰）。
- `-S`：显示**绝对序列号**（默认 `tcpdump` 显示相对序号，长连接或中途开始抓包时用 `-S` 更容易对齐收发两端）。
- `-vvv`：打印最详细的 TCP 选项（**必须加它才能看到完整的 `sack` 区间、时间戳 `TS`、窗口缩放 `wscale`**）。
- `-w capture.pcap`：把原始包存成文件，丢进 Wireshark 里做图形化时间线分析。

### 2. 逐字段拆解一行真实 `tcpdump` 输出

假设看到这样两行抓包记录：

```text
10:15:02.104512 IP 192.168.0.195.54321 > 203.0.113.10.443: Flags [P.], seq 10000:11388, ack 500, win 2048, options [nop,nop,TS val 12345 ecr 67890], length 1388
10:15:02.120881 IP 203.0.113.10.443 > 192.168.0.195.54321: Flags [.], ack 10000, win 501, options [nop,nop,TS val 67905 ecr 12345,nop,nop,sack 1 {11388:12776}], length 0
```

按前面学过的概念，直接翻译成自然语言：

- **第一行（客户端发数据）**：
  - `Flags [P.]`：`P` = `PSH`，`.` = `ACK`（常见符号速查：`[S]`=SYN，`[S.]`=SYN+ACK，`[.]`=纯 ACK，`[F.]`=FIN+ACK，`[R]`=RST，`[none]`=无任何标志位）。
  - `seq 10000:11388` + `length 1388`：发送了从第 `10000` 到 `11387` 共 **1388 字节** 的数据（正好等于协商出的 MSS）。
  - `ack 500`：我这边已经收齐了对端第 500 字节之前的所有数据。
  - `win 2048`：我当前的接收窗口通告值（实际字节数还要乘上握手时协商的 `wscale` 缩放因子）。
- **第二行（服务端回报丢包）**：
  - `Flags [.]`、`length 0`：纯确认包，不带应用数据。
  - `ack 10000`：服务端连续收到的字节仍停在 `10000`，说明 **`10000:11388` 这一段丢了**。
  - `sack 1 {11388:12776}`：服务端通过 SACK 告诉客户端：“虽然 `10000:11388` 没到，但我已经收到了后面的 `11388:12776`，你只补发缺口就行！”

### 3. 搭配 Linux 的 `ss -tnpi` 看内核内部状态

`tcpdump` 看到的是**网线上飞过的包**，而 `ss -tnpi`（Socket Statistics）能直接透视**本机内核协议栈内部的连接账本**：

```bash
ss -tnpi 'dst 203.0.113.10'
```

- `-t`：只看 TCP；`-n`：数字端口；`-p`：显示归属进程；`-i`：打印内核内部 TCP 指标。
- 重点盯这几项：
  - `Recv-Q` / `Send-Q`：接收队列和发送队列里**积压未消化/未确认的字节数**（如果 `Send-Q` 持续不为 0 且纹丝不动，说明发送端卡住或对端没确认）。
  - `cubic` / `bbr`：当前连接使用的拥塞控制算法。
  - `rtt` / `rto`：当前估算的往返延迟与超时重传阈值。
  - `mss` / `cwnd`：协商的最大报文段长度与当前拥塞窗口（单位通常为分段数）。
  - `retrans` / `unacked` / `sacked`：正在重传、已发未确认、以及被对端 SACK 确认的包计数。
