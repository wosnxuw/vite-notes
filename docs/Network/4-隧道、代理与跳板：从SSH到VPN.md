# 隧道、代理与跳板：从 SSH 到 VPN

日常工作里经常会同时碰到 WireGuard、Tailscale、OpenVPN、Xray/sing-box（VLESS/Trojan）、SSH 端口转发、ProxyJump 和企业堡垒机。表面看它们都在“绕过限制把流量送过去”，但很多人最容易乱的地方，就是把它们混成一个大筐。

只要回到协议栈的分层视角，这些工具其实只分成**两大底层工作流派**：**L3 隧道封装（原样打包）** 与 **L4/L7 分段代理（终结接力）**。理清这条分界线，很多令人困惑的现象——包括“为什么 TCP 上还能再套一层 TCP”——就会瞬间迎刃而解。

---

## 一、先立坐标系：封装（Encapsulation）vs 代理（Proxying）

| 流派 | 典型代表 | 工作层级 | 是否创建虚拟网卡 | 底层动作 |
| :--- | :--- | :--- | :--- | :--- |
| **L3 隧道封装** | WireGuard、Tailscale、OpenVPN | **L3（网络层）** | 是（TUN / `utun` / `tailscale0`） | 把本机内核构造的**完整内层 IP+TCP/UDP 包原样加密打包**，放进外层隧道发给对端，对端解包后再喂回内核 |
| **L4/L7 分段代理** | SOCKS5、HTTP 代理、Xray / sing-box（含 Netstack TUN） | **L4 / L7** | 常规模式否；TUN 模式是 | 在本地把客户端的 TCP 连接**当场终结**，剥离内层 TCP 头，只转发纯应用层字节流；远端代理再向目标重新发起新 TCP 连接 |
| **应用层通道与跳板** | SSH（`-L/-R/-D`、`ProxyJump`）、堡垒机（JumpServer） | **L7（应用层）** | 否 | 借用 SSH 会话建立加密端口转发或两段接力，侧重单端口映射、远程登录与运维审计 |

硬要归类一句话记住：
- **WireGuard / Tailscale / OpenVPN** 给主机接上一张虚拟网卡，提供完整的**虚拟私有局域网（L3）**；
- **VLESS / SOCKS5 / HTTP 代理 / SSH 端口转发** 本质都是**应用层或连接级的代理转发**。

## 二、真·TCP over TCP vs 伪·TCP over TCP

传输层协议对载荷（Payload）是完全“盲视”的：只要用户态程序把内层数据当成普通二进制字节写进外层 TCP 的 Socket，外层协议栈就会照单全收、再加一层外层 TCP 头和 IP 头。

不过，把 **Tailscale（走中继时）** 和 **Xray（走 TCP 传输时）** 放在一起看，两者在公网上存在一个极其容易混淆的本质区别：**前者是真正的“两层传输层套娃”，后者在公网上其实只有一层 TCP**。

### 1. 真·TCP over TCP：L3 隧道封装（Tailscale DERP / OpenVPN TCP）

以在 Tailscale 中继模式（DERP 走 TCP 443）里跑 SSH 为例，数据包的真实旅程如下：

1. SSH 客户端发数据，本机内核协议栈构造一个完整的内层 IP 包：`[内层 IP 头] + [内层 TCP 头] + [SSH 数据]`，查路由表交给虚拟网卡（`utun` / `tailscale0`）。
2. 用户态的 `tailscaled` 进程从虚拟网卡把这个原始 IP 包当成纯字节流读出来，用 WireGuard 加密，再贴上 DERP 协议头。
3. `tailscaled` 把这坨加密字节写进自己连向公网 DERP 服务器的**外层 TCP 443 Socket**。
4. 本机内核协议栈第二次介入，把这坨字节当普通应用数据，加上外层 TCP 头和外层 IP 头，经物理网卡发上公网。

此时，物理网线上飞过的单个数据包里，确实同时嵌套了**两个完整的传输层头部**：

```text
[外层 IP] [外层 TCP] [TLS/DERP] [WG头 | 加密载荷( [内层 IP] [内层 TCP] [SSH数据] )]
              ▲                                              ▲
       负责公网可靠传输                                对端解包后才会被内核看到
```

内层 TCP 的两端是**本机内核 ↔ 目标机器内核**，外层 TCP 的两端是**本机内核 ↔ DERP 服务器**——两条独立的 TCP 状态机同时横跨公网链路。公网一旦丢包，外层暂停交付并重传，内层误以为超时也跟着重传并砍半窗口，极易触发 **TCP Meltdown（双层拥塞控制互相打架）**。

### 2. 伪·TCP over TCP：L4/L7 分段代理（Xray / sing-box）

Xray 这类代理工具（VLESS / VMess / Trojan 等）虽然也常用 TCP 承载用户的 TCP 流量，但它做的不是原样打包，而是**连接终结（Termination）与三段接力**：

以本地 SOCKS5 / HTTP 代理或透明代理为例：
1. **第一段（本机回环 / 局域网）**：SSH 客户端与本地 Xray 建立 TCP 连接。本地 Xray 读出数据后，内层 TCP 头在这里就被本机内核剥离并终结，Xray 拿到的是纯粹的应用层字节流（SSH 密文流）。
2. **第二段（公网隧道）**：本地 Xray 把纯字节流加密，通过一条外层 TCP（如 VLESS + TLS + TCP）发给远端 Xray 服务端。
3. **第三段（目标直连）**：远端 Xray 解密还原出纯字节流，再由远端服务器内核向目标机器发起一条全新的 TCP 连接。

```text
[SSH客户端] ══TCP 1(本机)══▶ [本地 Xray] ══TCP 2(公网)══▶ [远端 Xray] ══TCP 3(出站)══▶ [目标机器]
```

**追问：那 Xray / sing-box / Mihomo 开启 TUN 虚拟网卡模式呢？**
- 现代代理内核在 TUN 模式下，通常会在用户态内置一个轻量级 TCP/IP 协议栈（如 **gVisor netstack** 或 **lwIP**）。
- 它虽然同样从虚拟网卡读取原始 IP 包，但会立刻在本地用户态协议栈里把内层 TCP **当场终结**、抽取出纯应用层字节流，再塞进外层公网 TCP 发送。
- 因此，无论常规代理还是 Netstack TUN 模式，Xray 跑在公网上的数据包里自始至终**只有一层外层 TCP 头**。

### 3. 两者底层机制对比

| 维度 | Tailscale (DERP 模式) / OpenVPN (TCP) | Xray / sing-box (常规代理 & Netstack TUN) |
| :--- | :--- | :--- |
| **工作方式** | **封装（Encapsulation）**：原样打包内层 IP+TCP 包 | **代理（Proxying）**：本地终结 TCP，只转发纯字节流 |
| **公网单包 TCP 头数量** | **2 个**（外层明文 + 内层加密） | **1 个**（仅外层代理连接） |
| **内层 TCP 是否跨公网** | 跨公网（端到端） | 不跨公网（止步于本机回环或局域网路由器） |
| **是否触发 TCP Meltdown** | **会**（两套拥塞控制互相打架） | **不会**（本地段近乎零丢包、零延迟，公网仅一套拥塞控制；但多路复用时仍可能有单层队头阻塞 HOL Blocking） |

## 三、L3 VPN 与现代组网：OpenVPN、WireGuard 与 Tailscale

### 1. 三者的演进关系

- **OpenVPN**：传统企业级 VPN（既指协议也指软件），支持 UDP/TCP 和 TUN/TAP。传统中心式架构下，OpenVPN 服务端能看到隧道内解密后的 IP 包元数据；如果内部业务本身没加密，甚至能看到明文（不过只要未在本机手动信任企业根证书，HTTPS 流量依然受端到端 TLS 保护）。
- **原生 WireGuard**：现代极简 L3 隧道协议，原生只跑在 UDP 上，密码学与内核态性能都很出色。但传统 WireGuard 组网通常采用**中心辐射式（Hub-and-Spoke）**架构：所有节点连向一台拥有静态公网 IP 的中心枢纽，所有流量都绕枢纽走，中心服务器带宽压力极大，且新增节点需要手工维护公钥与配置。
- **Tailscale**：基于 WireGuard 的 **Mesh（网状 P2P）私有组网方案**。它的核心创新是把**控制面与数据面彻底分离**：中心服务器只管认证和下发网络拓扑，业务流量优先在节点间 P2P 直连，大幅减轻中心压力（其数据面普遍采用用户态实现 `wireguard-go`，便于在底层无缝接入 NAT 打洞和中继切换逻辑）。

### 2. Tailscale / Headscale 架构拆解

自建架构通常包含三部分角色：**控制面（Headscale）**、**中继与打洞辅助（STUN / DERP）**、以及各个**终端节点（Tailscale 客户端）**。

#### 控制面（信令、认证与密钥交换）
- **始终走加密 TCP 443**。
- 可使用 Tailscale 官方控制服务器，或自建开源替代品 **Headscale**。它负责用户认证、收集并分发节点公钥、同步节点列表、下发 ACL 权限规则以及协调打洞信息。
- Headscale 控制服务本身不作为普通对端客户端运行（通常不会在同一职责上同时跑 Headscale 和 Tailscale 客户端，因此在其他节点的 `tailscale status` 列表里不会把纯控制平面节点算作普通客户端）。

#### 数据面（节点间的实际流量）
Tailscale 数据面采取**“优先 UDP 直连，不通自动降级 TCP 中继”**策略：

1. **直连模式（Direct / P2P）：走 UDP**
   - 最理想的工作状态。两端节点借助 STUN（UDP `3478`）完成 NAT 打洞后，直接建立标准 WireGuard 隧道，全部流量走 UDP（本地默认端口常为 `41641` 或随机高端口）。
   - 此时在隧道里跑 SSH，结构是 **TCP over UDP**：外层无重传、无拥塞控制，丢包恢复完全交给内层 SSH 的 TCP 独立处理，延迟最低。
2. **中继模式（DERP Relay）：走 TCP 443**
   - 当网络封禁 UDP，或两端处于对称 NAT / 双层未放行 NAT 导致打洞失败时，自动降级通过公网 **DERP（Designated Encrypted Relay for Packets）** 服务器中继。
   - DERP 走 **TCP 443**（基于 TLS/HTTPS 协议升级，必要时也可走 TCP 80），目的是伪装成常规网页流量以穿透严格防火墙。
   - Headscale 可开启内置 DERP（同时兼任 STUN），也可以额外挂接多台自建或第三方公网 DERP 节点——因为 DERP 转发的依然是端到端加密的 WireGuard 密文，属于“盲人搬运工”，只需具备公网 IP 并在配置中注册即可分担区域流量或作为热备。

#### 验证当前走直连还是中继

在终端直接执行：

```bash
tailscale ping <目标节点名或IP>
```

- 输出显示 `via <公网IP>:<端口>` → 打洞成功，当前走 **UDP 直连**；
- 输出显示 `via DERP(<地区代码>)` → 打洞失败或尚未建立直连，当前走 **TCP 中继**。

#### 网段与系统路由特征
- Tailscale 为节点分配 `100.64.0.0/10`（RFC 6598 CGNAT 网段），并在系统内核路由表中注入明细路由（例如 Linux 下 `ip route get 100.64.0.22` 会显示命中 `dev tailscale0 table 52`）。
- 不读取代理环境变量的纯 TCP 程序（如 `ssh 100.64.0.x`）会直接命中内核虚拟网卡路由；而读取 `HTTP_PROXY` 的应用层客户端如果未配置绕过该网段，流量会被提前拐进本地代理端口。

## 四、应用层隧道与跳板：SSH、ProxyJump、堡垒机与 Mosh

### 1. SSH 的协议定位与端口转发

正常情况下，SSH 和 SSH Jump **全部走 TCP**（默认端口 `22`），不走 UDP——交互式终端和加密会话强依赖 TCP 提供的有序字节流和丢包重传。在配置防火墙、安全组或端口映射规则时，只需放行对应 TCP 端口。

除了远程登录，SSH 也支持三种经典的应用层端口转发（本质都是把指定端口的 TCP 字节流塞进加密的 SSH 连接里搬运）：
- **`-L`（本地端口转发）**：把本机某个监听端口的流量，经 SSH 服务端转到远端能访问的内网地址（常用于访问远程内网数据库/Web 面板）。
- **`-R`（远程端口转发）**：把远端服务器某个端口的流量，反向拉回本机或本机所在内网（简化版的反向穿透）。
- **`-D`（动态转发）**：在本机开一个 SOCKS5 代理端口，所有走该代理的流量都由远端 SSH 服务器代为出站。

### 2. SSH Jump（`-J` / `ProxyJump`）的双段 TCP 隧道

当防火墙阻断本机直连目标机器，但存在一台双方可达的中间跳板机时，`-J` / `ProxyJump` 会建立**两段独立的 TCP 连接**，并在其上套出端到端加密通道：

1. **第一段（本机 → 跳板机）**：本机向跳板机发起标准 TCP 连接并完成 SSH 认证。
2. **第二段（跳板机 → 目标机）**：跳板机收到 `direct-tcpip` 通道请求后，向目标机的 22 端口发起第二段 TCP 连接。
3. **端到端加密会话**：本机把跳板机转发过来的 TCP 字节流当作底层管道，直接与目标机完成第二次 SSH 握手与加密会话。

```text
[本机] ════TCP 1 (SSH 认证跳板机)════▶ [跳板机 (纯转发管道)] ════TCP 2 (direct-tcpip)════▶ [目标机器]
  └────────────────────────── 端到端加密 SSH 会话（跳板机无法解密）──────────────────────────┘
```

关键特性：普通 `sshd` 跳板机就像 DERP 一样是“瞎子”，只负责搬运密文，看不到你在目标机里敲的命令。因此使用传统 `ProxyJump` 时，**本机必须同时持有登录跳板机的凭据和登录目标机的凭据**。

### 3. 普通跳板机 vs 企业堡垒机（以 JumpServer / Koko 为例）

企业内网中常见的堡垒机（如 JumpServer，其字符终端连接器 **Koko** 默认监听 `2222` 或自定义的 `32222` 端口；而堡垒机服务器自身的 `22` 端口是运维堡垒机本体用的，日常连接资产不走 22）在定位上与纯管道式的 `ProxyJump` 有明显差异。

假设管理员为你授权了目标资产 A，通常有三种连接模式：

1. **真正直连**：在堡垒机 Web 面板首次登录后上传公钥，后续直接从个人电脑 SSH 连向资产 A，完全绕过堡垒机（脱离了堡垒机审计的初衷，一般仅相当于借平台分发密钥）。
2. **终端中转（标准审计模式）**：`本机 ── SSH ──▶ Koko ── SSH ──▶ 资产 A`。
   - Koko 在中间**终结了你的 SSH 会话**，再代表你去连接资产 A，因此 Koko 能完整记录你的所有命令与输出用于合规审计。
   - 这类模式不一定非要在浏览器 WebUI 里操作：通常可在堡垒机设置里生成/配置密钥，用本地终端直接连接 Koko 进行交互或中继，不必每次复制临时口令。
3. **Jump / 隧道模式的差异**：
   - 如果是**普通 `sshd` 服务器**做 `ProxyJump`：纯 TCP 管道，需要两套密钥，中间节点无法解密和审计；
   - 如果是 **Koko 堡垒机**提供的 Jump 能力：你不需要持有目标资产 A 的私钥，由 Koko 拿出托管凭据去连接资产 A 再把会话桥接给你，因此在架构上堡垒机仍具备审计权限（部分企业环境也会按安全策略关闭该功能）。

### 4. 什么情况下 SSH 相关场景会见到 UDP？

虽然标准 SSH 不走 UDP，但有两种常见场景会在抓包或排查时看到 UDP：

- **外层 VPN / 隧道封装**：SSH 跑在 WireGuard、OpenVPN（UDP 模式）或 QUIC 隧道内部时，物理网卡外层抓到的是 UDP，但隧道解包后里面的 SSH 依然是 TCP。
- **Mosh（Mobile Shell）**：专门针对高丢包、高延迟或移动切换网络设计的远程终端工具。它仅在启动瞬间走一次标准 SSH（TCP）完成身份认证并在远端拉起服务端进程，**之后全部终端屏幕状态同步彻底切换为纯 UDP（默认端口 `60000–61000`）**，不再使用 TCP，从而避开弱网下的 TCP 阻塞与断连问题。
