# NAT、公网链路与内网穿透

前面两篇把单机内部的网卡、路由表和传输层（TCP/UDP）理顺了。但数据包离开自家或公司路由器、真正踏入公网后，马上会撞上两个现实世界的硬约束：

1. **绝大多数设备没有公网 IP**——它们躲在一层甚至多层 **NAT** 后面，外网无法直接找到它们；
2. **即便连上了公网服务器**，数据包在运营商骨干网里怎么绕路、会不会丢包限速，也不是靠换个传输协议就能凭空解决的。

这一篇把 NAT 的底层映射机制、P2P 打洞原理、打不通时的中继方案（FRP / TURN / DERP），以及公网运营商链路问题一次讲透。

---

## 一、NAT 底层在干什么？（连接跟踪与映射表）

因为 IPv4 公网地址数量有限，家庭和企业通常只分到 1 个出口公网 IP（甚至运营商机房里还再包一层 CGNAT），内部几十上百台设备共用私有网段（如 `192.168.0.x`）。

路由器能让这么多私网设备同时上网，靠的是 **NAT（准确说是 NAPT，网络地址端口转换）**。它在路由器内存里维护着一张动态的**连接跟踪映射表（conntrack）**：

1. **出站改写（SNAT）**：内网电脑 `192.168.0.10:54321` 访问公网 `8.8.8.8:443`。数据包经过路由器时，路由器把**源 IP 和源端口**改写成自己的出口地址，比如 `203.0.113.5:31001`，同时记下一条映射：`192.168.0.10:54321 ↔ 203.0.113.5:31001`。
2. **回程还原（DNAT）**：`8.8.8.8:443` 把回包发给 `203.0.113.5:31001`。路由器查映射表找到记录，把**目的 IP 和目的端口**改回 `192.168.0.10:54321`，精准递回内网电脑。

由此直接衍生出两个核心特性：
- **天然拦截陌生入站连接**：如果公网上一台陌生主机主动往 `203.0.113.5:31001` 发包，而路由器映射表里没有对应记录（或不符合该 NAT 的过滤规则），路由器根本不知道转给内网哪台机器，直接丢弃。
- **映射条目有超时时间**：路由器内存有限，一条连接长时间没流量就会被清理（尤其是无连接的 UDP，超时往往只有 30~120 秒）。这也是为什么许多 VPN 和内网穿透客户端需要定期发送心跳包（如 WireGuard 的 `PersistentKeepalive`）来维持映射不掉。

## 二、NAT 类型：锥形 NAT vs 对称 NAT

按单个 NAT 设备**分配映射端口的策略**和**允许谁回包的过滤策略**，经典分类为 5 种（NAT0 ~ NAT4）：

| 编号 | 名称 | 端口映射规则 | 外部入站放行规则 | P2P 穿透难度 |
| :--- | :--- | :--- | :--- | :--- |
| **NAT0** | **公网 IP（Public）** | 无需 NAT | 直接可达（仅受主机/路由器防火墙约束） | 无需穿透 |
| **NAT1** | **完全圆锥形（Full Cone）** | 内网固定 `IP:Port` 始终映射到同一公网 `IP:Port` | **任意**外部主机只要知道这个公网 `IP:Port` 都能主动发包进来 | 最容易 |
| **NAT2** | **地址受限圆锥（Address-Restricted Cone）** | 同上（始终同一公网端口） | 只有内网设备**主动联系过的外部 IP**（任意端口）才能发包进来 | 较容易 |
| **NAT3** | **端口受限圆锥（Port-Restricted Cone）** | 同上（始终同一公网端口） | 只有内网设备**主动联系过的外部 `IP:Port`** 才能发包进来 | 中等（常规打洞可通） |
| **NAT4** | **对称 NAT（Symmetric）** | **按目标地址/端口动态重新分配** | 仅允许对应的外部 `IP:Port` 回包 | **极难** |

### 锥形与对称的本质区别

- **锥形 NAT（NAT1 ~ NAT3，家用路由器常见默认模式）**：路由器把自己的一个公网端口和内网 PC 的一个端口相对固定地绑在一起。无论内网 PC 访问公网的 A 服务器还是 B 服务器，对外暴露的源端口都一样（比如都是 `31001`）。
- **对称 NAT（NAT4，常见于企业防火墙、校园网、部分移动蜂窝网）**：映射关系**取决于目标地址**。内网 PC 访问 A 时，路由器分配公网端口 `31001`；紧接着同一个本地端口去访问 B，路由器换成了全新的公网端口 `45892`。因为对外端口随目标动态跳变，第三方根本无法把你“真实可用的端口”告诉对端，导致常规 P2P 几乎失效。

> **容易混淆的关键点**：NAT1 ~ NAT4 描述的是**单个 NAT 设备的行为模式**，而不是你网络里串联了**几层 NAT**。

## 三、单层 NAT、多层 NAT 与端口放行机制

真实家庭和公司网络里，数据包往往不止过一道 NAT：

```text
单层 NAT（理想家宽）：
内网主机 (192.168.0.x) ──▶ 自购路由器 (拨号拿公网 IP) ──▶ Internet

双层 / 多层 NAT（现实高频痛点）：
内网主机 (192.168.0.x) ──▶ 二级路由器 (192.168.1.x) ──▶ 光猫路由模式 (100.64.x.x) ──▶ 运营商 CGNAT ──▶ Internet
```

为了解决入站被拦的问题，路由器常见三种端口放行机制：
1. **静态端口转发（Port Forwarding）**：手动在路由器里写死规则（如“公网端口 `2222` → 内网 `192.168.0.10:22`”）。
2. **DMZ（非军事区）**：把路由器上未命中其他转发规则的所有入站流量，全部转发给内网某一台指定主机。在光猫无法改桥接但有管理员权限时，常把光猫 DMZ 指向下级路由器的 WAN 口来打通一层阻塞（注意：开启 DMZ 后，防护责任完全落到下游设备自身的防火墙上）。
3. **UPnP / NAT-PMP / PCP**：通用即插即用与端口控制协议，允许内网程序（在线游戏、BT、P2P 组网客户端）自动向网关申请临时端口映射，无需人工登录路由器后台配置。

**多层 NAT 的核心卡点**：在二级路由器上开启 UPnP 或静态端口转发，**只能打通最内层路由器这一道墙**。如果前级光猫仍处于路由模式且未配置 DMZ/转发，或者运营商出口本身是 CGNAT，外网入站数据包依然会在外层网关被挡掉。

## 四、NAT 穿透（P2P 打洞）：STUN 与成败边界

如果两端主机都躲在 NAT 后面、且都没法手动配端口映射，还能不能直接点对点（P2P）通信？答案是靠 **STUN + UDP 打洞（Hole Punching）**。

### 1. STUN 如何当“镜子”？

**STUN（Session Traversal Utilities for NAT，NAT 会话穿越实用工具）** 是一个极轻量的公网辅助协议（常见端口 UDP `3478`），用来帮内网主机看清自己在公网上的真实面貌：

1. **发现映射地址**：客户端向 STUN 服务器发请求：“你看到的我是谁？”STUN 服务器从收到的数据包 IP/UDP 头里提取源地址 `IP1:Port1` 并原样答复给客户端。
2. **判断 NAT 类型**：客户端向 STUN 服务器（或另一台不同 IP 的 STUN 节点）再发一次请求，要求对方从**不同的 IP 或端口**通信/响应。客户端对比两次被告知的公网地址：
   - `IP1:Port1 == IP2:Port2` → 映射端口不随目标变化，说明是**锥形 NAT**；
   - `IP1:Port1 != IP2:Port2` → 映射端口随目标变化，说明是**对称 NAT**。

### 2. UDP 打洞（Hole Punching）的完整时序

假设主机 A 和主机 B 都在各自的锥形 NAT（如 NAT3）后面，公网上有一台负责协调交换地址的信令服务器（控制面）：

1. **各自照镜子**：A 和 B 分别向 STUN 查询到自己的公网映射 `A_pub` 和 `B_pub`，并通过信令服务器交换给对方。
2. **同时向外“开洞”**：
   - A 主动向 `B_pub` 发一个 UDP 探测包。此时 B 的 NAT 还不认识 A，这个包大概率会被 B 的路由器丢掉——但这没关系，**真正目的是让 A 自己的 NAT 记下一笔出站记录：“我允许 `B_pub` 给我的端口回包”**。
   - 几乎同一时间，B 主动向 `A_pub` 发一个 UDP 探测包。因为 A 的 NAT 刚才已经记录了 `B_pub`，这个包直接穿透进 A；同时 B 自己的 NAT 也打开了允许 `A_pub` 进入的洞。
3. **直连建立**：双方互相收到对方的探测包后，P2P 直连通道打通，此后业务流量直接走 `A_pub ↔ B_pub`，不再经过任何中转服务器。

### 3. 什么组合能打通？什么组合必失败？

| A 端网络环境 | B 端网络环境 | 打洞结果 | 原因简析 |
| :--- | :--- | :--- | :--- |
| 任意 NAT | 公网 IP（NAT0） | **必通** | A 直接主动连 B 的公网地址即可 |
| 锥形（NAT1/2/3） | 锥形（NAT1/2/3） | **通常可通** | 双方映射端口稳定，同步互发即可互开通道 |
| 锥形（NAT1/2/3） | 对称（NAT4） | **视情况** | 若锥形端是 NAT1/2 或对称端端口分配可预测，有机会成功；若锥形端是严格 NAT3 且对称端端口随机，常失败 |
| **对称（NAT4）** | **对称（NAT4）** | **必败** | 双方对彼此的映射端口都和发给 STUN 时不同，互相猜不中对方的真实端口 |
| **对称（NAT4）** | **多层 NAT 且外层未放行入站** | **基本必败** | 对称端换端口 + 多层防火墙拦截，无法完成双向握手 |
| 任意 | 所在网络封禁 UDP | **必败** | UDP 探测包根本出不去 |

## 五、打洞失败后的兜底：公网中继（FRP / TURN / DERP）

当两端网络拓扑注定打洞失败（例如公司对称 NAT 连家里双层 NAT，或者严格防火墙封禁了 UDP），唯一通用的解法就是引入一台**拥有公网 IP 的中转服务器**，把“外网连内网”转化为“两端都主动向外连公网”。

### 1. FRP（Fast Reverse Proxy，快速反向代理）

FRP 是最经典的**端口级反向代理中转**工具。架构非常简单：一台部署在公网云服务器上的服务端（`frps`），加上跑在内网机器上的客户端（`frpc`）。

以“从外部访问家里内网主机（`192.168.1.100`）的 SSH 服务（端口 `22`）”为例：

1. **建立控制隧道**：家里的 `frpc` **主动向外发起连接**，连上公网服务器 `1.1.1.1:7000` 上的 `frps`。因为是内网主动出站，完全符合 NAT 放行规则，一条长连接控制隧道由此建立。
2. **公网访问与流量中转**：
   - 公网 `frps` 在配置中监听端口 `6000` 并将其绑定给家里的 SSH 服务；
   - 外部终端执行 `ssh -p 6000 user@1.1.1.1`；
   - `frps` 在 `6000` 端口收到请求后，通过控制隧道通知家里的 `frpc`：“有新连接到了”；
   - `frpc` 在内网本地连向 `192.168.1.100:22`，并与 `frps` 协作完成双向流量转发。

FRP 的本质是一个部署在公网的**专用中转代理**，不是 P2P，传输速度和并发完全受公网服务器的带宽与延迟制约。

### 2. TURN 与 DERP（组网协议内置中继）

在 WebRTC 音视频或现代点对点组网（如 Tailscale）里，中继服务被无缝集成成了自动降级机制：

- **TURN（Traversal Using Relays around NAT）**：STUN 的“老搭档”，当 ICE 框架发现 STUN 打洞不通时，自动切换到 TURN 服务器中转媒体流。
- **DERP（Designated Encrypted Relay for Packets）**：Tailscale 设计的专用加密中继协议。节点间优先尝试 UDP 直连，一旦因对称 NAT、双层 NAT 或 UDP 封禁导致打洞失败，立刻自动无缝降级到公网 DERP 节点转发流量。
  - DERP 默认跑在 **TCP 443 端口（基于 HTTPS/TLS 升级）**，目的是伪装成普通网页流量，穿透极其严格的企业或校园防火墙；
  - 经过 DERP 的载荷依然保持端到端加密（如 WireGuard 密文），中继服务器相当于一个“盲人搬运工”，只按目标公钥转发密文，无法窥探内容；
  - **代价**：除了受中继服务器带宽和地理延迟限制外，原本跑在 UDP 上的隧道被迫降级到外层 TCP 443 上，在丢包环境下可能放大卡顿和单连接故障面。

## 六、跨出网关之后：公网路由与运营商链路

数据包跨过 NAT 进入公网后，并不存在一条“直达目标服务器的直线”。互联网是由成千上万个独立网络——**AS（Autonomous System，自治系统，如中国电信 AS4134、中国联通 AS4837、AWS、Cloudflare）**——通过 **BGP（边界网关协议）** 互联拼接而成的。

### 为什么有时候“换什么协议都卡”？

在连接海外或跨运营商公网服务器时，经常会遇到一种困惑：TCP 握手慢、延迟抖动大、偶尔半死不活，换了各种加密伪装协议甚至切到基于 UDP 的高速拥塞控制协议，短期好转后又很快变慢或被阻断。

底层原因往往不在协议本身，而在**物理与路由层面**：

1. **骨干网拥塞是物理瓶颈**
   - 普通家庭宽带出境通常默认走民用普通骨干网（例如电信的 **163 骨干网 / AS4134**）。在晚高峰时段，普通骨干网的国际出口链路负载极高、队列积压严重、丢包率飙升。
   - 无论你买的是小众 VPS 还是 AWS / Azure 这类顶级大厂的常规机房，只要去程或回程路由落在了拥塞的普通骨干网上，就同样会卡。
2. **协议优化与路由优化解决的是两件事**
   - **换代理/传输协议**（改 TLS 伪装、换拥塞算法）：解决的是**特征隐蔽性**和**轻度随机丢包下的发包效率**；
   - **换优化线路 / 专线**（如电信 CN2 GIA、联通 AS9929、移动 CMIN2 或优质中转/专线）：解决的才是**出口拥塞与跨网绕路**这一根因。
3. **运营商对 UDP 的普遍 QoS 限速**
   - 许多运营商在跨省或国际出口对长时间大流量的 UDP 流有严厉的限速（QoS）甚至阶段性阻断策略。基于 UDP 的高速传输协议虽然抗丢包强，但在被针对性丢包或整段回程 UDP 阻断时，仍需有 TCP 路径作为兜底。
4. **多地点、多运营商环境下的选线现实**
   - 如果需要同时从公司宽带、家里宽带、手机蜂窝网访问同一台服务器，只针对单一运营商优化的线路（例如只买了电信 CN2 GIA，但联通/移动回程绕路）会导致体验割裂；多端场景通常需要**三网优化线路**，或者为不同出口准备对应的中转节点。
